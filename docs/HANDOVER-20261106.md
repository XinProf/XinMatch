## 1. 项目目标

### 1.1 一句话

**XinMatch 是一个净室实现的粉末 XRD 物相分析平台**：用 CC0 的 COD 数据库做参考库，用公开文献算法做检索/定量/指标化，用 Qt 做与商业软件同源的 GUI，最终在真实实验室谱上达到「能用、可比、可复现」的物相鉴定效果。

### 1.2 四层兼容性目标（L1→L4）

| 层 | 目标 | 验收指标 |
|---|---|---|
| **L1 文件格式** | 读得进、写得出用户手上的数据 | 格式 round-trip 测试通过（当前支持 xy/txt/dat/csv/mdi/raw/xrdml/json 等） |
| **L2 参考库** | 覆盖 COD；ICDD PDF-2 作为「用户自带授权」插件 | 条目数、检索字段对齐 |
| **L3 算法** | **不比商业软件差太多**，不追求 FoM 数值相等（权重未公开） | 标准样品集 Top-N 命中率 ≥ 对标软件的 80% |
| **L4 工作流** | 术语、菜单、操作路径一致 | 用户可按商业软件手册操作本软件 |

> **L3 是最关键的产品判断**：FoM 内部权重不可知，所以验收只看**排序质量**，不看数值。这条决定了后面所有基准的形态（见 §4.2、§6.3）。

### 1.3 功能边界：做什么、明确不做什么

| 做 | 不做（或外包） |
|---|---|
| 数据模型、I/O、预处理、寻峰 | **不自研 Rietveld / Le Bail 内核** → 委托 GSAS-II |
| 参考库构建与多库挂载 | 不打包 ICDD 数据（版权） |
| 检索（峰列表 FoM + FPFM 全谱拟合 + 序贯鉴定） | 不做逐位复刻商业软件 FoM |
| 四态元素（必有/含有/可能/没有）+ 闭环、晶系、密度等限制条件 | 不做晶体结构解析（ab initio） |
| RIR/内标/DOC 定量、Treor/Dicvol 指标化 | 3D 结构可视化（降级 P3，可延后） |
| 报告导出（HTML/MD/TXT/PDF/PNG/SVG） | 仪器厂商私有格式的完整覆盖（按需补） |

**为什么精修外包**：Rietveld 是一个十年量级的坑（峰形、背景、择优取向、约束、收敛策略），而 GSAS-II 已是 BSD 许可的成熟实现。把精修外包，XinMatch 专注在「检索质量 + 用户体验」这两个真正差异化的点上。

### 1.4 差异化路线

不做「又一个 Match!」，做三件商业软件做得不够好的事：

1. **开放数据链**：COD 全量 + PCOD（百万级）+ TCOD + Materials Project + 用户自带 PDF-2，统一 `.xinDB` 格式，任意位置挂载。
2. **可解释的检索**：候选为什么排第一、哪些峰没被解释、少线相为什么被标记 —— 都要能说清（`★` 少线相标记、残差谱、逐峰归属）。
3. **工程化交付**：CLI/批处理/`library API`/`.xinm` 项目文件，让检索结论能进自动化流程和精修流程。

## 2. 设计思路与方案

### 2.1 净室实现（Clean Room）

规格只来自：公开文档、已发表算法、黑盒文件格式观察。**不反编译、不复用专有代码、不抄界面资源**。

这条不是洁癖，是法律边界：项目是 Academic + Commercial 双许可，必须保证代码来源干净。对应到工程上就是「每个公开函数 docstring 要写清算法出处」（`docs/CONVENTIONS.md` §4）。

### 2.2 内核 / GUI 完全解耦

```
xinmatch/
├── core/        # 纯计算：numpy + dataclass，零 GUI 依赖，可 CLI 调用，可单测
│   ├── model/   # Pattern / Peak / Entry / Phase / Restraints / Project
│   ├── io/      # 格式读写 + .xinm 项目文件
│   ├── preprocess/  # 平滑 / SNIP 背景 / Kα2 剥离 / 零点
│   ├── peak/    # 寻峰 + pseudo-Voigt 拟合
│   ├── db/      # .xinDB 读写（reader_v3 / writer_v3 / multi_db）
│   ├── search/  # 预筛 → FoM → 序贯鉴定
│   ├── index/   # Treor / Dicvol
│   ├── refine/  # GSAS-II 适配器（不自研内核）
│   ├── quant/   # RIR / 内标 / DOC
│   ├── micro/   # Scherrer / Williamson-Hall
│   └── report/  # 报告渲染
├── ui/          # PySide6 薄层
└── cli/         # 命令 + 批处理
```

**为什么这样切**：让低能力模型也能在无 GUI 环境下独立开发 + 验证一个模块 —— 「输入数组 → 输出数组 → pytest 断言」，不需要跑界面就能判断对错。**这是「小步可验」能成立的前提**，也是所有拆分原则的地基。

### 2.3 `.xinDB` v3：为什么自造列存格式

v3.0.0 之前用 SQLite 行存（`COD_inorganics.sqlite`），问题：

| 问题 | 后果 |
|---|---|
| 逐相读峰要 N 次 random IO | 47 万相检索秒级 |
| 库体积大 | COD-Full 53 万相 ≈ 20~29 GB |
| 峰数据与元数据混在一起 | 无法按 chunk 顺序解码 |

v3 改成列存 + 分块：

```
meta        一行 JSON：schema_version / data_date / build_time / peak_convention / 号段偏移…
entries     每相一行元数据（id / formula / cell / space_group / elements / density…）
peak_chunks 每 4096 相一个 chunk，float32 列存（2θ / d / I / hkl）
element_inv 元素 → 相 id 倒排（唯一正确的元素筛路径）
```

实测收益：COD-Full 53.2 万相仅 **0.86 GB**（对比 SQLite 20~29 GB 量级），COD-Inorg 7.8 万相 **113 MB**。

**检索成本（2026-11-06 重新实测，取代早期的「4.5 s / 预筛 66%」口径）**：只有两段随库规模涨 ——
预筛 `O(相数 × top_k × 窗数)`、`fetch_peaks` 正比于**触及的 chunk 字节数**而非命中数。
1.06M 相的 PCOD：预筛 1.36 s / 取峰 0.90 s / 打分 0.48 s，进程内合计 3.1 s、CLI 墙钟 5.7 s；
默认 78k 库进程内 0.92 s、CLI 墙钟 2.3 s（其中 1.3 s 是导入）。
`fetch_peaks` 有约 800 倍读放大（1000 候选落在 196/260 个 chunk，读 955 MB 取 1.2 MB）。
**schema v3.1 已评估为不做**，理由与「chunk 边界表为何无效」见 §6.8。

### 2.5 检索链路（理解代码的入口）

```
原始谱 → 预处理 → 寻峰
                    ↓
        ┌── 预筛 prescreen ─────────────────────────┐
        │  1) 元素倒排粗筛（必含/必不含，走 element_inv）│
        │  2) top_d 矩阵 × 测量窗 布尔命中 → main_hit  │
        │  3) 强度形加权 whits + 命中数 hits            │
        │  4) 排序键：main_hit 门控 → whits → hits      │
        │  5) diversify 配额（默认 20% 名额给非门控相） │
        └───────────────────────────────────────────┘
                    ↓ 800~1000 候选
        fetch_peaks（顺序解码 chunk）
                    ↓
        FoM 五分量打分 + 相位级折叠（same_phase / group_same_phase）
                    ↓
        Top-N 候选 →（可选）序贯鉴定：扣除已确认相 → 残差再检索
                    ↓
        `.xinm` 导出（结论 + CIF 引用 + manifest）→ 精修项目
```

三处最容易踩的点：
1. **排序键里 `main_hit` 是二值门控，不是缺陷而是载荷**（§6.3 有实证）。
2. **`same_phase` 折叠**决定「同一相的不同卡片」是否算一个，直接影响基准口径。
3. **预筛名额**是硬上限：候选不在池内，FoM 再好也上不来（`3-1` 次相失败的根因）。

### 2.6 版本号单一真相源（v3.5.0 落地）

曾经四处各写一遍然后漂移：`pyproject.toml` 3.4.1 / `__init__._FALLBACK_VERSION` 3.4.0 / `xinmatch.spec` 3.4.0 / `xinmatch_setup.iss` 10 处 3.4.0。后果不是难看：**冻结 exe 的 About 报 3.4.0、源码报 3.4.1、安装包名固定 3.4.0，用户报 bug 的版本号对不上 tag**。

现在的机制：

| 落点 | 规则 |
|---|---|
| `pyproject.toml` | **唯一真相源** |
| `xinmatch/__init__.py` | `_FALLBACK_VERSION` 必须与之一致（测试校验） |
| `xinmatch.spec` | 从 pyproject **推导** `APP_VERSION`/`VERSION_TUPLE`，禁止写字面量 |
| `tools/xinmatch_setup.iss` | 只剩一处 `#ifndef AppVersion` 默认值，其余全 `{#AppVersion}` |
| `tools/build_exe.ps1` | `-Version` 默认从包读；构建后校验 exe 的 `FileVersion` |
| `tests/test_version_consistency.py` | 5 项检查，任一处漂移即失败 |

**下次 bump 只改 2 个文件**（pyproject + `_FALLBACK_VERSION`），不再照 11 处清单人工改。

## 3. 任务拆分原则与方法（面向低能力模型）

这是本项目最重要的工作方法。核心命题：**如何把一个 XRD 分析平台拆成「低能力模型也能独立做对」的步骤**。

### 3.1 颗粒度：一个任务 = 一次会话

三条硬指标，缺一条就说明拆得不够细：

1. **单任务可独立验收**：有明确的 pytest 通过条件或数值阈值，不需要「感觉一下对不对」。
2. **单任务一次会话可完成**：含代码 + 测试 + ruff + 自检，数小时量级。做不完 = 拆得不够细。
3. **单任务不跨模块**：只改一个目录，避免和多任务冲突。

### 3.2 每个任务必须写清的五件事

这是给低能力模型的「防跑偏清单」。少写任何一条，模型就会自由发挥：

| 项 | 要求 | 反例（会导致跑偏的写法） |
|---|---|---|
| **路径** | 要改/新建的**具体文件** | 「在 db 模块里加个索引」 |
| **签名** | 函数名、参数名、类型、返回类型 | 「写个函数算 FoM」 |
| **I/O** | 输入从哪来、输出到哪去、单位与坐标系 | 「读谱然后检索」（哪种谱？2θ 单位？） |
| **算法** | 公式/文献/伪代码，或明确「照抄哪个已有函数的结构」 | 「用 XX 算法」 |
| **边界** | 空输入、单峰、零强度、越界、NaN 怎么处理 | 不写 → 模型自己猜 → 测试时炸 |

### 3.3 拆分模板

```
T<phase>.<index> <一句话标题>

目标：<这个任务完成后，什么能力变得可用>
改动：<文件路径列表>（新建/修改）
签名：<函数/类签名，含类型>
算法：<公式或伪代码；引用 docstring 要写的出处>
边界：<空/单点/异常输入的处理约定>
验收：<pytest 文件 + 具体断言；数值任务给合成回归的容差>
不做：<明确划出范围外，防止顺手改别的模块>
```

**「不做」这一栏是防扩散的关键**。低能力模型的典型失败模式不是做错，而是「顺手把相邻功能也改了」。

### 3.4 并行拆分

按**目录隔离**并行，典型一轮 3 个 Agent：

```
Agent A → core/search/ + tests/search/
Agent B → core/refine/  + tests/refine/
Agent C → core/quant/   + tests/quant/
```

约束：
- 三个 Agent 的目录不重叠（历史成功案例：search+refine+quant、search+refine+micro）。
- 每个 Agent 只跑自己的子目录测试；**全量 pytest 由主 Agent 统一跑**，避免并发抢资源超时。
- 有依赖关系的必须串行（如 Rietveld 定量必须等 GSAS-II 适配闭环）。

### 3.5 依赖排序原则

1. **先数据后算法**：口径（波长、d 范围、归一化）没冻结，算法写了也要返工。
2. **先尺子后引擎**：基准/真值没自洽，调参就是在错误的尺子上优化（§6.3 有惨痛教训）。
3. **先内核后 GUI**：GUI 最后统一接，避免界面先定死接口。
4. **先可逆后不可逆**：能补丁的（元数据）先补丁，能重建的（物理量）才重建（§6.2）。

## 4. 验收方法（每一步怎么证明「到了」）

四层闸门，逐层加严。**任何一层不过就不进入下一层**。

### 4.1 四层闸门

| 层 | 内容 | 命令 | 通过标准 |
|---|---|---|---|
| **L1 单任务** | 该任务自己的测试 | `pytest tests/<sub>/test_<topic>.py -q` | 全绿 |
| **L2 模块** | 所在子目录全测 | `pytest tests/<sub>/ -q` | 全绿，无新增 skip |
| **L3 全量** | 全仓回归 | `pytest -q` | 全绿（2026-11-06 多轮复测：元素约束产品化与 `prescreen_order` 裁定均 **1587 passed / 4 skip / 1 xfail / 0 failed**，15 min 22 s / exit=0 与 16 min 26 s / **exit=1**；大库提示轮 **1595 passed**，15 min 54 s；CLI 元素约束轮 **1624 passed / 4 skip / 1 xfail / 0 failed**，21 min 25 s / **exit=1**；T0.8 文档收尾轮同为 **1624 passed / 4 skip / 1 xfail / 0 failed**，16 min 15 s / **exit=1**；CLI 大库引导轮 **1654 passed / 4 skip / 1 xfail / 0 failed**，16 min 8 s / **exit=0**；IUCr 基准轮 **1654 passed / 4 skip / 1 xfail / 0 failed**，13 min 51 s / exit=0（本轮只动 `tools/`，无新增用例）；族级口径修复轮 **1654 passed / 4 skip / 1 xfail / 0 failed**，17 min 58 s / **exit=1**（只动 `tools/` 与文档，无新增用例；首轮出现过 1 例偶发失败，`--lf` 单跑即过、重跑全绿，`-q` 摘要行未落盘故未指名））。**判绿看进度行统计，不看 `$?`** —— 多轮的 exit=1 都是会话结束安全钩子拦截 pytest 临时目录清理（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，临时项 > 50 阈值），进度行 `F`/`E` 均为 0；而且 `-q` 的收尾 counts 行偶尔整行不落盘，只有进度点，此时按进度行字符数数（`.`/`s`/`x`）才是唯一可靠口径 —— **统计时必须先剔除钩子那行 JSON，它的 `SAFE_DELETE` 字样里含 `F`/`E` 字符，按全文数会数出假的 F/E** |
| **L4 基准** | 三把尺子：合成谱 / 13 组实验室真实谱 / IUCr CPD 标准谱 | `python -m tools.bench_pattern_set` / `bench_real_samples` / `bench_iucr` | 不劣于上一版；劣化必须解释。三把尺子结论相反时不得单方面改默认值（§6.6） |

静态检查固定三项：`ruff check`、`mypy xinmatch/core`、以及新增测试文件本身的可读性（有注释说明为什么这么断言）。

### 4.2 数值任务怎么验收

XRD 算法的坑在于「看起来对」。三类测试缺一不可：

1. **解析解回归**：能手算的必须手算。例：单峰 pseudo-Voigt 的 FWHM、Scherrer 的 D=Kλ/(βcosθ)。
2. **合成谱回归**：用已知结构造谱 → 反演 → 断言参数误差 < 容差（如 D/ε 误差 < 10%）。
3. **真实谱验收**：真实实验室数据 + 人工确认的真值（13 组样品，`D:\Project\XRD\test_xrd\txt\`）。

**真实谱必须进验收**，因为合成谱会系统性地高估某些判据（§6.3）。

### 4.3 建库任务怎么验收（这是最贵的一类）

建一个库要 12~36 小时，验收必须一次做对。固定四步：

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | `python -m tools.validate_xindb <库>` | 26 项检查（schema / meta 溯源 / chunk 对账 / entry 合理性 / 峰负载抽样 / 元素倒排抽样）0 fail |
| 2 | `python -m tools._compare_xindb_peaks <旧库> <新库>` | 逐 chunk 哈希比对；只改元数据的变更必须全等 |
| 3 | 抽样重建对照 | 取受影响相 + 随机对照，用当前代码重建小库，逐列逐峰比字节 |
| 4 | 回写后 diff | 改动列之外必须归零 |

**第 3 步是决定性的**，前两步只能证明「没变坏」，第 3 步才证明「改成什么样」。

### 4.4 二进制 / 发布验收

**不要手工一轮轮点** —— 仓里有脚本（`tools/verify_binary.py`，对**已发布产物**跑，不碰源码树）：

```bash
python -m tools.verify_binary --setup dist/XinMatch-Setup-<ver>.exe \
    --zip dist/XinMatch-Internal-<ver>.zip --workdir .scratch/binverify \
    --tag v<ver> --report .scratch/binverify.json
```

五轮定义（脚本 docstring 原文）：

| 轮 | 内容 |
|---|---|
| 1 | 两个产物的 SHA-256 + `SHA256SUMS.txt` round-trip |
| 2 | 便携：解压 → 冻结 CLI（`libraries` / `import`）→ 内置库存在 |
| 3 | 冻结 GUI：offscreen selftest 钩子（`XINMATCH_SELFTEST_*` 的 REG / LIBS / ABOUT）+ logo 字节 |
| 4 | 静默安装 Setup 到隔离目录 |
| 5 | 安装后：冻结 CLI + 真实检索（打安装后的内置库） |

`--skip-install` 可跳过第 4/5 轮（无管理员权限时）。offscreen 钩子实现在 `xinmatch/ui/app.py`，渲染完直接退出、不需要交互输入。

手工兜底时要验的最小集（本轮 v3.5.0 实测）：

| 检查 | 期望 |
|---|---|
| `XinMatch.exe --version` | 报 `3.5.0`（三形态一致） |

| **新功能穿透** | 用 `--restraints` 传新参数，行为真的变化（v3.5.0 验的是红色元素排除） |

## 6. 踩过的坑与经验（最重要的一章）

每条格式：**现象 → 根因 → 教训**。这些都是花了小时甚至几十小时换来的。

### 6.1 建库

**① 估时必须用「已完成的最后 20% 区间」外推**

- 现象：COD-Full 按累计均速外推报 21.5 h，实际约 35 h；PCOD-Inorg 外推 4.5 h，实际 12.7 h（衰减 10 倍）。
- 根因：`O(N_hkl × N_atom)` 随晶胞/原子数上升，前期小晶胞相快、后期有机大晶胞慢，均速外推系统性乐观。
- 教训：**看最后 20% 的瞬时速率**，别用平均值。同一条规律踩了两次，没有例外。

**② 建库命令必须带 `-v`**

- 现象：不加 `-v` 时日志只有 5 行表头，数小时的构建完全静默，无法判断死活。
- 根因：进度行走 `logger.info`，CLI 默认 `logging.WARNING`。
- 教训：所有长任务都要保证「有可观测的进度输出」。

**③ 中断一律 `--resume`，不要删库重来**

- 根因/细节：`entries`（2000 相/批）与 `peak_chunks`（4096 相/chunk）是**两条独立提交的流**，残状态有两种（entries 超前 / chunks 超前）。
- 正确做法：原命令加 `--resume`；它会把两条流一起回卷到最后共同 chunk 边界，最多重算一个 chunk（4096 相）。
- **最易犯的错**：归档步进起点取「最后一条已存相 +1」，会静默丢掉被回卷的那批相。必须取 `writer.resume_from_entry_id`（第一个被回卷的相）。
- 等价性已有实验证明（`tools/_verify_resume_equivalence.py`，两种残状态逐表全等）。

**④ id 号段三档不等宽**

- 现象：以为每档 20M，实际 COD `[0,20M)`（偏移 0）、PCOD `[20M,100M)`（+20,000,000）、TCOD `[100M,1e9)`（+100,000,000）。
- 根因：TCOD 的 8 位原生 id 最大到 40,354,736，占掉 4,035 万，第三档必须放宽到 1e9。
- **校验偏移是否生效的正确判据**不是看范围，而是「entry_id 减偏移还原成归档 id → 去源目录找同名 CIF」。

**⑤ `gemmi` 读不到晶胞 → 默认 (1,1,1) → 假峰**

- 现象：`read_small_structure` 对少数 CIF 读不到晶胞时返回默认 `(1,1,1,90,90,90)`，算出 **d=1.0 Å 的单峰**。
- 正解：**晶胞恢复**（用 CIF 文本六参数重建 `gemmi.UnitCell`），不是丢相。实测 `96-156-3735` 从 1 个假峰变 150 个真峰。
- 规模：COD 独有（抽样 2 万/源，COD 0.01% ≈ 54 相，PCOD/TCOD 为 0）。

### 6.2 数据口径（最容易「自己骗自己」的地方）

**① `elem_mask` 是死列，元素筛必须走 `element_inv`**

- 根因：mask 是单个 64 位有符号整数，建库时按 **63 位截断**（`_MAX_STORABLE_MASK`）。W/Pb/Bi/U/Ta/Au/Pt/Gd 等 **27%** 的相落在 bit 63 之外。
- 教训：用 mask 筛会静默漏判，且错得「很像对的」。

**② 写验收判据前，必须先读建库器写这一列的那几行代码**

- 现象：两次误报「差异 1,348 行」，实际是 0。
- 根因一：`element_mask()` 返回 `(lo, hi)` **元组**，直接跟库里的整数比 → 报「100% 不一致」。
- 根因二：建库器按 63 位截断存储，比对时不套同样的截断 → 全错。
- 教训：**看到「某列 100% 或大面积不一致」时，先怀疑自己的比对口径，而不是数据。**

**③ `peak_convention` 是 `norm1000`，不是归一化到 1.0**

- 现象：以为强度归一化到 1.0，三个库全报 FAIL。
- 教训：判据里的每个阈值都应来自 `meta` 或 schema 常量，不能凭记忆假设。

**④ 原地补元数据 vs 整库重建：判据是「这次改动碰不碰物理量」**

| 改动类型 | 处置 |
|---|---|
| 碰峰（peak_compute / 结构因子 / 峰合并） | **只能重建**，无替代方案 |
| 只碰元数据 | 补丁可等价，但要按四步证明（§4.3） |

成本核算：PCOD 106 万相补丁 1 min vs 重建 12.7 h（差 3 个数量级）；TCOD 4.7 万相 17 min —— **代码 delta 越大越模糊，越该直接重建**。

**元原则：不要重建同一个库两次。** 先把已知代码问题挖完、攒成一批，再一次性重建。所以 COD-Full（53.5 万相 / 36 h）优先于重做已验收的 Inorg 库；要重做 Inorg，也该在 Full 那个窗口顺手做（+58 min = Full 的 2.7%）。

> **这条原则已于 2026-11-01/11-02 兑现**：COD-Inorg 与 COD-Full 在同一个窗口内一起重建完成
> （Full 532,038 相 / COD-Full-20261020.xinDB / build_time `2026-11-02T14:09:12`），
> 晶胞恢复 + 180° 边界两类修复同时落库。现状与实测证据见 §8.4 注。

### 6.3 基准与「尺子」

**① 合成谱会系统性高估「依赖强度形」的规则**

- 根因：合成谱用**库内同一批参考强度**反演，所以「参考相对强度 ↔ 实测相对强度」精确成立；真实谱没有这个关系，少线相的最强线本来就是弱峰。
- 后果：任何靠强度形判别的规则（覆盖加权、锚定、形状相似度）在合成谱上显得有效，在真实谱上塌掉。实例：强线锚定 合成序贯 10/13→11/13，真实 5/12→**4/12**。
- **判据：新规则先看它依赖哪条证据；只靠位置 + 线数 + 元素，才可能在两套尺子上同时成立。**

**② 「连续化」被实测证伪**

把二值 `main_hit` 换成加权项的池内召回（800 席 / 67 真相位）：

| 排序键 | 池内召回 |
|---|---|
| legacy（main_hit → whits → hits） | 39/67 |
| **main_hit 门控 → hits**（换位） | **51/67** |
| 去掉门控（只看 hits） | 41/67 |
| 只看 whits | 33/67 |
| `2·main_hit + 命中率` | 50/67 |
| `1·main_hit + 命中率` | 50/67 |
| `2·main_hit + 命中率 + 0.3·whits` | 49/67 |

结论：**门控是载荷，不是缺陷**。它回答的「我的最强线是不是样品的强峰」在多相谱里恰恰是最强的单一判别特征。

**③ 两把尺子结论相反时，不要擅自切默认**

换键在真实谱上更好（T1 10/12→11/12、卡级 19/43→23/43），在合成谱上更差（T1 11/13→8/13、序贯 10/13→5/13）。处置：落成开关 `XinDBReader(prescreen_order="intensity"|"hits")`，**默认不变**，切换属产品裁定。详见 §7.1。

**④ 口径不一致会让自己写错报告**

我先写了「Top-1 7/12→8/12」，那是我自己探针的「首个真值相排第一」口径；基准脚本的口径是「榜首命中任一真值相」（10/12→12/12）。**同一件事两种口径差 4 个样本**。教训：报告里两个都写出来并说明差异，别只写对自己有利的那个。

**⑤ 文件名里的版本号不等于配置**（2026-11-06 踩到）

- 现象：`.scratch/bench_syn_350.json` / `bench_real_350.json` 看着像「3.5.0 基线」，实际是
  2×2 分离实验里「新排序 + div0」的产物（合成 8/13、真实 11/12·23/43）。拿它当基线比对，
  会得出「粗口径被改坏了」的错误结论。
- 教训：**基线要按配置认，不按文件名认**。默认配置的基线是 `ab_*_old_ord_div0.2.json`
  （真实 10/12·12/12·19/43·4/12、合成 11/13·12/13·10/13·19/24）；给 A/B 产物起名时必须带
  配置后缀，改完立刻重命名。

**⑥ 字段非空 ≠ 有证据**（2026-11-06 踩到）

- 现象：矿物名级口径把「`entries.mineral_name` 非空」当作「有名字」，而库里 24 张卡的该字段
  写的是晶系词（`hexagonal` / `cubic`）或占位符。2-1 的榜首 `96-157-7381` 正是
  `mineral_name="hexagonal"` + `formula="O Zn"`，于是这把尺子把**正确命中**判成 miss。
- 教训：判据要落在**归一化后的语义**上（`has_species_name()` 查物种键是否为空），不是落在
  「字符串是否非空」上。这条与 §6.2 ②「先怀疑自己的比对口径」同源。

**⑦ `elements_allowed` 是「必须全含」，不是「允许集合」**（2026-11-06 踩到）

- 现象：想表达「样品只含 Zn/Al/Ca/O/F」，按字面传了 `elements_allowed`，预筛池从 1000 缩到
  **76** 张卡，连真值 ZnO 都 MISS。因为该参数是 exact-required 语义（相必须**同时**含这五个
  元素），库里这样的相只有 76 个。
- 正解：「只允许」是减法，要用补集：`elements_excluded = 全元素表 - 允许集合`
  （走 `element_inv` 倒排，是硬约束）。改对之后同一样本池 386、两个次相进 Top-20。
- 教训：**语义型参数先读 docstring 再传**；`allowed` / `excluded` 这一对不是反义词。

**⑧ 召回缺口先查「信息够不够」，再查「排序对不对」**（2026-11-06）

`3-1` 的次相（Al₂O₃ / CaF₂）追了三轮：放大预筛名额到 8000 → 仍排 581 / 425（差 0.06 fom）；
换残差排序键 → 垃圾卡与真相同为 3/3 命中，判别力不足；**给元素约束 → 第 13 / 11 位**。
全量 12 组：无约束 20/43，元素已知 30/43，无一样品变差。
结论：这类缺口是**信息缺口**，不是排序缺口，别先动权重。详见基准报告 §20。

**⑨ 逐样品 diff 前先打印字段类型**（2026-11-06，§6.3④ 的变体）

裁定 `prescreen_order` 时做逐样品对比，我给 `rows[*]` 的所有字段统一套了一个
「列表就求和、否则 `bool()`」的辅助函数。但 `sequential_hit_phase` 其实是**整数**
（序贯命中相数），`bool(3)` 把它压成 1，整张表看起来像「所有样品 1→1、没有退化」，
差一点据此写出「`hits` 零代价」的结论。实际 `3-2` 是 3→2，正是粗序贯完整
4/12→3/12 的唯一来源。

- 教训：diff 之前先 `print(type(v), repr(v))`；整数计数与布尔列表不能共用一个聚合函数。
- 更一般地：**总量持平不等于逐项持平**。细口径 4/13→4/13 是退化与改善相互抵消的结果，
  只看 totals 会漏掉「有样品从完整变不完整」。

### 6.4 打包与发布

**① PyInstaller 不能直接打到 `dist\`**

- 现象：COLLECT 会**先删**目标目录，`dist\xinmatch-3.5.0` 有 3577 个文件，撞上本机批量删除保护 → exit 1，前两分钟打包白跑。
- 正解：先进 `build\stage\<variant>-<ver>-<hhmmss>`（每次唯一，永不需要「先删」）再 `Copy-Item -Force` 镜像。
- **别改回去**。注释已写在 `tools/build_exe.ps1`。

**② 便携 zip 必须排除 `*.xinDB-shm` / `*.xinDB-wal`**

- 根因：只要跑过一次 GUI/CLI，`data\` 就会长出这两个 SQLite 运行态文件；它们不是库的一部分。
- 打包含 `-x!*.xinDB-shm -x!*.xinDB-wal`；卸载后同样会残留这两件（Inno 卸载清单里没有它们），属正常。

**③ 大附件一次性上传 Release 会崩**

- 现象：`gh release create <tag> --notes-file ... a.exe` 在收尾 PATCH 时崩（`wsarecv: connection forcibly closed`），**gh 会连整个 draft release 一起回滚删除**，8 分钟白传。
- 正解三步：建空 draft → `gh release upload <tag> <asset> --clobber` 逐个传（每个包一层重试循环）→ `gh release edit <tag> --draft=false --latest`。

**④ 私有仓库的 release 下载 URL 对未认证请求恒 404**

- 该端点只认 cookie。**不能用它判定发布成功**。校验下载要走
  `api.github.com/repos/<o>/<r>/releases/assets/<id>` + `Accept: application/octet-stream`，支持 `Range` 与 `curl -C -` 续传，可做回下载 SHA-256 比对。

### 6.5 GUI 与线程

**① 不能在 worker 线程读 QWidget**

- 现象：`_do_search` 跑在工作线程，在 worker 里读 `PeriodicTablePanel.states()` 属于跨线程访问 QWidget，Windows 上会随机崩。
- 正解：`_current_restraints()` 在 `_run_search_match`（GUI 线程）先取好，把**不可变的 `Restraints`** 带进线程。

**② 面板 `states()` 只回报非默认态**

- `OPTIONAL`（黄色）是默认值，不会出现在返回里。写测试时别断言它存在，并加注释说明「黄色本来就不参与过滤」。

**③ 功能「界面有、实际没有」是最隐蔽的缺陷**

- 元素三态从 1.x 到 3.4，`ElementState.EXCLUDE` 在**全仓的引用数为 0**：面板能标红、摘要显示「排除：Bi」，但检索入口从不传 `restraints`。
- 教训：**每个 UI 开关都要有一条「它真的改变了检索结果」的端到端测试**。v3.5.0 补的 `tests/ui/test_element_restraints.py` 就是这个模式。

### 6.7 性能：端到端慢 ≠ 慢在你以为的地方（2026-11-06）

**现象**：v3.5.0 二进制验收记下「`3-1.txt`（207 峰）打 78k 相库 **36 s** 出榜」，本文
§2.3 据此规划了 `schema v3.1`（d 值倒排 + chunk 边界表），目标是压百万相检索。实际分段计时：

| 阶段 | 耗时 | 占比 |
|---|---:|---:|
| 预处理里的 `refine_peak_position` × 208 峰 | **35.2 s** | **93%** |
| `prescreen(1000)` + `fetch_peaks` + `rank_candidates` | 0.46 s | 1.2% |

**根因有两层**：

1. `curve_fit`（trf + 边界）拟合 11 点 4 参数模型时**每个峰都跑满 `maxfev=5000` 仍不收敛**
   并抛 `RuntimeError`；`except ...: return float(two_theta[idx])` 把「未精修」的位置
   **静默**当结果返回。208 个峰里 26 个（12%）中招 —— **慢只是表象，静默降级才是真缺陷**。
2. 换 LM 后顺带发现抛物线法同类问题：近似线性片段 a≈0，顶点 `-b/(2a)` 能给出 **1.6e12°**。
   任何无约束的极值解都必须校验是否落在窗口/物理范围内。

**教训**：

- **端到端计时只说"慢"，分段计时才说"慢在哪"**。这次若按原计划做库索引，会为一个 0.9 s 的
  检索优化 0.47 s，而 35 s 的来源完全没碰到。
- **异常兜底必须可观测**（计数或日志）。`except: return 输入值` 这种写法等于把失败伪装成结果，
  下游基准还会把它当正常数据。
- 优化算法层之前，先量一次「输入规模」：这里 208 峰 × 156 ms 就是个一眼可算的量级异常。

修复后：自动预处理 35.2 s → 0.35 s，CLI `search` 端到端 36 s → 2.3 s（其中 1.3 s 是导入），真实谱基准
10 min → 26 s；合成谱逐项相同，真实谱粗口径卡级 19→20/43（5-2 的 SiO₂ 由 miss 变 hit），
无任何命中变差。全文：`docs/基准报告-物相检索-v3.md` §18。

### 6.8 库检索成本：结构在哪、值不值得优化（2026-11-06 实测）

§6.7 修好峰位拟合后，「`schema v3.1` 索引」失去了 93% 的立论基础，于是把四个库在同一谱
（`3-1.txt`，208 峰 / 40 窗）上量了一遍，用数字决定做不做：

| 库 | 相数 | 预筛(40 窗) | 取峰(1000 相) | FoM 打分 | 进程内合计 | CLI 墙钟 |
|---|---:|---:|---:|---:|---:|---:|
| TCOD-Inorg | 46,846 | 57 ms | 73 ms | 416 ms | 0.92 s | 2.51 s |
| COD-Inorg（默认） | 78,035 | 101 ms | 77 ms | 372 ms | 0.92 s | 2.31 s |
| COD-Full | 532,038 | 560 ms | 352 ms | 382 ms | 1.66 s | 3.65 s |
| PCOD-Inorg | 1,061,953 | 1,358 ms | 896 ms | 480 ms | 3.10 s | 5.68 s |

- **只有预筛和取峰随相数涨**。打分稳定在 0.37~0.48 s（只跟候选数 1000 有关），
  预处理 0.35 s 与库无关。
- **默认库上最大的单项是导入**：`python -m xinmatch --version` 1.32 s（裸解释器 0.12 s、
  +numpy 0.24 s、`scipy.optimize` 0.77 s）；`-X importtime` 显示 scipy 共占 0.73 s。
  端到端 2.31 s = 导入 1.32 + 打分 0.37 + 预处理 0.35 + 预筛 0.10 + 取峰 0.08。
- **取峰有约 800 倍读放大**：1000 个候选落在 196/260 个 chunk 里，读 955 MB 取 1.2 MB（0.09%）。
  这是 chunk=4096 相/块的必然结果。

**结论：`schema v3.1` 不做。** 三项优化全做，1M 库 5.68 → 约 3.8 s，默认库零收益，
代价是 136 MB/百万相附加索引 + 全部已发布库迁移 + schema 双向兼容。两个反直觉的点：
① 「chunk 边界表」**无效** —— 候选散布满 260 个 chunk，边界表省不掉解码；
② 真要做，第一刀是 **chunk 粒度 4096 → 256**（读放大 800× → 50×），而那需要重建库。
**什么时候重新算这笔账**：出现「百万相库 + 频繁检索」的真实场景时，不要在 78k 库上为
`O(相数 × 窗数)` 写索引。全文：`docs/基准报告-物相检索-v3.md` §19。

### 6.9 pyqtgraph 谱图区（2026-11-09，v3.6.2 谱图交互改造）

**① `RectMode` 不看 `mouseEnabled`**

- 想实现"只改横轴/只改纵轴"的框选，直觉是 `vb.setMouseEnabled(y=False)` —— **无效**。
  `ViewBox.mouseDragEvent` 在 `RectMode` 下直接走 `showAxRect`（`ViewBox.py:1332`），
  那个开关只影响平移。
- 正解：子类化 `ViewBox` 覆写 `showAxRect`，把不参与缩放的那一轴换回当前视野；
  且**锁定分支必须 `padding=0`** —— pyqtgraph 默认的 2% 边距会把被锁的轴一起撑开。
- 相关：`setMouseMode(PanMode/RectMode)` 是全局状态，切换工具时记得一并复位。

**② `clipToView=True` 会让 `autoRange()` 只看可见点**

- 曲线带 `clipToView` 时 `ViewBox.autoRange()` 只统计当前窗口内的数据。结果：
  缩放一次之后「适应数据范围/复位」**再也回不到全量视野**（实测设 20–30° 后
  autoRange 原封不动，我还以为是按钮没接上）。
- 正解：复位类动作按**数据包围盒**直接 `setRange`（`PatternView.data_bounds()`），
  不要依赖 autorange。

**③ `AxisItem` 的宽度有两个真相**

- `setWidth(w)` 设的是 `fixedWidth`（布局约束）；`width()` 返回**当前几何宽度**。
  布局还没跑时两者不一致，用它做幂等判断会反复重设（且看起来"设了没用"）。
- 正解：比较 `fixedWidth`；要断言最终效果就 `processEvents()` 之后再读几何。

**④ 两块 pyqtgraph 视图要"像素级对齐"**

- 谱图上方的实验曲线和下方的参考线条分属两个 `PlotWidget`。只要左轴宽度差 1 px，
  同一个 2θ 就会偏一列，用户立刻看出"线对不上峰"。
- 做法：① 把下方视图左轴 `fixedWidth` 同步成上方左轴的**实测像素宽**（`sync_geometry()`，
  在 resize / 数据变化 / 主题切换时都调）；② 其余交给 pyqtgraph 的
  `linkedViewChanged`（`ViewBox.py:1075`）按屏幕几何重叠区补偿。
- 断言方式：`mapViewToScene(QPointF(2θ, 0)).x()` 在两块视图上比，容差 1.5 px。

**⑤ `QComboBox` 隐藏后仍是"模式真相源"**

- 用户要求"控制条隐藏、功能保留"。做法是 `setVisible(False)` 而不是删控件：
  下拉框继续持有 `currentIndex`，轴的点击/右键菜单最终都只是改它，
  于是"谁改模式"只有一个入口，不会出现两套状态漂移。

**⑥ 模型 reset 未必发 `currentRowChanged`**

- `set_candidates()` 换数据后"高亮行"已经失效，但 Qt 不保证补发信号 ——
  依赖它的预览行就会指着不存在的相。在 `set_candidates()` 末尾**显式**发一次空信号。

**⑦ `LabelItem` 延迟回收会带崩无关测试**

- pyqtgraph 0.13.7 的 `TextItem`/`LabelItem` 若在解释器退出时被 gc，`sizeHint()` 里会抛
  `'LabelItem' object has no attribute '_sizeHint'`。新增 widget 的测试**必须**显式
  `setParent(None); deleteLater(); processEvents()`（见 `tests/ui/test_pattern_view.py`
  的 `view` fixture）。

### 6.10 元素过滤器（四态 + 闭环）（2026-11-09，v3.6.3）

元素约束的**语义只有一份**：`core/model/element_symbols.py::element_constraint_sets()`。
预筛、SQL 直查（`query_filter.search_by_elements`）、基准脚本（`bench_iucr._pools`）
三处都调它。要改元素口径，**改这一个函数 + `Restraints.passes_elements()`**，别在多处打补丁。

**① 三条硬约束通路，方向各不相同**

| 通路 | 语义 | 未知元素（库里不存在）怎么办 |
|---|---|---|
| `elements_allowed` | 必须**全部**含有（AND） | 返回全 `False` —— 不可能满足，必须清空 |
| `elements_any` | **至少含一个**（OR） | **跳过** —— 它只是没有发言权，不能清空 |
| `elements_excluded` | 含任一即淘汰 | 跳过 —— 它排除不掉任何相 |

方向搞反的代价：`elements_any` 若照抄 `allowed` 的做法，一个拼错的符号会静默清空结果。

**② 「必有已满足则丢弃含有」必须落在换算点**

PolyXRD 规则④：勾了必有就不再要求至少含一个含有（否则纯金属相永远进不了候选）。
这条要在 `element_constraint_sets()` 里就把 `any_of` 置空 —— 只在
`passes_elements()` 里放行是**不够**的：预筛会把 `elements_allowed` 与
`elements_any` 取交集，端到端仍被 AND 一次。回归用例
`tests/db/test_prescreen_element_any.py::test_must_have_suppresses_the_any_of_filter`。

**③ 闭环不新开通路，用补集**

`S ⊆ 允许池` ⟺ `S ∩ (118 − 池) = ∅`，所以闭环就是往 `elements_excluded` 里
补 `set(ELEMENT_SYMBOLS) - pool`，复用既有 `element_inv` 倒排。**不要**再写一条
「池内」正向通路 —— 两条通路并存必然漂移。

**④ 补集写法与闭环写法等价（只差零元素物相）**

「检出元素标 `MAYBE` + 开闭环」与「其余 113 个标 `EXCLUDE`」换算出**同一个**
`elements_excluded`。唯一差异：闭环形式还要求「至少命中一个允许池元素」，
所以元素集为空的退化物相会被挡；真实库里没有零元素物相，检索上等价
（`test_closed_world_equals_the_complement_restraint` 钉住）。CLI
`--sample-elements` 保留补集写法，因为它不依赖 `closed_world` 标志。

**⑤ 字典模型让「重叠优先级」不可达 —— 别照抄 PolyXRD 的去重**

PolyXRD 的 `elements_match_filter` 用扁平列表（`must_have=[…], has=[…]`），
同一个符号可能出现在两类里，所以有「必有 > 含有 > 可能 > 没有」的去重。
XinMatch 的 `Restraints.elements` 是 `{符号: 状态}`，一个元素只有一个状态
（`set_element` 后写覆盖先写）—— 照抄去重只会留下没有测试覆盖的死分支。

**⑥ QSS 的 min-width 作用于内容矩形，边框宽度逐态不同就得逐态扣减**

按钮 `setFixedSize(cell_w, cell_h)` + QSS `min-width` 时，
`minimumSize() = min_w + 2×border`。三态时代所有边框都是 2 px，
`min_w = cell_w − 4` 恰好成立；四态改成 1/2/3 px 后，同一个 `min_w` 会让
「不限制」的 `minimumSize()` 比 `setFixedSize()` 小 4 px —— 布局一重算就把按钮
压小、符号被裁。必须按**本态宽度**扣减（`min_w = cell_w − 2×border`）。
`_BORDER_PX = 3` 只用于 `cell_w` 的**预留**（按最粗的算），不用于 min-size。

**⑦ 判绿要看进度行字符统计，`lastfailed` 会骗人**

- safe-delete 钩子会在 `[100%]` 之后**截断** pytest 的汇总段：`-q` 的
  `=== FAILURES ===` 与末行统计可能根本不落盘，日志末尾只剩 `[safe-delete]…` JSON
  与 `EXIT=1`。失败只能靠**进度行里的 `F`/`E` 计数**定位，再单文件复跑。
- `.pytest_cache/v/cache/lastfailed` 会残留**旧目录结构**下的条目
  （如 `tests/ui/test_smpf_kalpha2.py`、`tests/ui/test_external_library_mount.py`
  早已不存在），`--lf` 只会选中确实还在的那些 —— 别拿它当失败清单。

### 6.11 默认检索模式与元素约束的交互（2026-11-09，v3.6.3）

用户要求「默认使用 FPFM 法用来进行物相鉴定」，于是新增
`DEFAULT_SEARCH_MODE = SEARCH_MODE_FPFM_FULL`。

- **下拉框选项顺序不动**（「峰列表 FoM」仍第 0 项），默认项由
  `findData(DEFAULT_SEARCH_MODE)` 选中。别把「默认」隐含成「第 0 项」——
  改默认值时按 index 切换的测试会静默漂掉。
- **FPFM 检索链没有 `restraints` 形参**，元素四态 / 闭环到不了预筛。
  默认变 FPFM 之后「设了样品元素却不生效」从边缘情况变成常态，所以工具栏
  「样品元素」按钮在**有约束 + FPFM** 时常显 `｜FPFM 下不生效`；
  切回峰列表 FoM 后缀消失。要用化学先验，必须切回寻峰模式。
- 这条限制是 **FPFM 内核的结构限制，不是界面 bug**，本版没动 FPFM 内核。
  将来若要让它生效，得在 `core/search/fpfm.py` 加 restraints 形参并接上
  `element_constraint_sets()` —— 属于改检索链，必须重跑三把尺子。

#### 8.3.1 v3.6.2 新增的人工验收项

装完打开任一真实谱（例如 `test_xrd/txt/5-1.txt`）后逐条确认：

1. **参考线分区**：候选列表点一行 → 谱图正下方出现一行**橙色虚线**竖线，
   标注「候选 ⟨化学式⟩」；竖线正上方能对上谱图里的峰（不是错开一列）。
2. **勾选切换**：取消分区右上角的「同时显示峰强」→ 同一行的竖线变成等高；
   勾回去恢复高低。
3. **已确认相入区**：双击候选确认一相 → 分区里出现该相的**实线**行，
   颜色与谱图里叠加的参考线条一致；确认第二相 → 再多一行；撤销 → 少一行。
4. **轴点击切换**：左键点横轴 → 变成 d 值刻度；再点回 2θ。右键点纵轴 → 弹出
   「计数 / 平方根 / 对数」菜单，选「对数」后纵轴变 log 刻度。顶部控制条不显示。
5. **快捷图标**：点「横向框选」拖一个角度区间 → 只改横轴、纵轴自动贴合；
   点「原始谱图」→ 回到全量视野（**必须能真的缩回去**，这是本版修掉的坑）；
   点「十字线」拖动鼠标 → 右上角读数与谱图同时显示 2θ / 强度。

#### 8.3.2 v3.6.3 新增的人工验收项（元素四态 + 闭环）

打开右坞「限制条件」页，逐条确认：

1. **循环顺序**：点任一元素按钮 → 变「含有」（浅绿实线加粗）→ 再点「可能」（浅黄点线）
   → 再点「没有」（红虚线加粗）→ 再点「必有」（深绿 **粗** 实线加粗）→ 再点回到
   「不限制」（灰细实线）。tooltip 里能看到完整的五态循环。
2. **四态语义**：标 `Mg` 为「含有」、`Ca` 为「含有」→ 结果里 MgO 与 CaO 都在，
   **两者都没有的相不会出现**；把两者都改成「必有」→ 只剩同时含 Mg 与 Ca 的相
   （如白云石），单个 MgO 消失。
3. **闭环开关**：清空后只标 `Mg`「必有」→ 摘要提示「闭环未开启」、结果里仍有大量
   其它相；勾上「限定在所选元素内」→ 提示变成「允许池 1 个元素，其余 117 个一律
   视为没有」，结果只剩纯 Mg 类相（**这一步很容易误以为程序坏了，提示行是给用户的解释**）。
4. **补轻元素**：点「补轻元素」→ O / C / H / N / S 变成「含有」；先手工把 `O` 标成
   「没有」再点，`O` 必须**保持没有**（只填未标的格子）。
5. **与快速录入一致**：「样品元素」填 `Zn Al Ca O F` 后点「其余元素排除」→ 记下候选数；
   清除后改为手工把这 5 个元素标「可能」+ 勾闭环 → 候选数**必须相同**
   （两条路径等价，见 §6.10 ④）。
6. **默认检索模式**：打开主窗口，工具栏下拉框应显示「FPFM 全谱拟合（不寻峰）」；
   在「样品元素」里填几个元素 → 按钮文字结尾出现「｜FPFM 下不生效」；
   切到「峰列表 FoM（寻峰）」→ 该后缀消失，此时元素限定才真正生效。

## 10. 给接手者的三句话

1. **先跑起来，再读懂，最后才改。** 这个项目的坑大多不在代码里，在「口径」里 —— 数据口径、基准口径、真值口径。
2. **每次改动都要问「这碰不碰物理量」**。碰峰的改动只能重建库；不碰的才谈补丁。
3. **数字必须带口径**。同一件事在两把尺子上能差 4 个样本；报告里不写口径的数字，半年后连自己都解释不了。
