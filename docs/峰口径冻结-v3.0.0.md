# v3 峰口径冻结结论（M1-S1.2 验收）

> 本文记录 v3.0.0 `.xinDB` 重建时**峰计算口径**的最终裁决、证据与验收结果。
> 结论已固化在 `xinmatch/core/db/peak_compute.py` 的 `PEAK_CONVENTION` 常量里。

## 1. 结论

```
wavelength        1.5406 Å (Cu Kα1)
d 范围            [0.7703, 30.0] Å      （= 2θ [2.943°, 180°]）
反射枚举          全部 (h,k,l)，不做 ASU 筛选
合并              按 2θ 分组，容差 1e-5°，等价反射强度**求和**（含多重度）
系统消光          由 |F|² = 0 自然产生，不查消光表
强度              I = |F|² · LP，LP = (1+cos²2θ)/(sin²θ·cosθ)
温度因子          CIF 带 B_iso/U_iso 时施加 exp(-B·s²)，B = 8π²·U_iso
截断              丢弃 I < 0.001% 满量程的线（数值鬼峰）
归一化            最强线 = 1000
条数上限          取**强度**最强的 150 条（DEFAULT_MAX_PEAKS）
存储顺序          d 降序（= 2θ 升序）
```

`PEAK_CONVENTION = "CuKa1-1.5406-d0.7703-30.0-merge-mult-DW-norm1000"`，写入 `.xinDB` 的 `meta` 表。

## 2. 为什么必须合并等价反射

粉末衍射的强度是**反射族的总和**，不是单个 hkl 的强度。萤石 CaF₂（F m -3 m）是判据：

| 口径 | 峰数 | 最强线 | (111) 相对高度 |
|---|---|---|---|
| 本方案（合并多重度） | 17 | (220) d=1.9311 I=1000 | 843.6 |
| ASU 单反射（不含多重度） | 43 | (111) d=3.1535 | — |

真实 CaF₂ 粉末图最强线是 (220) 而非 (111)。用 ASU 口径会让**每一条参考谱的强度排序都错位**，直接摧毁 Hanawalt 预筛（其主峰取强度前 3）。

## 3. 上游 v2 库为何不可复现

`PolyXRD/cod_data/COD_inorganics.sqlite`（71,199 相）是 v2 主库的上游。实测：

- `meta` 表**只有** `atomic_sites_rows / build_time / cell_fix / cif_embedded / cif_missing / cif_source / formula_fix / schema_version` 八项，
  **没有** `wavelength`、`two_theta_range`、`max_peaks`、`intensity_scale`、`peak_engine` 任何一项。参数完全不可追溯。
- 库内部口径自相矛盾：
  - CaF₂（1000043）收至 d=0.7884 Å（2θ=156°），17 峰
  - 透辉石（1000007）收至 d=0.9270 Å（2θ=112°），286 峰
  - 全库每行 dmin 分布：`<0.80` 45.6%、`0.80–0.95` 13.4%、`0.95–1.05` 8.3%、`1.05–1.5` 23.3%、`≥1.5` 9.4%
- 强度与 pymatgen 的偏差随角度放大：CaF₂ 在 d=3.15 只差 3%，到 d=0.79 差 **13 倍**。
- 库里存有大量 I=0 的消光峰（抽样 3057 条中 2580 条含 I=0）。

**结论**：它是多次拼装 + 后期 patch 的产物，没有单一可复现管线。以它为"正确性基准"会把它的缺陷一并继承。

## 4. 权威基准换成 pymatgen

`pymatgen.analysis.diffraction.xrd.XRDCalculator` 是公开、可复现、被广泛引用的实现。实测本引擎与它在**无温度因子、满占据**的 CIF 上逐峰一致（max|ΔI| 中位 0.000）。

`PolyXRD-DataBase/tools/fastxrd.py` 也与之逐位等价，可用作交叉验证；但它依赖 `fastcif` 解析 CIF，而 `fastcif` 会拒掉一部分真实 COD 文件（例如 `_space_group_symop_*` 块写法的 1559793），因此 v3 改用 **gemmi 解析 + 自实现矢量化物理核**，既保鲁棒性又保等价性。

## 5. 验收结果（`tools/validate_peak_engine.py`）

四道闸门 + 一个参照指标（`-n 60 --pmg 10`，57 相，108.2 s，**ALL GATES PASSED**）：

| 闸门 | 含义 | 结果 |
|---|---|---|
| **G1** | 上游所有 I≥1 的峰，在 v3 完整峰表里都能找到对应 d（容差 1e-4 Å） | **100%（57/57）** |
| **G2** | 与 pymatgen 逐峰一致（d ≤1e-4，I ≤1.0） | **100%（9/9）**，max\|ΔI\| 中位 0.000 |
| **G4a** | 截断只丢弱线：保留的 150 条恰为最强 150 条 | **100%（57/57）** |
| **G4b** | 强线保留率（报告指标，非闸门） | I≥30：98.35%；**I≥100：100%（1208/1208）** |
| **G3** | 与上游前 10 强线排序的相关系数（参照，不作硬闸门） | 中位 0.998 |
| 速度 | 单进程满量计算 | 0.5–1.5 相/s（随晶胞大小）；14 workers 实测 864 相/分钟 |

G1=100% 说明**没有丢失上游的任何有效信息**；v3 是上游的超集（多出的部分是 d<1.0 Å 的弱线，上游因不可追溯的截断丢掉了它们）。
G4b 的 I≥100 保留率 100% 说明 `max_peaks=150` 只丢 I∈[30,100) 的次要峰，**最强线一条未丢**。

## 7. 已知取舍

- **max_peaks=150**：COD 相位的完整峰数中位 253、p90 1187、最大 38109。按**强度**截断到 150 后，
  **I≥100 的强线 100% 保留**（1208/1208）、I≥30 保留 98.35%；平均存储 120 峰/相。检索主要靠
  最强的一二十条线，因此这一取舍不影响匹配；若后续基准显示强线不足，可上调到 250（体积约 +45%）。
- **d 下限取 λ/2（2θ=180°）**：物理上完整的可测范围。代价是大晶胞相位会多出大量 d<1.0 Å 的极弱线，但这些线在强度截断后基本不会进入 150 条上限，不影响体积。
- **`entries.elem_mask` 是死列**：单列 SQLite INTEGER 只能存 63 位，而 27% 的 COD 相位含 W/Pb/Bi/U/Ta/Au 等 bit≥63 的元素。元素筛选已改为走 `element_inv` 精确倒排（实测比位图快 1.61 倍且结果正确）。该列仅为兼容保留，**读取方不得使用**。

## 8. 性能实测：两次被证否的优化方向

「建库慢」的直觉指向两个方向，都被实测否掉了。记在这里，避免后来者重复投入。

### 8.1 否证一：hkl 枚举不是瓶颈

`_enumerate_hkl` 对每个 h 平面调一次 `gemmi.UnitCell.calculate_d_array(plane)`，
其中 `plane` 有 `(2kmax+1)(2lmax+1)` 个点。看起来像是「跨语言逐点调用」的
典型低效写法，但实测（`tools/_probe_hkl_speed.py`，12 个最大晶胞相）：

| 实现 | 合计耗时 | 等价性 |
|---|---|---|
| gemmi 逐平面（现用） | **0.016 s** | — |
| numpy 倒易度量张量 `G* = G⁻¹` 一次性向量化 | 0.321 s | 与 gemmi `max\|Δd\| ≤ 3.6e-15` |

numpy 版慢 20 倍。原因是 `n_hkl` 实际只有 1.6 万量级（`dmin=0.7703` 已把球半径压得很小），
gemmi 的 C++ 循环在这个规模上远快于 numpy 的大数组分配与 einsum 开销。
**`_enumerate_hkl` 在 cProfile 中只占 0.3% 总时间，不是优化目标。**
（两者数学等价这一结论仍然有用：`G* = G⁻¹` 可作为独立校验路径。）

### 8.2 否证二：温度因子/占据数去重只值 10–20%

分段计时（`tools/_probe_sf_timing.py`，最大晶胞相 `F16 H3 O6 Sr5 V3`，
132 原子 / 16036 反射，总 856 ms）：

| 分段 | 占比 |
|---|---|
| `D_dw_occ`：`w *= exp(-B·s²)` 与占据数加权 | **45.4%** |
| `E_cos_sin`：相位余弦/正弦 | 23.9% |
| `E_sum`：加权求和 | 23.1% |
| `E_phase`：`hkl @ frac` | 4.0% |
| `C_fofs`：Cromer-Mann f(s) | 1.8% |
| `B_s2` + `A_prepare` | 0.3% |

`D_dw_occ` 最大，而实测 10 个大晶胞相里 **9 个的 B 值与占据数各只有一个唯一值**，
给 132 个原子各算一次 `exp(-B·s²)` 确实是纯浪费。按唯一值去重后
（`tools/_verify_sf_equiv.py`）：

- **数值上 24/24 相 bit-exact**（`max|ΔF²| = 0`，含 33 个唯一 B 值、258 原子的极端相）；
- 但速度只提升 **1.0–1.2x**（132 原子相 359→297 ms，258 原子相 843 ms 不变）。

原因是剩下的大头 `E_cos_sin + E_sum`（约 47%）是
`O(n_hkl × n_atoms)` 的三角函数与加权求和 —— 结构因子
`F = Σ_j f_j·occ_j·exp(2πi h·r_j)` 必须对晶胞内**每一个**原子求相位，
既不能按元素合并、也不能丢弃弱散射原子（会改变 |F|²），这是公式本身的下限。

> 测量陷阱：Windows 上 `time.process_time()` 粒度约 15.6 ms，小相读数会被量化到
> 0/15.6/31.2 ms，必须用大相判断。而建库多进程运行时墙钟（`perf_counter`）完全不可用
> —— 会被别的进程的调度延迟污染，读数呈 0.2x–1.6x 的假抖动。

### 8.3 结论

单相计算已接近物理下限，提升吞吐只能靠堆进程（16 核跑 14 worker 已近线性）。
COD-Full（约 535k 相）全量建库是**一次性成本**，按实测 22 相/s 估算约 **6–7 小时**；
COD-Inorg（71k 相）约 **55 分钟**。产品指标（检索响应、库体积）不受此影响。
