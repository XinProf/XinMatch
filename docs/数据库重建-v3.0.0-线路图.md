> 版本：**2.0.0 → 3.0.0**（升一个大版本）

## 2. `.xinDB` 格式设计（v3 schema，全新设计）

### 2.1 设计原则

> **总则：结构全新设计，但"匹配准确性"是唯一不可妥协的约束。** 速度与体积的优化手段（列存、位图、预筛、分层）都只作用于"如何更快地找到候选、如何更省地存数据"，**绝不触碰"候选如何打分、如何排序"**。

1. **列存打包，不存行表**：峰用定长 float32 BLOB，`np.frombuffer` 零拷贝。
2. **构建期生成 top-K 预筛矩阵**：库内直接存 `(N, 32)` 强峰矩阵，运行时零建索引。
3. **两级检索 + 硬上限**：矩阵预筛 → ≤800 候选 → 解全峰 → 复用现有打分（**口径一行不改**）。
4. **元素位图整数运算**：`elem_mask`（uint64）替代逐相正则/相关子查询。
5. **meta 自描述**：`schema_version` / `peak_convention` / `top_k` / `dtype` / 构建时间戳。
6. **`.xinDB` 单文件**（SQLite 容器，DELETE journal，可 `mode=ro` 只读挂载）。

**准确性第一的三条铁律**（贯穿全文，任何取舍都不得违反）：

| # | 铁律 | 落点 |
|---|---|---|
| A | **打分与排序逻辑零改动** | 复用 `search/` 现有 FoM/Hanawalt/correlate，v3 只换数据来源层 |
| B | **峰数据精度不损失** | 全峰用 float32（d 值误差 <1e-6 Å，远小于容差窗口）；预筛矩阵只做"剪枝"不做"排序"，最终排序必用全峰精确值 |
| C | **预筛候选上限带余量** | `prescreen` 取 ≤800 候选（≥ 现行全表扫描真实 top-N 的 2 倍余量），确保真物相**绝不因剪枝被漏掉**；若某样本 800 仍截断真物相，则上限自动放大并告警 |

### 2.2 schema 草案

```sql
-- 文件：<name>.xinDB
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
--   schema_version=3, peak_convention='CuKa1-1.5406-dmin-1.0-norm-1000',
--   top_k=32, dtype='f32', entry_count, build_time, cif_source

CREATE TABLE entries (                     -- 每相一行
    entry_id    TEXT PRIMARY KEY,          -- "96-100-0005"（COD ref_id 口径）
    formula     TEXT, space_group TEXT, mineral_name TEXT,
    crystal_system TEXT,
    elements    TEXT,                      -- "O,Ti" 逗号串（显示/复核）
    elem_mask   INTEGER,                   -- uint64 元素位图（过滤★）
    a,b,c,alpha,beta,gamma,volume,density REAL,
    n_peaks     INTEGER,
    peak_off    INTEGER, peak_n INTEGER,   -- → peak_chunks（CSR）
    tier        INTEGER                    -- 0=实验测定优先 / 1=预测 / 2=理论
);

CREATE TABLE peak_chunks (                 -- 打包峰数据
    chunk_id    INTEGER PRIMARY KEY,       -- chunk = 4096 相
    top_d       BLOB, top_i   BLOB,        -- (n,32) float32 预筛矩阵★
    all_d       BLOB, all_i   BLOB         -- CSR float32 全峰（仅候选解）
);

CREATE TABLE element_inv (element TEXT, eids BLOB);  -- 可选倒排（uint32 数组）
```

### 2.3 体积测算

| 库 | 相数（来源） | 估算体积 | 对比旧库 |
|---|---|---|---|
| `COD-Inorg.xinDB` | 79,198（`inorg_cif/COD` 子集） | **≈100 MB** | 旧 cod_inorganics 745 MB |
| `COD-Full.xinDB` | 535,166（`COD` 全库，去空/坏后 ~50 万） | **≈660 MB** | 旧 cod_full 987 MB |

> 无机子集 `COD-Inorg.xinDB` 作为**默认交互库**（排序不被同相复本稀释）；`COD-Full.xinDB` 作为**可选全量外挂库**。

### 2.4 外挂形式设计（核心新增）

两个 `.xinDB` 库**不随包分发**，作为外挂库存在任意文件夹：

| 项 | 做法 |
|---|---|
| 库文件位置 | 任意用户文件夹（如 `D:\XRD-DB\COD-Inorg.xinDB`、`E:\data\COD-Full.xinDB`） |
| 挂载机制 | 复用现有 `multi_db.add_external_library(path)` → `<user-data>/libraries.json` 注册 → GUI「添加外部库」 |
| 识别 | `reader_v3.probe()` 读 meta.`schema_version=3` + 扩展名 `.xinDB`，与旧 `.db`/`.sqlite` 完全区分 |
| 打开 | `open_search_database(path)` 对 `.xinDB` 直接 `mode=ro` + mmap，**无需转换 sidecar**（与旧 PolyXRD 侧车不同，v3 是原生格式） |
| 只读保证 | 检索绝不写库；`PRAGMA query_only=ON`；DELETE journal，无 `-wal/-shm` |
| 可移植 | 单文件自包含（meta 记录 CIF 源与口径），拷到别的机器挂载即用 |

## 5. 明确不做 / 风险登记

| 项 | 决定 | 理由 |
|---|---|---|
| PCOD / TCOD | **本阶段不做** | 用户明确"暂时只用 COD"；schema 预留 `tier`/`elem_mask` 已兼容未来扩展 |
| 兼容旧 `.db` / PolyXRD | **不做** | 用户明确不背历史包袱 |
| 改 FoM/Hanawalt 打分权重 | **不做（准确性红线）** | 打分/排序是匹配准确性的核心，改了基准不可比、准确度不可控 |
| 检索路径写库 | **禁止** | 一律 `mode=ro` + mmap |
| 两个库随包分发 | **不随包**，纯外挂 | 用户明确"外挂形式，存任意文件夹"；仅保留挂载能力，库文件由用户自备 |
| CIF 内嵌 | **不内嵌** | 内嵌使库涨 ~1.3 GB；回落外部 CIF 归档 |
| 大库排序稀释 | `COD-Inorg` 作默认交互库 + `tier` 分层 | 复用已验证结论 |

## 6. 准确性护栏（"准确性第一"的可验证落地）

全新设计数据库结构，**唯一不能动的就是匹配结果**。以下四条护栏把"准确性第一"从口号变成可执行的验收门槛：

| # | 护栏 | 机制 | 验收门槛 |
|---|---|---|---|
| 1 | **oracle 双实现比对** | 同数据（同一批 CIF）分别走「旧行表」与「v3 列存」两条链路，逐字段比对 d/I/元素/晶胞 + 最终 top-N 排序 | 峰数据误差 ≤1e-6；**排序 top1/top10 逐项一致**（允许分层去重后更优） |
| 2 | **13 试样基准回归** | `bench_search_v3.py` 用固定 13 个标准试样（石英/方解石/刚玉/金红石/赤铁矿…）跑 v3 库 | top1/top10 命中数与 M0 基线**不劣化** |
| 3 | **预筛召回率下限** | `prescreen` 候选集 vs 全表扫描真实 top-N 的重合度 | **召回 ≥99%**（真物相永不因剪枝漏掉）；不达标则放大候选上限 |
| 4 | **浮点精度审计** | float32 打包 vs float64 源值的 d 值残差 | d 残差 <1e-6 Å（远小于容差窗口 0.01~0.02 Å，不改变命中判定） |

> **红线说明**：护栏 1、2 是硬门槛，**任何一步不通过都不得发版**；护栏 3、4 是性能/精度的安全余量校验，通过才证明"提速缩容"没伤害"准确性"。三者共同保证：新库更快更小，但**匹配结果与旧库逐字段可复现**。
