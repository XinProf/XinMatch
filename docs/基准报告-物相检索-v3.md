## 1. 为什么要换尺子

v3.1.0 文档里的多相验收是在 v2 SQLite 卡片库上做的，而运行期只走 `.xinDB`。
2026-11-04 的定位（`docs/检索基准-v3-诊断-20261104.md`）证明两代库的**强度口径不同**：
同一条目 MgO `96-900-6475` 的 220 线在 v2 卡是 284、在 v3 库是 570（v3 带 LP 修正，
更接近教科书 0.52）。合成谱按 v2 卡生成、检索用 v3 库，强度判据被系统性冤枉。

因此生成器新增 `--peak-source v3 --library <xinDB>`：d/I 直接取自库内同一条目
（hkl 仍从 v2 卡按 d 对齐补，仅供 March-Dollase 织构几何）。13 组谱重新生成到
`D:\Project\XRD\test_xrd\synthetic_v3\`，**旧谱保留不动**。

## 4. 度量本身的缺陷（v3.2.0 已修）

同一相在库里有几十张近重复卡（BaTiO₃ 的 `96-210-0858` / `96-210-0859`、TiO₂ 的
`96-500-0223` / `96-900-8214`…）。此前脚本按 **entry_id** 判命中，把"找对了相但落到
姊妹卡"记成失败，于是 Top-1 从相位级的 10/13 掉到条目级的 7/13。

v3.2.0 新增 `xinmatch/core/search/phase_key.py`：

| 函数 | 作用 |
|---|---|
| `parse_composition` / `normalize_formula` | 化学式归一（元素计数、顺序无关、小数占位度保留） |
| `same_phase(a, b)` | 同相判定：元素集相同 + 晶胞 ±1%（角度 ±1.5°）+ 空间群一致；**缺晶胞时**才退回化学计量比较 |
| `group_same_phase` / `families` | 把已排序候选切成相位族，代表 = 族内排名最高者，顺序保持不变 |

判定用晶胞而非化学计量做主判据，是因为占位度精修变体（`Al1.499 Be2.49…` vs `Al2 Be2…`）
晶胞几乎相同、化学式不同；反过来多晶型（锐钛矿/金红石）化学式相同、晶胞不同。
13 项单元测试见 `tests/search/test_phase_key.py`。

## 10. 预筛名额：根因、修复与实测对照（2026-11-04）

### 10.1 根因

§9 里"只命中主相"的样品不是打分排错，而是**真相相根本没进候选池**：

| 验证（3-1） | 结果 |
|---|---|
| `candidate_limit=800`，真相相在 Top-400 内的名次 | ZnO **1**；Al₂O₃ 无；CaF₂ 无 |
| `candidate_limit=8000` | ZnO 1；Al₂O₃ **197**；CaF₂ **197** |
| 只改预筛输入：不传实测强度（`measured_i=None`），仍 800 名额 | ZnO 5；Al₂O₃ **85**；CaF₂ 无 |

`XinDBReader.prescreen` 的排序是 **主峰命中 → 强度加权命中 → 命中数**
（`main_hit` / `whits` / `hits`）。"我的最强反射是否落在一条**强**实测峰上"在多相
样品里等价于"我是不是主相"——次相的主峰在实测谱里往往是弱线，于是名额被主相及其
同族卡占满。旁证：预筛的 `n_hits` 在 3-1 上是 **75970/78035**（`min_match=2` 只挡掉
2 千个相），**800 个名额在做全部判别**，排序规则因此极其关键。

### 10.2 修复

`prescreen` 新增 `diversify_slots` 参数（默认 `_DIVERSIFY_SHARE = 0.2` × 名额）：
一部分名额仍按老的"主峰优先"顺序发放，保证头部不变；余下名额按**命中数**排序
（去掉 `main_hit` 与强度权重）发放，让"解释了很多强峰但不是主相"的卡进来。
`diversify_slots=0` 精确复现改动前的行为，便于对照。

同时把默认名额 800 → **1000**：800 个位置装不下"主相同族卡 + 次相"两头。

### 10.3 名额分配的扫描结果

同一套基准跑 5 种配置（真实谱 = 卡级/族级相召回，合成谱 = 相位级）：

| 配置 | 合成 T1 | 合成 T5 | 合成序贯 | 合成召回 | 真实 T5 | 真实卡级 | 真实族级 | 真实序贯 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 800 / diverse 0（旧） | 10/13 | 11/13 | 9/13 | 18/24 | 11/12 | 20/43 | 24/43 | 4/12 |
| 800 / diverse 200 | 10/13 | 12/13 | 9/13 | 18/24 | 12/12 | 23/43 | 27/43 | 5/12 |
| 800 / diverse 400 | 9/13 | 12/13 | 8/13 | 17/24 | 12/12 | 23/43 | 27/43 | 5/12 |
| **1000 / diverse 200（采用）** | **11/13** | **12/13** | **10/13** | **19/24** | **12/12** | **24/43** | **27/43** | **5/12** |
| 1000 / diverse 400 | 9/13 | 12/13 | 8/13 | 17/24 | 12/12 | 23/43 | 26/43 | 5/12 |

两条读法：

* **配额太大反而变差**（400 那两行）：把一半名额让给"命中数"会挤掉老顺序里本来正确的
  头部卡片，合成谱直接掉 1–2 个 Top-1。200（20%）是拐点。
* **1000 / 200 全面不劣于旧配置**：合成 +1 Top-1 / +1 序贯 / +1 相召回，真实 +4 卡级 /
  +3 族级 / +1 序贯，Top-1 不变。

代价（COD-Inorg 78k / PCOD 1.06M，`3-1` 208 峰，热缓存，3 次中位数）：

| 配置 | COD-Inorg | PCOD-Inorg |
|---|---:|---:|
| 800 / 0（旧） | 0.37 s | 1.50 s |
| 1000 / 200（采用） | 0.41 s（+11%） | 1.89 s（+26%） |

PCOD 的 +26% 主要来自"分散取候选"要解码更多 chunk（`fetch_peaks` 按 chunk 解码）。
可接受：默认库是 COD-Inorg，且 PCOD 本来就不是交互式检索的首选库。

### 10.4 顺带修掉的边界 bug

`candidate_limit=40000` 时 `search_match_v3` 返回 **0 个候选**（800 / 8000 均正常）。
根因不是预筛，而是 `fetch_peaks` 把整批 id 塞进一条 `entry_id IN (?, …)`——SQLite
宿主参数上限（老版 999 / 新版 32766）一超就 `OperationalError`，被
`except sqlite3.Error` 吞成"空结果"。现按 900 一批分批查询（`_FETCH_ID_BATCH`），
回归 `tests/db/test_reader_v3_fetch.py`（用 10 参数上限的连接代理模拟老库）。

**教训**：`except sqlite3.Error: return {}` 这类宽捕获会把参数/资源类错误伪装成
"查无结果"，比抛异常危险得多。

### 10.5 未做

相位族去重后分配名额（每族先给 1 席，剩余按分数回填）仍是最彻底的一招，但它把
"族代表"塞进候选池，和 FoM 的打分口径耦合；先用 §9 的 `3-1` 这类样本把 FoM 层
问题定性，再动它。

**结论先说**：在自洽的 v3 基准上，**没有任何一种局部重排受控策略能超过基线**

的是 §11.5 的**强线锚定**（10/13 → 11/13），但它在真实谱上丢一组样品，因此同样
**不作为默认行为上线**，只作为候选列表上的标记。

### 11.1 基线与口径（必须用 v3 谱集）

### 11.2 试过的反制（全部 ≤ 基线）

| 变体 | 合成序贯完整 | 备注 |
|---|---:|---|

### 11.3 根因（诊断实测，非推测）

- **synth_01 第 2 轮**：真相 ZnO 在候选池 rank 22、强度覆盖 **0.861**，榜首只覆盖
  0.652，但 `npeaks`（条数）0.474 远高于 ZnO 的 0.316 → 「多线撞弱峰」。covI 能救它，
  但同一改动在 synth_04 把确认顺序从 SiO₂→Fe₂O₃ 翻成 Fe₂O₃→SiO₂，第二轮拿走 SiO₂ 后
  顺序崩掉。
- **synth_07**：真相 NaCl（rank 10，覆盖 0.686，`pos` 0.991）本可被 covI 抬上来，
  但池中还有假相 `Ba1.75Na0.5Se4S` 覆盖 **0.923** 更高 → covI 只是换个假榜首。
- **synth_10**：真 Fe₃O₄ 与 Si 掺杂尖晶石 `Fe2.91O4Si0.09` 的五项判据**几乎逐位相同**
  （覆盖均 0.443、FoM 0.7764 vs 0.7770）→ 打分层无法区分，属本征近平局。
- **synth_07 的 KCl、synth_10 的 Fe（第 1 轮）根本不在候选池**（>pool 60）——它们是
  「少线相」，`npeaks` 天生很低，被 FoM 排序挤出前 N。这是**召回**问题，不是排序问题。

### 11.4 结论与下一步

| 结论 | 含义 |
|---|---|
| 「局部强度加权覆盖」不是密集卡问题的解 | 任何单一覆盖指标都会同时抬高另一类假密集卡，且与相位确认顺序强耦合 |
| 剩余失败 = 召回（少线相 Fe/KCl）+ 本征近平局（尖晶石族）+ 残差扣除劣化少数相强度形 | 三者在打分层之外 |
| 本版不改 FoM 权重与 P 定义 | 硬上会伤合成尺子；3.2.0 的权重口径保持冻结 |

**真正的下一步（本节 §11.5 已落地一半）**：序贯**少线相召回**——对「解释强残差峰
但线数少」的相做定向召回（而非提高覆盖面权重），同时用位置精度与「单强线金属型
假相」区分。**§11.5 记录了这条路的实测结果：机制有效但不足以默认开启。**

### 11.5 强线锚定：机制有效、但只标记不重排（3.3.0 落地）

「少线相召回」用**排序**解决，不改打分：

| 判据 | 阈值 | 为什么 |
|---|---|---|
| 最强参考线所命中的残差峰强度 | ≥ 0.30 × 最强残差峰 | 锚定必须落在真的强峰上 |
| `P(2θ)` | ≥ 0.98 | 位置精度，剔除「宽度对上、位置偏」的假卡 |
| 匹配对数 | ≥ 2 | 单线巧合不算证据 |
| `P(ncorr)`（自身反射解释率） | ≥ 0.50 | 区分「线少但都对」与「大卡碰巧中一条」 |
| 参考反射数 | ≤ 20 | 直接排掉 40~150 线的密集卡，即霸榜机制本身 |

实现：`AnchorPolicy` + `_anchor_ok()` / `_anchor_flags()` / `_promote_anchored()`
（`xinmatch/core/search/sequential.py`），结果写进 `ResidualSearchResult.anchored_ids`。

**两套基准的实测**（2026-11-04，COD-Inorg-20261020，top_n 20）：

| 口径 | 默认（纯 FoM 排序） | 锚定重排（`promote_anchored=True`） | 差 |
|---|---:|---:|---:|
| 合成 `synthetic_v3` 序贯完整 | 10/13 | **11/13** | **+1** |
| 合成 `synthetic_v3` 序贯相召回 | 19/24 | **21/24** | **+2** |
| 真实 12 组序贯完整（3 轮） | **5/12** | 4/12 | −1 |
| 真实 12 组序贯完整（5 轮） | **6/12** | 5/12 | −1 |
| 真实 12 组序贯内相召回（3 轮，43 相） | **23/43** | 22/43 | −1 |
| 真实整谱 Top-1 / Top-5 | 10/12 · 12/12 | 10/12 · 12/12（整谱路径不经过锚定） | 0 |

合成收益是真的：`synth_07` 的 NaCl（17 线、rank 10、`pos` 0.991、最强线命中 1.00×
最强残差峰）被抬到首位后整相回收，`0/2 → 2/2`。但真实谱的反例同样硬：

- **`3-2`（ZnO + Al₂O₃ + CaF₂）第 2 轮**：榜首 6 张全是真 Al₂O₃（FoM 0.753），锚定把
  第 7 名 `Bi1.284O2.988Y0.684`（FoM 0.667、`pos` **0.984**、`ncorr` 0.588、17 线）
  抬到首位。它的位置精度比真 CaF₂ 的 0.928 **还高**，于是被确认 → 残差被污染 →
  CaF₂ **5 轮也找不回来**（不是「多花一轮」）。
- 线数护栏救不了它（17 ≤ 20），两线锚定（Hanawalt 式：最强两条参考线都命中、
  强度比在 2.5× 内）也救不了：单线/双线/双线+比值三种变体的八项指标**完全相同**。

**根因**：合成谱用同一批参考强度重建，所以「参考相对强度 ↔ 实测相对强度」关系
精确成立；真实谱没有这个关系，`P(I/I₀)` 对少线相天然接近 0，锚定只能靠位置与
线数，判别力不够。**合成尺子在这条规则上系统性高估。**

**决定（用户裁定 2026-11-04）**：默认 `promote_anchored=False` —— 引擎排序与 3.2.0
逐项相同（真实谱 Top-1 10/12 · Top-5 12/12 · 序贯 5/12 · 整谱卡召回 24/43 · 族级 27/43），
锚定只作为**标记**出现在候选列表：第一列色带显示 `★`、tooltip 解释、状态栏报
「★ N 条最强线命中强残差峰（少线相，排名靠后也值得核对）」。用户自己决定看不看，
引擎不替他决定。开关留在 `search_residual(promote_anchored=True)`，供离线实验。

**下一步（尚未做）**：把 Bi-Y-O 这类假卡挡掉需要**样品侧元素合理性**（XRF/EDS 或
「仅含检出元素」约束），这是打分层之外的输入，属独立任务。

## 13. 3.4.1 `same_phase` 修复：空白式卡不再「万能匹配」（2026-11-05）

### 13.1 缺陷

`phase_key._composition_agrees` 曾在「任一侧组成不可解析」时返回 `True`，注释原文是
`no evidence, not a mismatch`。该函数**只在至少一侧缺晶胞**时被调用——此时组成是唯一证据。
返回 `True` 等于承认「不知道 ⇒ 同相」，后果两条：

1. **真值匹配虚高**：一张空白卡可以同时命中**所有**真值相，于是「一张卡 = 全对」；
2. **折叠错族**：空白卡能并进任意相位族，甚至当上族代表，把真族的代表位置顶掉。

库内规模：COD-Inorg **416 / 78,035（0.53%）** `formula` 为空。它们**全部带晶胞、全部有峰**
（20~150 条），是**真实结构**，只是 CIF 缺 `_chemical_formula_sum`——
`cif_meta.elements_from_sites` 是最后兜底，所以 `entries.elements` 有值而 `entries.formula` 为空。
其中 28 条还带矿物名。

### 13.2 修复

`_composition_agrees` 改为**两侧都非空才可能为真**（正向证据才允许判同）。晶胞路径不受影响：
两侧都带晶胞且吻合时，空白卡仍判同相——晶胞本身就是正向证据。

`tests/search/test_phase_key.py` 新增 4 组用例（空式 vs 已知相双向 `False`；两侧皆空 `False`；
空式但晶胞吻合仍 `True`；折叠时空白卡独立成族）。全量 pytest 全绿（0 失败，15m18s）。

### 13.3 影响：合成零变化，真实谱显著下降

| 基准 | 指标 | 修复前 | 修复后 | 变化 |

### 13.6 新口径 = 可核验下界（P1 补式已执行，实测未兑现）

## 14. §10.5 相位族预筛配额：实现、实测与否决（2026-11-05）

### 14.1 提案与实现

§10.5 曾建议「每族先给 1 席，剩余按分数回填」。实现为 `XinDBReader.family_slots`（默认
`None` = 不设限）：族不用元数据，而用**三强线指纹**——把卡片 `top_d` 的前三列按 d 窗宽量化成
一个 `int64` 键（`_family_keys`）。理由：预筛本来就持有 `top_d` 矩阵，不必回表；同相异卡的三强线
几乎相同会被并到一起，而多晶型的三强线相差远大于窗宽，自然分开。

分配逻辑：按 legacy 顺序走，同一族最多取 `family_slots` 张；名额没填满就加大扫描前缀，
**名额总数不变，只改「哪些卡拿到名额」**。默认关闭，`reader.family_slots` 打开；
基准脚本带 `--family-slots`。

### 14.2 先测上界：池内召回

后续所有指标都 ≤ 池内召回，所以先只测它（1000 席，25 个样品，67 个真值相，
`.scratch/_probe_quota_pool_recall.py`）：

| 每族上限 | off | ≤16 | ≤8 | ≤4 | ≤2 | ≤1 |
|---|---:|---:|---:|---:|---:|---:|
| 池内召回 | 45/67 | 45/67 | 45/67 | 44/67 | 45/67 | **48/67** |

上限 1 时有得有失：`synth_07`/`synth_11`/`5-2b`/`7-1`/`7-2` 各 +1，`synth_04`/`synth_10` 各 −1。
**`3-1` 完全不动**（仍是 1/3）：Al₂O₃ 首个同相卡在池内第 **2071** 位、CaF₂ 在第 **4262** 位。

### 14.3 为什么它救不了 `3-1`：霸榜是弥散的，不是单族洪水

| 事实（3-1，8000 池 / 前 1000 位） | 数值 |
|---|---|
| 三强线指纹族数 | 8000 池 4,772 个；**前 1000 位内 522–569 个** |
| 最大族 | 8000 池 81 张；**前 1000 位内 44–67 张** |
| 真相同相卡首个位置（1000/2000/4000/8000 席） | ZnO=4；Al₂O₃=—/—/2071/2071；CaF₂=—/—/—/4262 |

前 1000 席已被 ~550 个族分摊，把每族压到 1 席最多释放 ~450 个位置，够不到 2071。
`synth_12` 更极端：真值同相卡在 2889 位，而它最大的族也只有 172 张（占 17%）——**配额的上限
（约 20% 的名额）与缺口（2~4 倍名额）差一个量级**。

### 14.4 端到端实测：明显劣化，否决

| 配置 | 合成 T1 | 合成 T5 | 合成序贯 | 合成召回 | 真实 T1 | 真实 T5 | 真实卡级 | 真实族级 | 真实序贯 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 不设限（现默认） | **11/13** | **12/13** | **10/13** | **19/24** | **10/12** | 12/12 | **19/43** | 19/43 | 4/12 |
| 每族 ≤1 | 6/13 | 9/13 | 7/13 | 15/24 | 9/12 | 12/12 | 19/43 | 18/43 | 4/12 |
| 每族 ≤2 | 6/13 | 10/13 | 7/13 | 16/24 | 10/12 | 11/12 | 18/43 | 18/43 | 4/12 |

**根因**：族内保留的是**legacy 顺序第一张**，不是 FoM 分最高的那张；而族定义只看三强线，
化学上不同的相也可能同指纹——于是「砍掉的多是真正高分的那张卡，留下的是恰好主峰落进窗内的
近邻卡」。合成谱上代价最大（T1 −5），因为那里真值就是库内某一张具体卡。

### 14.5 结论

## 16. P1 两项收尾：元素「必须不含」约束落地、预筛排序两边不讨好（2026-11-06）

计划表里剩下的两条 P1：「预筛排序函数连续化」与「少线相召回收尾 + 样品侧元素合理性
挡假卡」。一条落地，一条量到结论但**不该单方面改默认**。

### 16.1 元素「必须不含」：从死代码变成可用约束

三态元素约束里 `ElementState.EXCLUDE`（红色）从 1.x 到 3.4 **全仓零引用**：周期表
面板能标红、摘要能显示「排除：Bi」，但 `main_window._do_search` 调 `search_match`
时根本不传 `restraints`，预筛更没有这条通路。于是「样品里没有 Bi」（XRF/EDS 已确认）
这条化学上最硬的先验进不了召回，§11.5 的 `3-2` `Bi-Y-O` 假卡只能靠肉眼剔。

落地的链路（四段，缺一段就等于没做）：

| 层 | 改动 | 语义 |
|---|---|---|
| 预筛 | `XinDBReader.element_exclude_filter()` | 「**不含任何一个**给定元素」，走 `element_inv` 倒排，与 63 位 `elem_mask` 无关（W/Pb/Bi 等 27 % 的相在 mask 之外） |
| 预筛 | `prescreen(elements_excluded=...)` | 与 `elements_allowed` 取交集；候选归零时照常返回空结果，不抛异常 |
| 检索 | `search_match_v3(elements_excluded=...)` | 转发到预筛 |
| 兼容层 | `search_match(restraints=...)` 的 `EXCLUDE → elements_excluded` | 此前这半边被静默丢弃 |
| GUI | `MainWindow._current_restraints()` + `_do_search(restraints=)` | 面板状态在 **GUI 线程**读出（面板是 QWidget，worker 里碰会跨线程崩），再带进工作线程 |

一处刻意与「必须含」相反的设计：**未知元素在排除方向上什么都不排除**（返回全 `True`）。
拼错一个符号不该把结果清空 —— 「不可能含有」不等于「不可能满足」。

**真实样品量化**（`tools/bench_real_samples` 的 13 组真实谱，理想化设定：把真值相的
元素并集当作一份完美 XRF 报告，其余元素全部标红；`top_n=60`）：

| 指标 | 无约束 | 有约束 |
|---|---:|---:|
| Top-1 命中（任一真值相，与基准脚本同口径） | 10/12 | **12/12** |
| Top-1 命中（首个真值相恰好排第一，更严） | 7/12 | 8/12 |
| 真值相位次变化 | — | 上升 21 / 持平 17 / 下降 4 / 被挤出榜单 1 |

两个 Top-1 口径都必须列出来：基准脚本数的是「榜首卡命中任一真值相」（宽），
逐相名次口径更严（要求第一个真值相就排第一）。只报后者会低估约束的收益，
只报前者会掩盖「榜首其实常是多相里的另一相」这一事实。

单个样品的典型变化：`5-1` 的 SiO₂ 从「不在前 60」→ **第 1**；`3-1` 的 Al₂O₃/CaF₂ 从
「不在前 60」→ 第 14/11；`4-1` 的 CaF₂ → 第 3。

**必须记下来的非单调性**：过滤会腾出名额，于是**新放进来**的卡可能把某张真值卡挤出
固定宽度的 Top-N —— `5-2` 的 Muscovite 就从 46 掉出前 60。所以「加了化学约束，名次只会
上升」是错的；它对总量有利（21 升 / 4 降），但不是逐项单调。

### 16.2 预筛排序：§14.5 建议的「强度加权覆盖率」实测更差

§14.5 的结论是「下一步应改打分，例如按命中峰的强度加权覆盖率这类连续量排序」。
先把「池内召回」这个上界量出来（25 个样品 / 67 个真相位 / 800 席，
`.scratch/_probe_prescreen_order_recall.py`）：

| 排序 | 池内召回 |
|---|---:|
| `main_hit → whits → hits`（3.4.x 默认） | 39/67 |
| **`main_hit → hits → whits`** | **51/67** |
| `hits → whits`（去掉主峰门控） | 41/67 |
| `whits → hits` | 33/67 |
| `2·main_hit + 命中率`（连续化） | 50/67 |
| `1·main_hit + 命中率` | 50/67 |
| `2·main_hit + 命中率 + 0.3·whits` | 49/67 |

两条结论：

1. **「连续化」不成立**：把二值门控换成任何加权项都掉 1~2 个真值相，去掉门控掉 10 个。
   门控是载荷，不是缺陷 —— 它回答的「我的最强线是不是样品的强峰」在多相谱里恰恰是
   最强的单一判别特征。
2. **真正该动的是第二键**：`whits` 与 `hits` 交换，同预算多召回 12 个真值相。原因是
   少线相的最强线本身就是**实测弱峰**，`whits`（乘了参考侧最强线强度）必然把它压到
   主相每一张近邻卡之后。

### 16.3 但两把尺子结论相反：默认值不能单方面改

端到端 2×2（`tools/bench_*`，同一库同一样品清单；改动只有两处：排序后两键、diversify
默认份额）：

| 口径 | 合成 T1 | 合成 T5 | 合成序贯 | 合成相召回 | 真实 T1 | 真实 T5 | 真实卡级 | 真实族级 | 真实序贯 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 旧排序 + div0.2（3.4.x 默认） | **11/13** | **12/13** | **10/13** | **19/24** | 10/12 | 12/12 | 19/43 | 19/43 | 4/12 |
| 旧排序 + div0 | 9/13 | 12/13 | 9/13 | 18/24 | 10/12 | 11/12 | 18/43 | 19/43 | 4/12 |
| 新排序 + div0.2 | 8/13 | 10/13 | 4/13 | 13/24 | 11/12 | 12/12 | 23/43 | 23/43 | 4/12 |
| 新排序 + div0 | 8/13 | 10/13 | 5/13 | 14/24 | **11/12** | **12/12** | **23/43** | **25/43** | 4/12 |

* 新排序在**真实谱**上全面更好：Top-1 +1、卡级相召回 19/43 → 23/43（+21 %）、族级 → 25/43。
* 新排序在**合成谱**上明显更差：Top-1 −3、序贯 10/13 → 5/13。
* `diversify` 配额只对旧排序有意义：旧排序下关掉它会同时损失合成 T1 与真实卡级召回
  （说明它补的正是「强度形把次相挤出去」那个洞）；新排序下这个洞不存在，配额反而
  挤掉主峰命中的卡（51/67 → 47/67 池内召回）。

**根因不是巧合，而是尺子本身**：合成谱 `synthetic_v3` 是用**库内同一批参考强度**反演
的，所以「参考相对强度 ↔ 实测相对强度」精确成立，任何强度形判据都会显得有效；真实谱
没有这个关系（§13 记录过同一现象的另一种表现）。换句话说，合成尺子**系统性高估**
依赖强度形的规则 —— 这也是 3.5.0 里新排序在合成谱上掉分的直接原因。

## 17. 真实谱真值口径加「矿物名级」补充列（2026-11-06）

### 17.1 为什么需要第二把尺子

组成级口径（本报告 §2 起沿用，`tools/bench_real_samples.TRUTH`）把真值表示成**组成比**，
因为它必须能和一个矿物名对上。这个做法有三个结构性盲区 —— 都是**尺子**的问题，不是引擎的问题：

| 盲区 | 粗口径的后果 | 本批样品里的实例 |
|---|---|---|
| 同组成的多晶型被合并 | 两个晶型算一个真值相，分不出「找到了哪一个」 | 石英/方石英（5-1、5-2、5-2b）、锐钛矿/金红石（2-2） |

| 掺杂卡组成不完全相等 | 语义正确的卡被判 miss | 5-3 榜首 `96-901-0407` = `Co0.03Fe0.97HO2`，矿物名 Goethite |

### 17.2 判定规则

新增 `xinmatch/core/search/mineral_name.py`。核心是先把库里的拼写归一到**物种键**，
再比较键是否相等 —— **不做子串匹配**，因为 `Nitrocalcite` 含 `calcite`、`Anatase` 与
`Rutile` 组成相同，子串/组成都会把它们混为一谈。

| 库内写法 | 物种键 | 被丢弃的是什么 |
|---|---|---|
| `Quartz low` / `Quartz high` | `quartz` | 多晶型限定词 |
| `Muscovite-2M1` / `Muscovite 2M1` / `Kaolinite 2M` | `muscovite` / `kaolinite` | 多型后缀（`\d+[a-z]\d*`） |
| `Brucite (deuterated)`、`deuterated brucite at 90 K` | `brucite` | 括号注记、温度子句、前置限定词 |
| `Hematite-proto` | `hematite` | 结构前缀 |
| `Nitrocalcite` / `Magnesium calcite` / `Strontiofluorite` | 保持原样 | **不是** calcite / fluorite |
| `Anatase` / `Rutile` / `Cristobalite` | 保持原样 | 不同物种，永不互认 |
| `hexagonal` / `cubic` / `unknown` | `""`（视为无名） | 晶系词不是物种 |

判定顺序（优先级就是语义，改动前请先读这一段）：

1. **固溶体家族**：真值声明 `family_required` / `family_optional` 时，判
   `必含元素 ⊆ 卡元素 ⊆ 必含 ∪ 允许掺杂`。NCM811 用 必含 `{Li,Ni,O}`、允许 `{Co,Mn}` ——
   库内没有 811 等比例卡，榜首 `96-152-0787` 是 `Li1.01Mn0.1Ni0.89O2`（缺 Co）。
2. **卡有物种名**：按名字判定，**不再看组成**。一张写着 `Rutile` 的卡不能算 `Anatase` 命中。
3. **卡无物种名**（含 `hexagonal` 这类占位名）：回落到组成比（`same_phase`），
   但若同一组里另一真值与之**组成相同**（`split=True`），则不计入任一侧 ——
   组成对多晶型没有分辨力，硬算就是编造。
4. **真值只有名、没有组成**（Biotite / Hornblende）：无名卡一律不算。

## 18. 峰位精修换优化器：36 s → 2.3 s（2026-11-06）

### 18.1 现象与归因

用户可感的「一次检索 36 s」（v3.5.0 二进制验收里 `3-1.txt` 打 78k 相库）被当成库检索慢。
逐段计时后完全不是：

| 阶段 | 耗时 | 占比 |
|---|---:|---:|
| `load_pattern` + `smooth` + `snip` 背景 + `strip_alpha2` + `find_peaks` | < 60 ms | 0.2% |
| **`refine_peak_position` × 208 峰** | **35.2 s** | **93%** |
| `reader._matrix()` + `entry_ids()` | 62 ms | 0.2% |
| `prescreen(1000)` | 79 ms | 0.2% |
| `fetch_peaks` | 72 ms | 0.2% |
| `rank_candidates`（1000 候选） | 311 ms | 0.8% |

即：**慢在预处理里的逐峰高斯拟合**，不在 `.xinDB`。

### 18.2 根因：`curve_fit` 每个峰都跑满 `maxfev=5000`

`refine_peak_position(method="gaussian")` 用 `scipy.optimize.curve_fit`（默认 `trf` + 边界）
拟合 11 点、4 参数的高斯+常数背底。实测**每一个峰都触发
`RuntimeError: Optimal parameters not found: The maximum number of function evaluations is exceeded`**，
156 ms/峰。更严重的是失败分支：

```python
except (RuntimeError, ValueError):
    return float(two_theta[idx])   # 静默返回「未精修」的位置
```

208 个峰里有 **26 个（12%）** 走的就是这条分支 —— 它们在后续检索里用的是网格点位置，
而调用方完全看不出来。这不是慢的问题，是**静默的质量缺陷**。

### 18.3 修法：同一模型、同一初值、换 LM + 解析雅可比

- 模型、初值、窗口、最小二乘目标全部不变，只把优化器换成
  `least_squares(method="lm")` 并给出解析雅可比（σ = FWHM/2√(2ln2) 链式求导）。
- 模型求值次数从 5000 降到中位 **15**，1.3~1.5 ms/峰。
- LM 无界，因此加窗口/物理护栏：`fwhm > 0`、`amplitude ≥ 0`、`x[0] ≤ center ≤ x[-1]`；
  不合格则退到抛物线，抛物线也不合格才退回网格点。
- **顺带修掉抛物线的同类 bug**：近似线性的片段使二次项 a≈0，顶点解 `-b/(2a)` 可达
  **1.6e12°**（构造用例可复现）。现在抛物线结果也必须落在窗口内，否则退回网格点。

### 18.4 位置一致性：差异峰都是「原先没精修」的那些

| 比较 | 结果 |
|---|---|
| LM 与旧 curve_fit（208 峰） | 中位差 **5.6e-08°**；> 1e-4° 的 26 个、> 0.05° 的 3 个 |
| 差异最大的 3 个峰 | 旧值恰好等于 `x[idx]`（未精修），新值与独立的抛物线法相差 < 0.006° |
| 结论 | 两种优化器在同一最优点收敛；差异全部来自旧实现的失败兜底 |

### 18.5 端到端与检索质量

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 自动预处理（208 峰） | 35.2 s | **0.35 s** |
| 真实谱基准 13 组（含序贯 3 轮） | 10 min 03 s | **26 s** |
| CLI `search` 端到端（subprocess 墙钟，3-1 / COD-Inorg） | 约 36 s | **2.31 s** |
| 合成谱基准（相位级） | 11/13·12/13·10/13·19/24 | **逐项相同** |
| 真实谱粗口径 | 10/12·12/12·19/43·19/43·4/12 | 10/12·12/12·**20**/43·**20**/43·4/12 |
| 真实谱细口径 | 12/13·13/13·21/50·20/50·4/13 | **逐项相同** |

唯一一处命中判定变化是 5-2 的 SiO₂ 由 miss 变 hit（粗口径卡级/族级各 +1），
没有任何命中变差。逐行逐字段比对：13 行 × 22 列中 28 处差异，全部集中在

**① 库规模只推高两段，而且都是结构性的。**
相数 46k → 1.06M（23 倍）时，预筛 57 → 1,358 ms、取峰 73 → 896 ms（约 12~23 倍），
其余基本不动：打分 372 → 480 ms（1.3 倍），因为它只跟**候选数**（1000）有关，
与库里有几百万相无关；预处理 0.35 s 也与库无关。
成本模型：

```
预筛 ≈ O(相数 × top_k × 窗数)        # 每窗一次全矩阵布尔运算（1.06M×32 = 136 MB）
取峰 ≈ O(触及的 chunk 字节数)         # 与命中多少相无关，与"散落在多少个 chunk"有关
```

**② 默认库上，瓶颈已经不是检索算法，是导入。**
COD-Inorg（默认库）2.31 s 的构成：导入启动 1.32 s（57%）+ 打分 0.37 s（16%）+
预筛 0.10 s + 取峰 0.08 s + 预处理 0.35 s。想再快，能动的只有导入和打分，
不是索引。

**③ 取峰有约 800 倍读放大。**
1000 个候选散落在 **196/260** 个 chunk 里，实际读出约 955 MB，只为取
1000 × 147 峰 × 8 B ≈ **1.2 MB**（0.09%）。这是「chunk = 4096 相」的必然结果，
不是实现缺陷 —— 任何按 chunk 分块的储存在随机取 1000 相时都会这样。

### 19.4 结论：`schema v3.1` 不做

| 方案 | 1M 库收益 | 默认库收益 | 成本 |
|---|---:|---:|---|
| d 值倒排（预筛 1.36 s → ~0.3 s） | -1.0 s | 0 | 百万相约 136 MB 附加索引；全部已发布库要迁移；schema 版本升级需双向兼容 |
| chunk 边界表 | ~0（候选散布满 260 个 chunk，边界表省不掉解码） | 0 | 无 |
| 改 chunk 粒度 4096 → 256 | 取峰 -0.8 s（读放大 800× → 50×） | 0 | 必须**重建库**（PCOD 12.7 h），且与 chunk 边界表互补而非替代 |

三项全做，1M 库 5.68 s → 约 3.8 s，**默认库一分不省**。
判断：不值得。真要动手，第一刀是 chunk 粒度（重建窗口顺手做），不是 d 倒排 ——
这与 §2.3 当初的设想相反，原因是当时把 36 s 整体误记成了库的账。

> **这条要把 `prescreen` 的 O(相数 × 窗数) 记住，但不要在 78k 库上为它写索引。**
> 只有当某天出现「百万相库 + 频繁检索」的真实场景，才重新算这笔账。

## 20. `3-1` 类次相召回：三个假说、一个答案（2026-11-06）

### 20.1 问题

转交记录 §7.2 把「`3-1` 类次相召回收尾」挂在 P1 上，原判断是「根因是预筛名额，
不是 FoM；方向是按样本复杂度自适应名额」。这句话来自 §10.5 的观察：

> `3-1` 次相完全不动：Al₂O₃ 首个同相卡在池内第 2071 位、CaF₂ 第 4262 位。

「池内第 2071 位」读起来像「再多给点名额就进来了」。这一节把这个假说连同两个替代假说
一起量了一遍，结论是**三个都不成立，第四种做法成立**。

### 20.2 假说一：放大预筛名额（否）

`3-1`（208 峰 → 40 预筛窗），`search_match_v3(candidate_limit=…)`，逐档看次相的真实排名
（真值＝ZnO / Al₂O₃ / CaF₂）：

| 候选上限 | 打分耗时 | ZnO | Al₂O₃ | CaF₂ |
|---:|---:|---:|---:|---:|
| 1,000（默认） | 0.82 s | **1** | MISS | MISS |
| 2,000 | 1.28 s | 1 | 1,342 | MISS |
| 4,000 | 2.30 s | 1 | 312 | MISS |
| 8,000 | **4.61 s** | 1 | **581**（fom 0.585） | **425**（fom 0.593） |

第 20 名的 fom 是 **0.653**，两个次相差 **−0.06 ~ −0.07**。也就是说把它们放进池子只是
让它们从「没被算过」变成「算过但排在 400~600 位」—— 仍然离 Top-20 很远，而代价是
端到端 5.6 倍。**「名额」不是瓶颈，排序（打分口径）才是。**

### 20.3 假说二：换残差阶段的排序键（否）

`3-1` 序贯第 1 轮确认 ZnO 后，残差只剩 **11 个峰**。逐条查这 11 个峰：

- **位置是准的**：Al₂O₃ 五条最强线中的 4 条（57.49 / 43.35 / 35.14 / 68.21°）在残差里
  分别对应 57.48 / 43.33 / 35.12 / 68.21°，CaF₂ 的两条（47.12 / 28.34°）对应
  46.98 / 28.24°。**相肯定在样品里。**
- **不是噪声**：按局部一阶差分估 σ，这些峰是 **5.3 ~ 31.8 σ** 的实峰。
- **但强度形不可用**：它们的实测强度全都挤在 187~236（≈最大峰的 1.1%），
  而 Al₂O₃ 卡片说 100 / 88.6 / 74.9 / 70.7 / 56.1。形状被压平了，`P_intensity` 因而
  对 Al₂O₃ 不利。

于是试了两种替代排序键，都不成立：

| 排序键 | Al₂O₃ | CaF₂ | 问题 |
|---|---:|---:|---|
| FoM（现状） | 389 | 214 | 出不了 Top-20 |
| 解释残差峰数（降序） | 1,922 | 4,717 | **密集卡刷满**：解释 10/11 个峰的前 5 张卡全是垃圾（`Al3 Ca2 H3 O8` 等），真相只解释 4 个和 2 个 |
| 三强线命中数（降序，容差 0.15°） | **1** | 74 | 见下 |

「三强线命中」看起来最优：Al₂O₃ 命中 3/3 直接到第 1 位。**但它不可靠**：
容差放到 0.3°（引擎默认相关窗）后，`As Ca Cu H O5` 同样 3/3 且 fom 0.692 > Al₂O₃ 的 0.684，
照样压住真相；更糟的是第 1 轮残差有 33 个峰时，该规则把真 ZnO（fom 0.909）换成
`Fe4.93 H O8`（fom 0.673），单样品召回从 2/3 掉到 1/3。**11 个峰里的「三条线同时命中」
不构成证据 —— 8000 张卡里有 52 张能做到。** 该实现已回退，不进入代码。

### 20.4 答案：把化学信息给它（是）

同一张 `3-1`，加一条「必须不含」约束（除 Zn/Al/Ca/O/F 之外的元素一律排除，即
XRF/EDS 已给出的样品元素）：

| 设置 | 候选池 | ZnO | CaF₂ | Al₂O₃ |
|---|---:|---:|---:|---:|
| 无约束 | 1,000 | 1 | MISS | MISS |
| 元素补集约束 | **386** | 1 | **11** | **13** |

两个次相直接进 Top-20，检索还快了 3 倍（池子小了）。全量 12 组真实谱的上界口径：

| 口径 | Top-1 | 相召回（卡级 Top-20） | 相召回（族级） | 序贯完整 |
|---|---:|---:|---:|---:|
| 无约束（现状默认） | 10/12 | **20/43** | 21/43 | 4/12 |
| 元素已知（上界） | **12/12** | **30/43** | **33/43** | 5/12 |

> 族级两列已按 §29 的新口径（族内任一成员命中）重跑：无约束 20/43 → **21/43**，
> 上界仍是 33/43（7-1 的 Boehmite 在这一口径下本来就已通过代表卡命中）。

逐样品（卡级、粗口径分母）：

| 样品 | 真值相 | 无约束 | 元素上界 | 变化 |
|---|---:|---:|---:|---|

| 2-2 | 1 | 1/1 | 1/1 | 0 |

| 5-2 | 4 | 3/4 | 3/4 | 0 |
| 5-2b | 4 | 3/4 | 3/4 | 0 |

| 7-1 | 7 | 2/7 | 3/7 | +1 |

**没有一样品变差**，净增 10 相。原因不神秘：`elements_excluded` 走 `element_inv` 倒排，
是硬约束，把「化学上不可能的卡」整体删掉，预筛池从 1000 缩到 386~600，
次相不必再跟一堆不可能的组合抢 Top-20。

### 20.5 这条结论能怎么用、不能怎么用

**能用**：
- 界面上把「样品元素」提到显眼位置（现在在约束面板里，容易被跳过）。凡是做过 XRF/EDS
  或知道配方的样品，填元素后的召回是 30/43 而不是 20/43。
- 报告里 20/43 这个数字应标注为「**无化学约束**时的值」，不是引擎上限。

**不能用**：
- 30/43 是**上界**：元素是从真值反推的。真实使用中元素来自外部测量，可能缺元素
  （轻元素 Be/B/C/N/O/F 常常测不到）——缺一个 O 就会把大量氧化物误杀。所以这个数字
  只能当「化学信息给足时的能力上限」，不能当交付指标。
- 不要据此改 FoM 权重：这次证明的是「信息不足」，不是「打分不对」。权重改动的两次
  实测（§9.3、§16）都无效，与此并不矛盾。

**API 陷阱（实测踩到）**：`prescreen(elements_allowed=…)` 的语义是「**必须全部含有**」
（exact required filter），不是「允许集合」。想表达「只允许 Zn/Al/Ca/O/F」必须用补集：
`elements_excluded = 全元素表 - 允许集合`。第一次按字面意思传 `elements_allowed`，
池子缩到 76 张卡、连 ZnO 都 MISS —— 因为「同时含 Zn 和 Al 和 Ca 和 O 和 F」的相在库里
只有 76 个。

## 23. COD 全库候选池稀释：元素约束让两个库收敛（2026-11-06）

### 23.1 问题

§22 证明 COD-Full 与 COD-Inorg 峰数据完全同源，但合成谱相位级 Top-1
仍是 7/13 vs 11/13。全库 **93.3%** 的相含 C/H，怀疑是**有机卡稀释候选池**。
本节验证这个假说并找正解。

### 23.2 诊断：真值相没被挤出池，是 FoM 输给有机卡

`.scratch/_probe_codfull_pool.py`（只读）对 4 个退化样品跑四种干预，
用 `_phase_hit` 的相位级判据定位真值相名次：

| 样品 | Full 默认 1000 | 深名额 8000 | 元素补集 1000 | Inorg 默认 | Top-20 有机卡 |
|---|---:|---:|---:|---:|---:|
| `synth_02` | #2 | **#1** | **#1** | #1 | 17/20 |
| `synth_03` | #2 | #2 | **#1** | #1 | 16/20 |
| `synth_08` | #3 | **#1** | **#1** | #1 | 9/20 |
| `synth_09` | #7 | #23（更差） | **#1** | #1 | 19/20 |

- 真值相**全部在池内**（#2/#2/#3/#7），不是名额挤出 → 再次否定「放大名额」
  假说（与 §20 一致）。深名额只在 2/4 有效，`synth_09` 反而 7→23：
  更多候选只是放进更多能凑巧匹配的有机卡。
- 元素补集约束 **4/4 把真值相抬到 #1**；池从 1000 缩到 56–943，
  单次检索 1.6–2.3 s → 0.62–1.19 s（快约 2–3 倍）。

### 23.3 全量 13 组：两个库在元素上界下数字完全相同

给 `tools/bench_pattern_set.py` 补 `--oracle-elements`（与
`tools/bench_real_samples.py` 对称）：用真值相在库内的 `elements` 反推允许元素，
其余全部标 `EXCLUDE`。默认输出逐项不变（与 §21/§22 基线比对为 `True`）。

| 库 | 口径 | Top-1 | Top-5 | 序贯完整 | 相召回 |
|---|---|---:|---:|---:|---:|
| COD-Inorg（默认） | 无约束 | 11/13 | 12/13 | 10/13 | 19/24 |
| COD-Full | 无约束 | 7/13 | 11/13 | 8/13 | 17/24 |
| COD-Inorg | 元素上界 | **12/13** | **13/13** | **12/13** | **23/24** |
| COD-Full | 元素上界 | **12/13** | **13/13** | **12/13** | **23/24** |

**决定性证据**：给足化学信息后两个库收敛到完全相同的四个数字。
全库相对无机库的全部差距（T1 −4、序贯 −2、相召回 −2）**100% 来自那些
多出来的有机 / 无关卡**，不是峰数据、不是引擎、不是库规模本身。

换句话说：**默认库选 COD-Inorg 的优势，本质是一次隐式的化学过滤** ——
它预先替用户排除了大部分有机相；一旦用户显式给出元素，这个优势就消失了。

### 23.4 反例：`synth_04` 变差（两个库一致）

元素上界不是零代价：`synth_04` 的 Top-1 与序贯完整都由命中变不命中，
且**两个库都一样**，所以不是全库特有问题。诊断显示真值相仍在池内
（默认 #1 → 约束后 #3），是排序变化而非被排除；放大名额 8000 也让它 #1→#3。
净账：COD-Full 6 个样品 Top-1 变好 / 1 个变差，COD-Inorg 2 个变好 / 1 个变差。
所以元素约束在合成谱上**主要抵消大库稀释**，不是普遍提升 —— 真实谱那边
（§20）才是 20/43→30/43 且无一样品变差。

**上界口径说明**：元素由真值相在库内反推，现实中来自 XRF/EDS 或配方；
轻元素漏填会误杀氧化物。这是「化学信息给足时引擎能做到什么」，不是交付指标。
但这条证据走 `element_inv` 倒排硬过滤、**不依赖强度形**，所以不受合成谱
「用库内参考强度反演」的尺子偏差影响，两把尺子方向一致。

### 23.5 结论与产品含义

1. **稀释假说成立**，正解是元素约束，不是放大名额、不是改 FoM、不是重建库。
2. §20.7 已产品化的「样品元素」输入框正是这个功能：挂载 COD-Full 这类
   覆盖性大库时**更该填**，一行输入就能把全库拉到无机库水平。
3. 默认检索保持 COD-Inorg 依然正确（相当于内置化学先验），但文档应向用户
   说明：全库挂载时元素约束不是可选项而是前提。
4. 不改任何默认值、不动峰数据、不重建库；本轮只给基准脚本加了上界口径开关。

## 25. 元素约束补到 CLI：`--sample-elements`（2026-11-06）

§20.7 把「只允许这几个元素」从 118 次点击压成 GUI 里的一行输入框，§24 又在
挂载大库时把这条建议推到用户眼前。但命令行侧一直只有 `--restraints`，要表达
同一件事仍得手写 113 个 `EXCLUDE` 键值 —— 表达成本原封不动地留在了自动化链路里。
本节把 GUI 的快捷语义原样搬到 CLI，并让两边共用同一份补集实现。

### 25.1 做法：纯函数下沉到 core，GUI / CLI 同源

| 层 | 改动 |
|---|---|
| `xinmatch/core/model/element_symbols.py`（新增） | 118 元素符号表、`parse_element_symbols()`、`complement_restraints()`、`restraints_from_sample_elements()`。**零 PySide6 依赖** —— CLI 若直接 import `xinmatch.ui.periodic_table` 会把整个 Qt 拖进命令行进程 |
| `xinmatch/ui/periodic_table.py` | 删除本地重复实现，改为 re-export；`apply_detected_elements()` 的补集改用 `complement_restraints(detected).elements`。GUI / CLI 语义只有一个来源 |
| `xinmatch/cli/main.py` | `search` / `run` 各加 `--sample-elements`，与 `--restraints` 放进 `add_mutually_exclusive_group()`；`_load_restraints()` 优先走快捷参数 |

**语义护栏不变**：检出元素保持 `OPTIONAL`，其余 113 个标 `EXCLUDE`。
`elements_allowed` 是「必须**全部**含有」，按字面传允许集合会把池缩到几十张卡、
连真值都 MISS（§20.5）。

### 25.2 参数边界：三处刻意的「不静默」

| 情形 | 行为 | 理由 |
|---|---|---|
| `--sample-elements` 与 `--restraints` 同时给 | argparse usage error（exit 2） | 不靠函数内部的静默优先级猜用户意图 |
| `--mode fpfm --sample-elements ...` | 明确 `ValueError`，提示去掉该参数 | FPFM 全谱拟合不接元素约束；不继承 `--restraints` 在 FPFM 下的历史静默忽略 —— 填了约束却没生效是更糟的失败 |
| 未知符号 / 化学式 / 空输入 | 中文可操作错误（exit 1） | 不猜化学式。`Al2O3` 会被当成未知符号并提示「请填元素符号，不要填化学式」；漏填轻元素会误杀氧化物 |

结果 JSON **只在显式给出时**回显 `sample_elements`，默认输出逐项不变 —— 既有脚本
的基线不需要改。

### 25.3 元素表口径核对：三份表、两个顺序、一个集合

动手前先核了一遍，避免「补集漏掉某个元素」：

| 表 | 数量 | 顺序 | 用途 |
|---|---|---|---|
| `cif_meta.IUPAC_ELEMENTS` | 118 | 原子序数 | **权威**：定义 `elem_mask` 位号，绑定 `meta.element_mask_scheme` 哈希，位号一变已建好的库就读错 |
| `core/model/element_symbols.ELEMENT_SYMBOLS` | 118 | 周期表按钮布局（镧系/锕系单独放末尾） | GUI 摘要展示 + CLI 补集 |
| `ui/periodic_table._ELEMENTS` | 118 | 同上（含行列坐标） | 按钮网格 |

三者**集合完全相同**、各自无重复（实测 `set` 相等、`IUPAC-only` / `core-only` /
`gui-only` 均为空）。共享层刻意不 import `cif_meta`，避免 model 反向依赖 db；
同步由 `tests/model/test_element_symbols.py` 的集合断言 + GUI 的 import 期逐项
校验双重守住。基准脚本 `ALL_ELEMENTS`（91 项）是**另一套上界口径**，只用于
`--oracle-elements` 复现，不参与 CLI 补集，不要混。

**118 项补集在真实库上安全**：`reader_v3.element_exclude_filter()` 对
「`element_inv` 里根本没有」的元素是 `continue`（排除不了任何相），不像
required 方向那样把结果清空。COD 里没有的超铀元素标 `EXCLUDE` 只是几次缓存
命中的 SQL 查询，既不会误杀、也不会把候选池清空。

### 26.2 LP 语义澄清，以及一条容易被读错的时间线

结论里的「不做全局 **LP** 修正」指 **Lorentz-Polarization（洛伦兹-偏振因子）**，
`LP(2θ) = (1+cos²2θ)/(sin²θ·cosθ)`，**不是线性规划**。全仓没有 `linprog` /
线性规划实验；权重标定用的是 NNLS + 网格坐标上升（`tools/tune_weights.py`）。

更要紧的是别把这条 2026-10-13 的结论与今天的 v3 库读成矛盾：

| 时间 | 库强度口径 | 发生了什么 |
|---|---|---|
| T0.8 当时（v2 SQLite 卡片库） | 未修正的 COD `I_calc`（结构因子²，缺 LP） | 合成谱生成器按 v2 卡强度造谱，人工验收基线也绑定旧谱。若**运行时**给整库统一乘 LP 再归一化，合成谱验收与真实谱 Top-1 双损 ⇒ 决定不改 |
| v3 重建库（2026-10-20） | **建库时**就把强度口径改成含 LP / 结构因子修正 | 这是**上游建库口径变更**，不是运行时全局 LP。MgO 220 线 v2=284 → v3=570（§1） |
| 2026-11-04 诊断 | 库是 v3，但 13 组合成谱仍按 v2 强度生成 | 两把尺子不同源 ⇒ 新增 `--peak-source v3` 重建合成谱（§1、`docs/检索基准-v3-诊断-20261104.md` §4） |

即：T0.8 否定的是「在检索运行时对既有库做一次性全局 LP 补偿」，而 v3 是在
**建库阶段**连同合成谱一起换了口径 —— 两者不冲突，后者恰恰避开了前者担心的
「尺子与库不同源」问题。

### 26.3 五分量、发布权重与唯一的 ground truth

`FoM = 1 − w₁(1−P_peakpos) − w₂(1−P_intensity) − w₃(1−P_npeaks)
− w₄(1−P_ncorr) − w₅|ln(I_scale)|`（`FOM_MODEL.md` §2 /
`fom_criteria.py::FomWeights`）：

| 判据 | 工作定义 | 发布权重 | 相对重要性 |
|---|---|---|---|
| `P_peakpos` | `exp(−mean(Δ2θ²)/σ_pos²)`，`σ_pos=0.15°` | **0.2275** | 33.2 % |
| `P_intensity` | `exp(−mean(ΔI_norm²)/σ_intensity²)`，两侧 max→100，`σ_intensity=10` | **0.1112** | 16.2 % |
| `P_npeaks` | `n_matched_exp / n_exp_total` | **0.2306** | 33.7 % |
| `P_ncorr` | `n_matched_ref / min(n_exp, n_ref)` | **0.1152** | 16.8 % |
| `I_scale` | LSQ `Σ(I_exp·I_ref)/Σ(I_ref²)`，失配取 `\|ln(I_scale)\|` | **0.0454** | — |

前四项近似 `2:1:2:1` 但**不是精确分数**（代入 1/3、1/6 会让 R² 变负）。
T6.10 已用 NNLS 重拟合 + 网格细化复算：R²=0.9971 / τ=0.9660 / RMSE=0.0049，
结论 `KEEP`（发布权重在搜索范围内已最优）。留一样品交叉验证 Top1 3/3、
Top5 15/15。

**唯一的参考软件 ground truth** 是 lab6/LaB6 Top1 一行
（`tools/build_baseline.py::LAB6_REF_P_VALUES`）：
`peakpos 0.9968 / intensity 0.9963 / npeaks 0.9961 / ncorr 1.0000 /
i_scale 1.0348 / FoM 0.9979`。它是**反推用的对照值，不是 XinMatch 的五分量
验收门槛** —— 项目里并不存在「`P_peakpos ≥ 0.99`」这类独立阈值，别把它当门禁读。

### 26.4 三条结论与关键数字（正文见 `STATUS.md` §T0.8）

**① 权重保持发布值不动** —— 三条独立证据：

| 单相标样 | `BRUCITE` `CORUNDUM` `FLUORITE` `MAGNETIT` `ZINCITE` `ZIRCON` `CPD-Y2O3` | 计入，wt=100 |
| CPD-1 梯度 | `CPD-1A`…`1H`（三相，8 组配比） | 计入，weighed wt% |
| CPD-2/3/4 | 择优取向 / 非晶 / 微吸收 | 计入（`CPD-3` 的 Glass 29.47 wt% 是非晶，不进相分母） |
| 合成铝土矿 | `BAUXITE`（七相，wt% 已知） | 计入 |
| 非晶标样 | `SILICA` | **排除**：背景 912 / 峰高 985，7251 点里 267 个「峰」全是噪声 |
| 药物组 | `MANNITOL` `SUCROSE` `VALINE` `STARCH` `NIZATIDI` | **排除**：库内无该物相，见 §28.6③ |
| 药物混合 | `PHARM1GR` `PHARM2GR` | **排除**：说明文件只给 5 个候选相，未指明各谱含哪些 |
| 天然花岗闪长岩 | `GRANODIO` | **排除**：说明文件明写「True values not known」 |

**评分集 = 19 个样本 / 48 个真值相。** 排除的 9 个样本一律不进分母，理由逐条写在
`IUCR_EXCLUDED` 里（不是「不好跑」）。

取文件规则：`_raw` 优先，`_mdi` 次之，裸名兜底。`_raw` 与 `_mdi` 是**同一次测量的
两种导出**（`_mdi` 从 5.02° 起、7250 点，`_raw` 从 5.00° 起、7251 点），混用会让
数字不可比；`CPD-1F/1G/1H` 只有裸名一种，所以裸名必须是兜底而不是报错。

### 28.2 主口径为什么是「矿物名级」

这是与 §17 相反的选择。理由不是偏好，而是这批数据的真值相**落在同组成多晶型族里**
——`Synthetic Bauxite` 七相全部如此（COD-Inorg 计数）：

| 真值相 | 库内同组成卡 |
|---|---|
| Gibbsite (54.90 %) | Gibbsite / Bayerite / Doyleite / Nordstrandite（17 张） |
| Kaolinite (3.02 %) | Kaolinite / Dickite / Nacrite / Metahalloysite（22 张） |
| Anatase (2.00 %) | Anatase / Rutile / Brookite（40 张） |
| Quartz (5.16 %) | Quartz / Cristobalite / Coesite / Moganite（309 张） |

但**「组成级会系统性高估」这个预判被实测否掉了**。同一批候选上两把判据并列比较
（COD-Inorg、给元素、族级）：

| 口径 | 卡级 | 族级 |
|---|---|---|
| 矿物名级（fine） | 39/48 | **45/48** |
| 组成级（coarse） | 39/48 | 44/48 |

> **口径修订（§29）**：本节初版记的是「两边都是 44/48，总数巧合相同，偏差双向」。
> 族级判定修好之后（族内任一成员命中即算命中）fine 变成 45/48，与 coarse 不再相等。
> 详见 §29.5 —— 初版举证的那一半差异是族级实现缺陷造成的假差异。

现在剩下的唯一差异是**单向**的，组成级漏判：

- **组成级漏判**：`CPD-2` 的 Brucite 被漏掉 —— 库内 Brucite 卡多为氘代
  （`D1.96 H0.04 Mg O2`），而比值判据要求元素集完全相同，含 D 的卡永远匹配不上
  `H2 Mg O2`；矿物名级按名判定，正确命中。

`BAUXITE` 的 Boehmite 曾被认为是「组成级误判」的例子（一张同组成 `Al H O2` 但
不带该矿物名的卡占了位置）。族级改判族内全部成员后，矿物名级也命中它了 —— 那张
「异名卡」其实就是同一族里的另一张卡（`Bohmite` 错拼），所谓误判并不存在。

所以两个口径**互不包含**，只能并列、不可互相替代，也绝不能平均。`--coarse`
开关保留这条对照，默认关闭。

### 28.3 主结果：两个库 × 两套口径

19 个样本、48 个真值相，矿物名级口径：

| 库 | 模式 | Top-1 | Top-5 | 卡级 | 族级 | 序贯 | wt 加权（族级） | 预筛被截断 |
|---|---|---|---|---|---|---|---|---|
| COD-Inorg 78,035 | plain | 17/19 | 18/19 | 26/48 | 27/48 | 37/48 | 0.778 | **19/19** |
| COD-Inorg 78,035 | elements | 18/19 | 18/19 | 39/48 | **45/48** | 45/48 | **0.995** | 3/19 |
| COD-Full 532,038 | plain | 17/19 | 18/19 | 24/48 | 25/48 | 37/48 | 0.762 | **19/19** |
| COD-Full 532,038 | elements | 18/19 | 18/19 | 39/48 | **45/48** | 45/48 | **0.995** | 3/19 |

`plain` = 只给谱；`elements` = 额外给样品元素，其余元素按产品路径（118 元素补集）
标为必须不含。元素由真值化学式反推，属于**上界**（现实中来自 XRF/EDS）。

这张表里最重要的一行不是数字最大的一行，而是：

> **库从 78k 扩到 532k（6.8 倍），给元素时相召回一格没掉（45/48、0.995 全同）；
> 不给元素时掉 2 个相（27 → 25）。**

`wt 加权` 是按 weighed wt% 加权的族级召回（`Σ 命中相 wt / Σ 相 wt`），回答「按质量
计我解释了多少样品」。§23 用合成谱得出过「元素约束让两个库收敛」；这里用 IUCr 官方
配比重做了一遍，结论一致，而且这次含量是真值。

`Top-5 覆盖全相` 只有 6/19，全部来自单相样本 —— 多相样本不可能在 Top-5 里覆盖 3–7
个相，这个指标在本数据集上只有「单相是否被认错」一个含义。

### 28.4 含量—召回曲线（本数据集独有）

只统计 12 个多相样本的 41 个真值相（单相样本的 100 wt% 没有信息量）。**族级**：

| wt% 桶 | 相数 | Inorg plain | Inorg elements | Full plain | Full elements |
|---|---|---|---|---|---|
| < 5 % | 7 | 1/7 | **5/7** | 1/7 | **5/7** |
| 5–20 % | 11 | 4/11 | **10/11** | 3/11 | **10/11** |
| 20–50 % | 15 | 8/15 | **15/15** | 7/15 | **15/15** |
| ≥ 50 % | 8 | 8/8 | 8/8 | 8/8 | 8/8 |

**卡级**与**序贯**同表（Inorg elements）：<5 % 3/7 与 4/7；5–20 % 7/11 与 11/11；

最硬的单点是 `CPD-1A`：刚玉只有 **1.15 wt%**、锌白 4.04 %、萤石 94.81 %。

所以「次相检测下限」不是一条线，而是两条：**给元素后低于 5 wt% 仍能找回大部分
（7 个里 5 个，含 1.15 % / 1.36 % / 1.36 % 三个极端值）；不给元素时 < 5 % 桶只剩
1/7。**

### 28.5 三个诊断：低分是引擎的，还是库的？

#### ① 预筛 1000 卡上限：`CPD-1F/1G/1H` 的萤石丢失

`CPD-1G`（三相近等量 31.37 / 34.21 / 34.42）plain 只有 1/3，缺刚玉与萤石。萤石的
111（28.26°）与 220（47.00°）都是谱里第 2、第 3 强的峰，按道理不该丢。

直接看预筛元数据（`search_match_v3` 的 `n_prescreened` / `truncated`）：

| 模式 | 预筛通过 | 截断 | 萤石在候选里 |
|---|---|---|---|
| plain | 1000 | **True** | ✗ |
| elements | 366 | False | ✓（Top-5 第 3 位，FoM 0.772） |

机制：`PRESCREEN_TOP_K = 40` 只拿最强 40 个实测峰去匹配，`DEFAULT_RANK_LIMIT = 1000`
截断候选。这张谱有 174 个峰（0.02° 步长 + 高背景），能碰巧匹配 2 个窗（`min_match=2`）
的卡在 78k 库里就远超 1000 张，萤石只有 4 条线、排不进前 1000。**这是候选池稀释，
不是评分失败** —— 同一个引擎、同一张谱，只是把候选池从 1000 收到 366，萤石立刻回来。

#### ② `BRUCITE` 单相标样：择优取向把 001 峰放大 5.1 倍

Brucite 的峰位与理论完全吻合（18.58 / 37.98 / 50.84 / 58.60 / 68.24），但 001
峰强度 **73,657**，是第二强峰（14,424）的 **5.1 倍**。层状氢氧化物压片极易 (001)
择优取向，实测强度分布与库内粉体理论强度不是一个形状。

| 模式 | Brucite 排名 | 相召回 |
|---|---|---|
| plain | 100 名外（Top-1 是一张 MIL-53(Sc) 的乱名卡） | 0/1 |
| elements | 第 8 名（`deuterated brucite at 15 K`） | 1/1 |

结论：单相标样的失败同时来自「择优取向 + 候选池稀释」，元素约束能救后者，救不了
前者。`CPD-2`（专门设计来测择优取向，含 Brucite 36.26 wt%）是同一个故事的放大版：
plain 族级 1/4、wt 加权 **0.199**；elements 族级 **4/4**、wt **1.000**。

#### ③ 药物组：库覆盖缺口，不是引擎问题

这部分**不进评分**，因为真值在库内不可达。COD-Full（532k，含有机）里逐条核实：

| 真值相 | 化学式 | 库内同组成卡 | 实际是什么 |
|---|---|---|---|
| Mannitol | `C6 H14 O6` | 7 | 全是山梨醇（`Gamma Sorbitol`）与无名卡 —— 同分异构体 |
| Sucrose | `C12 H22 O11` | 14 | 全是乳糖 / 海藻糖 —— 同分异构体 |
| DL-Valine | `C5 H11 N O2` | 25 | 有 `L-Valine` 1 张；真值是外消旋 DL-，手性不同即不同晶相 |
| Starch | `C6 H10 O5` | 13 | 糖酐（`Levoglucosan`）等小分子 —— 淀粉是半结晶聚合物，COD 不收 |
| Nizatidine | `C12 H21 N5 O2 S2` | **0** | 库里没有 |

这五条本身就是结论：**COD 这类晶体学数据库不足以支撑药物 XRD 检索**，真实药物谱
在当前库上必然低分。把这条记下来比把它折叠进召回率有用 —— 折叠进去只会让人以为是
算法不行。

### 28.6 结论

1. **第三把尺子成立且必要**：IUCr CPD 提供了前两把尺子都没有的东西 —— 真实谱 +
   官方 weighed wt%。「含量—召回」曲线现在可以画了。
2. **元素约束的价值被独立复核**：同一批真实谱，只补「样品元素」一条现实可得的信息，
   相召回 27/48 → 45/48，wt 加权 0.778 → 0.995，预筛截断 19/19 → 3/19。这与 §23
   用合成谱得出的结论一致，两套完全独立的尺子同向。
3. **给元素后检索对库规模不敏感**：78k → 532k（6.8 倍），相召回 45/48 与 0.995
   一格未动。不给元素时掉 2 个相。
4. **两个真值口径互不包含**：族级 fine 45/48、coarse 44/48，差异只剩一处 ——
   组成级漏判 `CPD-2` 的 Brucite（氘代卡元素集不等）。**这条差异不是「各有各的错」
   而是单方的下界**：上一版记的「双向偏差」（BAUXITE 的 Boehmite 被组成级误判）
   已被 §29 推翻，那是族级只取代表卡造成的假差异。
5. **瓶颈已经不在算法层**：19 个样本里 plain 有 19 个、elements 有 3 个被 1000 卡
   上限截断。继续调 FoM 权重不会有收益 —— 收益在候选池与库覆盖。

**边界**（必须与结论一起引用）：

- 元素由真值化学式反推，是**上界**。现实中 XRF 会给更宽的元素集（检出限、轻元素、
  非晶成分），数字只会更低，不会更高。
- `GRANODIO`（天然多相，真值未知）、`PHARM1GR/2GR`（真值不完整）、`SILICA`
  （非晶）四个样本已排除，本报告的 48 相分母不含它们。
- `CPD-3` 的 Glass（29.47 wt%）与 `SILICA` 是非晶，本引擎不做非晶定量，两者都
  未参与任何分母。
- 样本量小：19 个样本、48 个相，单相缺失就能让一个桶的比率跳 14 个百分点。所有
  比值都应当读作量级判断，不是精确指标。

## 29. 族级口径修复：从「族代表卡」到「族内任一成员」（2026-11-07）

这一节修的**不是引擎**，是基准自己的判据。触发它的是一场「为什么铝土矿只召回 3 个相」的
只读诊断：诊断结论里有两条是引擎/数据的问题（只记录，见 §29.6），第一条是基准的 bug。

### 29.1 缺陷：族折叠的语义与实现不一致

「族级」这个指标在报告里一直写作「折叠后 Top-20 族」，语义是**同一物相的多张卡只占一个
位置** —— 这正是不看族级就没有的那部分信息（`5-3` 卡级 1/5、族级 2/5 就是它）。

但实现一直是每族只取**排名最高的那张卡**（代表卡）：

```python
fam = [whole.candidates[g[0]] for g in group_same_phase([c.entry for c in whole])][:top_n]
in_fam = [any(fine_hit_entry(c.entry, t) for c in fam) for t in fine_truths]
```

这等价于把语义偷偷换成「**这一族的榜首卡是不是真值相**」。两者只有在「族内所有卡对同一
真值相判定一致」时才等价，而 COD 里恰好不成立：拼写变体（`Boehmite` / `Bohmite`）、
不同设置、掺杂固溶体都会在同一族里并存，且排名先后与拼写是否正确**无关**。

### 29.2 证据链：BAUXITE 七相为什么只召回 3 个

`BAUXITE`（七相，weighed wt% 已知）给元素时族级只有 3/7。逐层排查后，**候选池与峰都不是
原因**：预筛 1000 张（`truncated=True`）里七相全在，184 个峰把各相的理论线都检出了
（Goethite 7/7、Quartz 9/9、Kaolinite 7/8、Anatase 5 检出 + 4 条 0.22° 内偏移）。

| 相 | wt% | 卡排名 | 族排名 | 最佳命中卡 | peakpos | intensity |
|---|---:|---:|---:|---|---:|---:|
| Gibbsite | 54.90 | 0 | 0 | `96-154-4375` gibbsite | 0.840 | 0.683 |
| Boehmite | 14.93 | 15 | **6** | `96-901-2253` Boehmite | 0.790 | 0.812 |
| Hematite | 10.00 | 3 | 3 | `96-901-5964` Hematite | 0.874 | 0.747 |
| Goethite | 9.98 | 25 | 12 | `96-100-8768` Goethite | 0.772 | 0.315 |
| Quartz | 5.16 | 47 | 22 | `96-900-5018` Quartz | 0.734 | 0.412 |
| Anatase | 2.00 | 63 | 31 | `96-100-8198`（无名） | 0.730 | 0.288 |
| Kaolinite | 3.02 | 135 | 68 | `96-900-9234` Kaolinite | 0.800 | **0.000** |

`Boehmite` 的族（族 6）共 8 张卡，按名次是：

```text
rank 10  96-901-2275  'Bohmite'   Al H O2   ← 代表卡（错拼）
rank 12  96-901-2274  'Bohmite'   Al H O2
rank 15  96-901-2253  'Boehmite'  Al H O2   ← 正确拼写，同一族

```

代表卡是错拼的那张，`fine_hit_entry` 按名判定 → miss；正确拼写卡就在同一族里，却被代表卡
挡住了。**15 wt% 的主相被自己的口径判成漏检。**

顺带排除了「折叠深度不够」这个先前的怀疑：`deep_n = 100 / 200 / 400` 三档族级都是 44/48，
候选顺序与 `deep_n` 无关（100 与 1000 的前 30 张 ID 与 FoM 逐张一致）。

### 29.3 修复：族内任一成员命中即算命中

`tools/bench_real_samples.py` 新增共享函数 `family_members(cards, top_n)`，返回**前 top_n 族、
每族带全部成员卡**；`tools/bench_iucr.py::_score` 与 `bench_real_samples` 的三处族级判定
（粗口径 / 细口径 / 元素上界）一并改用它：

```python
def family_members(cards, top_n):
    groups = group_same_phase([c.entry for c in cards])
    return [[cards[i] for i in g] for g in groups[:top_n]]

in_fam = [any(fine_hit_entry(c.entry, t) for fam in fams for c in fam) for t in fine_truths]
```

族的**排名**不变（仍是族首卡的名次），变的只是「这一族算不算命中」。这不放松口径：
一个族仍然只占一个位置，只是不再让排序的偶然性决定真值相能不能被看见。

### 29.4 重跑：受影响的全部历史数字

只改了判据、没碰检索，所以**卡级 / Top-1 / Top-5 / 序贯 / 预筛**一个都不该动。实测吻合：

**IUCr CPD（19 样本 / 48 相）**：逐相对照脚本报「变化条目 1」，两个库都是同一处。

| COD-Full | plain | 24/48 | 25/48 | 0.762 |
| COD-Full | elements | 39/48 | **44/48 → 45/48** | **0.987 → 0.995** |

唯一变化：`BAUXITE` 的 **Boehmite**（§29.2）。含量梯度随之 5–20 % 桶 9/11 → **10/11**
（两库同）。`wt` 分母 1,869 wt%，Boehmite 14.93 wt% → +0.008。

**13 组实验室谱（粗 /43、细 /50、上界 /43）**：

|---|---|---|

代表卡常是无名的那张。

`hits` 组逐项不变，说明 §21 的裁定依据不受影响。

### 29.5 连带纠正：§28.2 的「双向偏差」有一半是假差异

上一轮把 `BAUXITE` 的 Boehmite 记成「组成级误判命中、矿物名级正确记为 miss」，据此得出
「两口径偏差是双向的」。族级口径修好后：矿物名级也命中 Boehmite，**那条差异消失了**。
现在两口径（族级、给元素）是 fine **45/48** 对 coarse **44/48**，唯一差异是
`CPD-2` 的 Brucite（组成级漏判，氘代卡元素集不等）—— **单向**。

也就是说，上一轮那个「双向」结论里，一半是口径的**实现缺陷**，被误当成了口径的**固有差异**。
`COARSE_NOTES` 与 `bench_iucr.py` 的模块文档已按实测改写，并写下了这条教训：

> 口径差异必须先确认口径本身的实现无缺陷，再谈「两个口径各有各的盲区」。

### 29.6 只记录、不动引擎的两条边界

诊断里另外两条**不是基准的问题，也不是一行能修的**，按项目口径只记录：

**① Kaolinite：择优取向的第二个受害者。** `peakpos 0.800`（全场第二高）但
`intensity 0.000` —— 001 线（12.33°）实测峰高只有 **137**，而全谱最强峰是 5000。
库内粉体理论强度里 001 是最强线。这与 §28.5 ② 的 BRUCITE 001 被放大 5.1 倍是**同一物理
效应的两个方向**（一个压、一个抬）。元素约束救不了它：元素已经给对了，错的是强度形。

> **§31 更正**：称 Kaolinite「择优取向受害者」只说对了一对配对。把 `P_intensity` 逐对
> 拆开后，001 被压只是最大的一对，紧随其后的四个大偏离**全是正向**（参考强度 0.8 的
> 线上落着 996 的实测强峰），是**别的相的强峰被误配到它的弱线上**。删掉 001 这一对，
> P 也只从 0.00032 到 0.00127。同理，BRUCITE 001 被放大 5.1 倍却没进它自己的偏离前六。
> 结论：漏检的主因是「参考弱线误配 + 判据对配对长度敏感」，不是择优取向。

**② 序贯轮次被「元素允许、物相不合理」的卡吃掉。** BAUXITE 八轮的确认顺序：

```text
#1 Gibbsite   #2 Hematite   #3 Boehmite   #4 无名卡
#5 Silicon    #6 Hydrogen   #7 Goethite   #8 Quartz
```

`Si` 与 `H` 都在样品允许元素集里，元素约束放行 —— **元素约束只能排除「元素不可能」，
不能排除「物相不合理」**（单质硅、单质氢）。三轮白费后 Kaolinite 与 Anatase 没机会进榜。
这类「化学上合法但物理上荒谬」的卡需要另一层判据（如单质/气相相过滤），属于引擎改动，
要独立验收，本轮不做。**该判据已按此要求单独验过，结论是不做 —— 见 §30。**

## 30. 序贯里的「单质卡」：证据驱动的「不动」决策（2026-11-07）

§29.6 ② 记下过一个现象：BAUXITE 给元素后序贯 8 轮里，第 5、6 轮被 `单质:Si`、
`单质:H2` 占掉，元素约束放行（Si 与 H 都在硅酸盐 + 氢氧化物的允许元素集里）。
当时的推论是「需要另一层判据，如单质/气相相过滤」。**本节把这个推论拿到数据上验，
结论是：不做。**

### 30.1 规模：单质卡在库里占多少

| 库 | 相数 | 单质卡（元素集只有 1 个元素） |
|---|---:|---:|
| COD-Inorg | 78,035 | **1,413（1.81 %）** |
| COD-Full | 532,038 | 1,413（0.27 %，同一批卡） |

不是罕见异类，但也远不是主流。它们在 Top-20 里出现的频率更低：IUCr 19 样本 × 2 套模式
（760 个位置）27 个，3.55 %；13 组实验室谱（520 个位置）13 个，2.50 %。

### 30.2 三档变体：有物理依据的窄规则零增益

同一批样本（IUCr 19 × 2 模式 + 13 组 × 2 模式 = 32 组），只改序贯每轮「选哪张卡」：

| 变体 | 规则 | IUCr（/96 位） | 真实谱（/100 位） | 合计 |
|---|---|---:|---:|---:|
| `none` | 现状：取榜首 | 82 | 61 | 143 |
| `diatomic` | 只跳双原子/气相单质（H₂ N₂ O₂ F₂ Cl₂ Br₂ I₂） | 82 | 61 | **143（零增益）** |
| `all` | 跳过所有单质卡 | **83** | **62** | **145** |

`diatomic` 有物理依据（固态样品里不可能有气相相），但它**一点用都没有** —— BAUXITE 的
`H2` 排在第 6 轮，跳过它不改变前 5 轮的结果。真正产生增益的是跳过**金属单质**：

- `BAUXITE` elements 5 → 6：多找到 **Anatase（2.00 wt%）**；
- `5-3` 上界 4 → 5：多找到 **Fluorapatite**。

### 30.3 反事实：单质标样会 6/6 失效

「跳过金属单质会不会误伤真实的单质样品」不能靠推理，得测。库里没有单质谱样本，所以用
库内单质卡自己的峰位与强度合成**理想粉体谱**（Gauss，FWHM 0.12°，背景 20，0.02° 步长，
5–90°），再跑现状与 `all` 两套序贯：

| 单质 | 库内卡 | 峰数 | 现状 | 跳过单质 |
|---|---|---:|---|---|
| Si | `96-724-8757` | 150 | ✅ 第 1 位 `Si` | ❌ 第 1 位 `C8 N4 S3` |
| Al | `96-150-2689` | 10 | ✅ 第 1 位 `Al` | ❌ 第 1 位 `Co0.5 Ga2.5 Zr` |
| Fe | `96-411-3919` | 150 | ✅ 第 1 位 `Fe` | ❌ 第 1 位 `Ba Fe2 Ho O5` |
| Zn | `96-901-1599` | 23 | ✅ 第 1 位 `Zn` | ❌ 第 1 位 `Mn0.02 Zn1.98` |
| Cu | `96-151-2504` | 8 | ✅ 第 1 位 `Cu` | ❌ 第 1 位 `Cu0.91 Ge0.09` |
| Mg | `96-810-3640` | 150 | ✅ 第 1 位 `Mg3` | ❌ 第 1 位 `C24 Cl N24 Ni4 O55 V18` |

**6/6 全部失效，而且失效方式一致：第 1 轮就丢掉真值。** 序贯是逐相剥离，第一轮选错会
污染残差，后面 7 轮都救不回来。

口径边界要说清楚：这是**理想谱**，比真实谱容易（强度形精确、无择优取向、无噪声）。
所以它只能证明「风险存在」，不能证明真实单质样品一定失效 —— 但方向是明确的：真实谱只会
更难，不会更容易。

### 30.4 裁定：不改默认值

1. **增益太小**：+2 个相（两把尺子各 +1），而 §28.6 已经声明这套数据集的样本量下
   「单相缺失就能让一个桶的比率跳 14 个百分点」。为一个噪声量级的收益引入一条会改变
   榜首行为的规则，收益/风险比不成立。
2. **有物理依据的窄规则零增益**：`diatomic` 一相未增。要拿增益就必须跳金属单质。
3. **代价是确定的**：6/6 单质标样在第 1 轮丢失真值。而单质标样恰恰是实验室最容易做的
   实验之一（Si / Al / Cu 都是常见的仪器标定物）。
4. **序贯的真正瓶颈不在这里**：BAUXITE 剩下的 Kaolinite 是择优取向（§29.6 ①，归因已在
   §31 更正为「参考弱线误配 + 判据对配对长度敏感」），
   Anatase 是 2.00 wt% 的最低含量相；两者都不是「被单质卡挤掉」的问题 ——
   `all` 变体也只多找回 Anatase 一个，Kaolinite 依然没进。

所以：**默认行为保持「取榜首」，不加单质过滤。** 该现象连同反事实一起记入交接文档，
避免下一轮再把它当成「一行就能修的小 bug」。

### 30.5 重开条件

三条同时成立才值得重开：

- 有**真实的**单质标样谱（不是合成谱）能重复 30.3 的对照；
- 过滤器只在用户**显式声明「本样品不含单质相」**时启用，绝不进默认路径；
- 三把尺子上「不劣化」同时成立，且单质标样集合不退化。

## 31. 择优取向与强度形失配：29 个失败相的真实成因（2026-11-07）

§29.6 ① 和 §30.4 ④ 都把 Kaolinite 的漏检归给「择优取向」。本节把这个说法拿到数据上
验，**结论是：归因错了。择优取向不是这 29 个失败相的主因，「强度形」这个判据本身才是。**

本节全部只读：不改 FoM、不改配对、不改引擎。

### 31.1 分类：没有一个相卡在峰位

对 98 个真值相（IUCr 48 + 真实谱 50，元素 / 上界口径），取候选池里 FoM 最高的一张卡，
用它的 `p_values` 分类（`peakpos ≥ 0.6` 且 `intensity ≥ 0.5` 记为命中）：

| 类别 | 相数 | 说明 |
|---|---:|---|
| 命中 | 65 | 位置与强度形都过门 |
| **强度形失配** | **29** | 位置过门，强度形不过 |
| 候选池无卡 | 4 | 元素约束/预筛就没放行 |
| **峰位失配** | **0** | —— |

最低的 `peakpos` 是 **0.663**（BRUCITE，且它最终通过）。也就是说：**没有任何一个失败相
是「位置对不上」**。全部可归因的失败都集中在强度形一项 —— 位置证据已经够把相找出来，
扣分扣在强度形上，而强度形扣分的方式与物理无关（见 31.2、31.3）。

### 31.2 逐对拆解：主导偏离是「别的相的强峰打在它的弱线上」

把 `P_intensity = exp(-mean(Δ²)/σ²)`（σ=10）按配对逐项拆开：

| 相 | P_intensity | 名次 | mean(Δ²) | 最大单对 | 最大偏离是什么 |
|---|---:|---:|---:|---:|---|
| Kaolinite（BAUXITE，3.9 wt%） | 0.00032 | 135 | 805 | 7,433（占均值 923 %） | 001（12.33°）被**压**：I_ref 100 → I_exp 13.8 |
| Gibbsite（7-1） | 0.68（通过） | 0 | — | — | 33.19°：I_ref **0.6** → I_exp 25.4 |
| Brucite（BRUCITE） | 0.62（通过） | 7 | — | — | 68.80° 一带的弱线；001 被放大 5.1 倍**没进前六** |

Kaolinite 那一行是关键。001 被压（100 → 13.8，原始计数 137）确实是择优取向，但它只是
**最大的一对**；紧随其后的四个大偏离**全是正向**：

| 2θ | I_ref（归一 100） | I_exp | 实测原始计数 |
|---|---:|---:|---:|
| 26.64° | 18.3 | 100 | 996 |
| 35.65° | 4.5 | 75.4 | — |
| 28.17° | 4.2 | 67.4 | — |
| 64.00° | 0.8 | 52.8 | — |

参考强度 18.3 / 4.5 / 4.2 / 0.8 的弱线，实测却是 996 / 75 / 67 / 53 的强峰 —— 那不是
Kaolinite 的峰被放大，是**别的相的强峰被误配到它的弱线上**。把最差的一对（001）整对删掉，
P 也只从 0.00032 升到 **0.00127**，仍然等于 0。

两个「通过」的相反而更能说明问题：Gibbsite 通过，但它的最大偏离同样是别人的峰
（33.19°，参考强度只有 0.6）；Brucite 的 001 被放大 5.1 倍（73,657 vs 14,424）这么大的
择优取向，**在它的偏离排序里连前六都进不去**。所以：

> 在 Kaolinite 这个病例上，`P_intensity` 的大小不由择优取向决定，而由**参考弱线上撞进来
> 几个别人的强峰**决定。参考强度 0.8 的线上落一个 996 的峰，Δ = 99.2，单这一对就把
> mean(Δ²) 抬到 9,842 / n —— 这个量级跟 σ=10 的模型完全不匹配。

**这句不能推广到全部 29 个失败相。** 5,721 张卡的聚合统计（§32.2）显示：弱线对占配对数的
71.6 %（通过的卡）/ 78.3 %（失败的卡），却只贡献 **34.4 % / 47.8 %** 的 `ΣΔ²`；按每对平均，
反而是**强线**的 Δ² 更大（通过的卡 67.9 对 14.1，失败的卡 1,250 对 318）。也就是说
「弱线劫持」是少数病例的放大器，不是普遍机制 —— 失败的卡主要是**参考强线在实测里就弱**
（次相、择优取向、被压制），那是数据本身，不是任何统计量能修的。§32 把这个区分做实。

### 31.3 结构性缺陷：`mean(Δ²)` 惩罚「配对得多」的卡

配对是对**参考的全部峰**做的（每相最多 150 峰），所以一张卡匹配上的对数越多，它碰上
「弱线被劫持」的机会就越多，`mean(Δ²)` 就越高。这形成一条与物理无关的偏置：

| 样本 | 相 | 匹配对数 | P_base |
|---|---|---:|---:|
| real/3-1 | Fluorite | **11 / 17**（65 %） | **0.000** |
| real/3-1 | Fluorite（现状榜首那张） | 4 / 17（24 %） | 更高 |

一张对上了 11 根线（含 6 根弱线）的卡，排在只对上 4 根线的卡后面 —— 因为多对的那 7 根里
有一根撞了别人的峰。这不是强度形判据想表达的意思。所以「强度判据该不该改」这个问题是
成立的，下面测。

### 31.4 五种重排实验：涨 7 跌 4，净增益是零和重排

在同一批候选上只换强度分量的估计量，其余四个分量不变，重排后看 Top-20 相召回（98 相）：

| 变体 | 规则 | 命中 | Δ | 涨 / 跌 | Top-1（/32） |
|---|---|---:|---:|---:|---:|
| `base` | 现状 `mean(Δ²)` | 70 | +0 | — | **31** |
| `trim10` | 丢掉最差 10 % 配对后取均值 | 73 | +3 | +7 / −4 | **31** |
| `trim25` | 丢掉最差 25 % | **74** | **+4** | +7 / −3 | 30 |
| `trim40` | 丢掉最差 40 % | 73 | +3 | +7 / −4 | **31** |
| `q75` | `exp(−q75(Δ²)/σ²)` | 72 | +2 | +7 / −5 | 29 |
| `median` | 中位数 | **74** | **+4** | +8 / −4 | 30 |

三个观察，缺一个都会得出错误结论：

1. **涨的是同一批 7 个相，与估计量无关。** `trim10/25/40`、`q75`、`median` 的增益集合
   完全相同。真正的变量是「跌哪几个」，而跌的候选一直只有那四五个：`5-2` 的
   Cristobalite、`7-1` 的 Boehmite 几乎每个变体都掉。
2. **涨的相在现状下排 25–52 名，跌的相在现状下排 15–18 名。** 不是 Top-20 边界抖动
   （Goethite 25 → 3、Quartz 47 → 19、Corundum 52 → 15），是实在的重排。
3. **但两侧都是真值相。** 涨 7 个、跌 4 个，净 +3～+4 —— 这是**零和交换**，不是「修好」。
   `trim10` 之所以看起来最稳，只因为它恰好跌得少（4 个），不是因为它更对。

权重也要摆出来：`intensity = 0.1112`，占五分量总和 0.7299 的 **15.2 %**。一个只值 15 %
的分量，换一种估计量就能翻转 11 个相的进出 —— 说明这批相在 Top-20 边界上本来就挤在一起，
排序对这 15 % 的扰动不稳健。**在这种不稳健上做选择，选的是噪声。**

### 31.5 那处「Top-1 从 31 掉到 30」是命名口径，不是引擎退化

`median` / `trim25` 的 Top-1 少一格，全部来自同一个样本 `real/2-1`。核结构：

| 变体 | 榜首卡 | 空间群 | 晶胞 | 是方解石吗 |
|---|---|---|---|---|
| `base` | `96-157-7381` `O Zn` | P 6₃m c | a=3.251 c=5.209 | 锌矿（真值之一） |
| `median` | `96-702-2027` `C Ca O3` | **R -3 c** | **a=4.9915 c=17.0880** | **是**（方解石 a≈4.99 c≈17.06） |

`real/2-1` 的真值就是 Zincite + Calcite 两个。两个变体的榜首**都是真值相**，只是一个选
锌矿、一个选方解石。判它「不是 Top-1」的唯一原因是那张卡的 `mineral_name` 写的是化学名
`"Calcium Carbonate"`，而真值别名表里只有 `"Calcite"`。

`mineral_species_key` 第 3 步已经小写归一（`mineral_name.py:97`），所以这不可能是大小写
问题 —— 是**别名表缺项**。全库扫一遍名字含 carbonate / CaCO3 / calcite 的 72 张卡：

- `'calcium carbonate'` 只出现 **1 次**，就是这张 `96-702-2027`，晶胞落在方解石；
- `'caco3'` 也只出现 **1 次**（`96-702-0139`），同样是方解石胞；
- `'calcite'` 有 43 张，其中 31 张的晶胞按 0.06 Å 公差**不算**方解石胞 —— 所以别指望用
  晶胞去判多晶型，名称才是这里唯一可靠的判据。

别名缺口审计（被拒卡排名 vs 已接受卡最佳排名）共 11 行，分两类：

| 该补（同物异名 / 化学名 / 错拼） | 例证（被拒排名 / 已接受最佳） |
|---|---|
| `Calcite` ← `"Calcium Carbonate"` | 9 / 14 |
| `Calcite` ← `"CaCO3"` | 10 / 11 |
| `Boehmite` ← `"Bohmite"`（错拼，两处） | 10 / 15 |
| `Feldspar` ← `"Orthoclase"` | 59 / 74 |
| `Corundum` ← `"eta- Al-oxid_fit2gnn"` | 12 / 52 |

| 该拒（同组成不同多晶型，拒绝是对的） | 例证 |
|---|---|
| `Rutile` ← Anatase | 0 / 10 |
| `Cristobalite` ← Quartz | 0 / 191、4 / 16 |
| `Quartz` ← Cristobalite | 5 / 44、15 / 26 |

**关键结论：别名缺口不改变任何已发布的命中数。** 上表「该补」五行里，四行的已接受卡本来
就在 Top-20 内（真值已计入命中），第五行（Feldspar 59 / 74）两侧都在榜外。所以它只影响
**哪张卡代表这个真值相**，也就是只影响 Top-1 这种「看榜首身份」的指标，不影响召回。

因此**不需要为它第三次重跑历史数字**。要做的事只有一件：别把 Top-1 的排位当成纯引擎
信号 —— 它同时受命名口径与排序口径两块影响。

### 31.6 裁定：不改默认值

1. **净增益是零和交换。** 涨 7 跌 4，两侧都是真值相。+3/98（3.1 %）换 4 个相跌出榜，
   不满足「三把尺子同向为正」这条硬口径。
2. **改残差统计量治不了。** 31.2 的四个大偏离确实来自别的相的强峰被配到参考弱线上，但
   §32.2 的聚合统计说明那只解释少数病例；失败卡的 `ΣΔ²` 有 52.2 % 来自**强线**对
   （参考强线在实测里本来就弱）。换 mean / median / trim / quantile 只是改变对这些错配的
   **容忍方式**，一条错配都消不掉。
3. **强度分量只占 15.2 %**，却足以翻转 11 个相的进出 —— 说明 Top-20 边界本身是软边界。
   在软边界上按 +3 选参数，等于按噪声调参。
4. **缺精度侧指标。** 现在三把尺子全是召回口径，Top-20 里塞进多少错卡不受惩罚。任何
   「提高召回」的重排都无法被证伪 —— §30 已经因为同一个理由否过一条规则。

所以：**`sigma_intensity=10` 的均值模型保持不动，`compute_p_values` 的强度分支不改。**
同时更正一处归因：Kaolinite 漏检不是「择优取向」造成的，是**参考弱线被别的相强峰误配**
加上**判据对配对长度敏感** —— 但这只是该病例的主因，不是 29 个失败相的普遍主因（§32.2）。

### 31.7 重开条件

四条同时成立才值得重开：

- 有**精度侧指标**（Top-20 里的非真值相计数，或 CDP 含量口径不退化），否则无法判断
  +7 / −4 里哪一边是对的；
- 上游**参考强度门限**（`ref_cut`，只用 I_ref_norm ≥ 10 的对）在单独测试里表现正向 ——
  实测只有 +1，且已由 §32.2 解释为「弱线只占 Δ² 的 34–48 %」，所以这条基本可判定为死路；
  > 原写法「例如一对一强制分配」是错的：`_greedy_correlate` 用 `matched_ref` 集合，
  > **配对本来就已经一对一**，§32.1 用 5,721 张卡实测 0 次违反。
- 三把尺子（合成 / 13 组实验室 / IUCr）同向为正，且 Top-1 在**补齐别名后**的判据上不退化；
- 长度偏置被显式归一（按覆盖率补偿），而不是靠截尾把它掩盖掉。

## 32. 上游配对与 FoM 分量消融：为什么 29 个强度形失配修不动（2026-11-07）

§31 把强度形失配的成因指向「参考弱线被别的相强峰误配」，并把「一对一强制分配」写成了
上游的可选修法。本节先验那两条，再把 FoM 的五个分量逐个拿掉看边界怎么动。**结论：配对层
没有可修的缺陷，权重也不该动；唯一值得立项的候选是 `i_scale`，但它必须先补精度侧指标。**

### 32.1 配对本来就已经是一对一

`_greedy_correlate` 维护 `matched_ref` 集合，每个参考峰最多被用一次；每个实测峰在循环里
也只访问一次。实测验证：5,721 张候选卡的 `pairs` 里，**exp 索引重复 0 次、ref 索引重复
0 次**。

所以 §31.7 原来写的「例如一对一强制分配」是个假选项 —— 它就是现状。与之相关的另一个
「上游选项」是 `ref_cut`（只用 I_ref_norm ≥ 10 的对计算强度形），§31.4 已测：**+1**。
下面解释为什么它没用。

### 32.2 弱线是多数配对，却是少数偏差

按 `I_ref_norm < 10` 划「弱线对」，把 5,721 张卡分成「强度形通过」与「强度形失败」两组：

| 组 | 卡数 | 配对数 | 弱线对 | 弱线占配对数 | `ΣΔ²` | 弱线贡献的 `ΣΔ²` |
|---|---:|---:|---:|---:|---:|---:|
| 通过（`P_intensity ≥ 0.5`） | 1,172 | 28,177 | 20,188 | **71.6 %** | 826,769 | **34.4 %** |
| 失败（`< 0.5`） | 4,549 | 115,260 | 90,249 | **78.3 %** | 59,938,939 | **47.8 %** |

换成每对平均 `Δ²`：

| 组 | 弱线对均 `Δ²` | 强线对均 `Δ²` |
|---|---:|---:|
| 通过 | 14.1 | 67.9 |
| 失败 | 317.7 | **1,250.0** |

两条结论必须同时说，只挑一条都会误导：

1. **弱线对占配对数七成以上**（71.6 % / 78.3 %）—— 所以「大部分配对在信息量很低的线上」
   是对的，这也解释了 `P_intensity` 为什么对噪声敏感。
2. **但弱线只贡献 34–48 % 的 `ΣΔ²`，按每对平均反而比强线小一个量级**（失败组 318 对
   1,250）。失败卡的偏差质量一半以上来自**参考强线在实测里本来就弱** —— 次相含量低、
   择优取向、被别的相压制。

所以 §31.2 的「弱线劫持」只能解释 Kaolinite 那类**具体病例**（它的最大几对恰好都在弱线
上），不能当作 29 个失败相的普遍机制。普遍机制是**「该相的强线在实测里不成立」**，
那是样品与数据本身，不是判据写法能修的。§31.2 的结论段落已按此改写。

顺带解释了 `ref_cut` 为什么只有 +1：它拿掉的正是那 34–48 % 的偏差质量，剩下 52–66 % 的
强线偏差一分未动。

### 32.3 五分量消融：只有 `i_scale` 是双尺子同向

固定配对与 `p_values`，只改 `compute_fom` 的权重（把一个分量的权重置 0 或 ×3），
按尺子分开统计 Top-20 相召回（98 相）与 Top-1（32 组）：

| 变体 | 合计 | Δ | IUCr（/48） | real（/50） | 涨 / 跌 | Top-1 |
|---|---:|---:|---:|---:|---:|---:|
| `base` | 70 | +0 | 39 | 31 | 0 / 0 | **31** |
| `drop_peakpos` | 67 | −3 | 39 | **28** | 0 / 3 | 28 |
| `drop_intensity` | 73 | +3 | **42** | 31 | 7 / 4 | 30 |
| `drop_npeaks` | 67 | −3 | 39 | **28** | 1 / 4 | 29 |
| `drop_ncorr` | 69 | −1 | 39 | 30 | 0 / 1 | 30 |
| **`drop_i_scale`** | **72** | **+2** | **40** | **32** | **2 / 0** | **31** |
| `intensity × 3` | 69 | −1 | 40 | 29 | 2 / 3 | **27** |
| `drop_int + i_sc` | 74 | +4 | 43 | 31 | 11 / 7 | 29 |
| `i_sc=0 & int × 3` | 69 | −1 | 41 | 28 | 3 / 4 | 27 |

逐条读：

- **`peakpos` 与 `npeaks` 是承重墙**：拿掉各 −3，且损失全部落在真实谱（IUCr 一格未动
  —— IUCr 那批样本对这两个分量不敏感）。Top-1 也各掉 3 / 2 格。**这两个不能碰。**
- **`intensity` 的 +3 全部来自 IUCr**（39→42），真实谱 **+0**（31→31）。加上 7 涨 4 跌，
  这就是 §31.4 那批相在换位置。**跨不过尺子。**
- **`intensity × 3` 是灾难**：Top-1 从 31 掉到 **27**，真实谱 −2。这条最有用 —— 它说明
  「加大强度分量」的方向是明确错的，与 §31.4 的 `median` 变体（把强度看得更"干净"）
  结果一致：这个通道给的信息越重，排序越差。
- **`i_scale` 是唯一双尺子同向的**：IUCr +1、real +1，**零损失**，Top-1 一格未动。
  但它权重只有 0.0454，是五分量里最小的，增益 +2 相也仍在噪声量级。
- `ncorr` 拿掉 −1（丢 Fluorapatite），属于轻微承重。

### 32.4 裁定：配对与权重都不动

1. **配对层没有可修的缺陷。** 已经一对一；唯一的额外约束 `ref_cut` 只有 +1，且 32.2 给出
   了机制解释（弱线只占偏差质量的 34–48 %）。**§31.7 里「一对一强制分配」这一条是假选项，
   已更正。**
2. **权重是参考软件的发布值，不是我们的自由参数。** §26 已经裁定「权重保持发布值」；
   要改就是改产品语义，不是改度量。而现在的证据只有召回一侧。
3. **`intensity` 的正负取决于哪把尺子。** 去掉 +3（全在 IUCr）、加倍 −1（Top-1 −4）。
   一个分量在两把尺子上符号相反，说明它在这批数据上没有稳定的判别力 —— 这与 §31 的结论
   同源：强度通道被误配与含量效应污染，换写法换不掉。
4. **`i_scale` 登记为唯一候选。** 双尺子同向（+1/+1）、零损失、Top-1 不动，是本节唯一
   通过「不劣化」门槛的改动。但它是 +2 相 / 98（2 %），且缺精度侧指标，现在动它不划算。

**净结论：本节零代码改动。** 五项里两项承重（`peakpos` / `npeaks`）、两项有害但不可靠
（`intensity` / `i_scale`）、一项轻微承重（`ncorr`）。「强度形失配」不是一条判据写法能
解决的问题，它是「该相的强线在实测里不成立」这件事本身。

### 32.5 `i_scale` 的重开条件

三条同时成立才动它：

- **合成尺子**（`tools/bench_pattern_set.py`）上 T1/T5 不退化 —— 本节只测了两把真实尺子；
- 有**精度侧指标**（Top-20 非真值相计数或 CDP 含量口径），证明 +2 相不是靠放错卡进来；
- 与「权重保持发布值」这条既有裁定显式对账：要么改 §26 的结论并说明理由，要么把 `i_scale`
  的调整做成**可配置项**而不是新默认值。

> ①② 已在 §33 做掉：合成尺子通过、精度侧指标不通过（两把变差一把变好），
> 且「截断尾巴」在三把尺子上零变化 —— `i_scale` 由「唯一候选」降为「不推荐」。

## 33. `i_scale` 权重：三把尺子 A/B 与「截断」对照（2026-11-07）

§32.5 给 `i_scale` 定了三条重开条件。本节把 ①② 做掉：补上合成尺子与精度侧指标，
并在「删掉这一项」之外加一个更保守的对照 —— **截断它的尾巴**。

结论事先说：**`i_scale` 的无界尾巴不是问题（截断在三把尺子上零变化）；删掉它的 +2 相是
重新加权的效应，不是修 bug。默认值不动。**

### 33.1 `i_scale` 到底是什么

`compute_p_values` 先把两侧强度各自归一到 max = 100，然后取 LSQ 斜率
``s = Σ(I_exp·I_ref)/Σ(I_ref²)``，FoM 里扣 ``w · |ln s|``（`w = 0.0454`）。

因为**归一化在求 s 之前**，任何整体强度尺度差都已被消掉，`s` 只能反映「匹配上的那批峰的
形状偏强/偏弱」。所以它与 `intensity` 分量共享同一对归一化强度，实测秩相关
**Spearman 0.639**（8,324 张卡，Pearson 0.435）—— 部分重复，但不是同一件事。

它是唯一**无界**的分量，所以先量一下尾巴：

| 分位 | `|ln s|` | FoM 扣分 |
|---|---:|---:|
| p50 | 0.181 | 0.008 |
| p75 | 0.525 | 0.024 |
| p90 | 0.995 | 0.045 |
| p95 | 1.355 | 0.062 |
| p99 | 2.238 | 0.102 |
| max | 6.734 | **0.306** |

`|ln s| > 1` 的卡占 **9.9 %**、`> 2` 占 1.3 %；扣分均值 0.0171（占 `w` 本身的 37.6 %）。
最大值 0.306 相当于把 FoM 砍掉三成 —— 对一张典型 FoM≈0.7 的卡，这是致命的。

### 33.2 设计：四个变体 × 三把尺子

| 变体 | 规则 |
|---|---|
| `base` | 现状 `w · |ln s|` |
| `i_scale=0` | 整项删掉（`w = 0`） |
| `clamp1.0` | `w · min(|ln s|, 1.0)` —— 保留原意，砍掉尾巴 |
| `clamp0.5` | `w · min(|ln s|, 0.5)` |

三把尺子：合成谱 13 组 / 24 相（相位级）、IUCr 19 样本 / 48 相、13 组实验室谱 / 50 相。
外加**精度侧指标** `fp_above` = 排在「最佳真值卡」之前的非真值卡张数（按当前权重排序）——
它不与召回机械挂钩，召回涨了它未必降。

### 33.3 结果：只有「整项删掉」动得了，且是混合账

| 尺子 | 变体 | 相召回 | Top-1 | Top-5 相 | `fp_above` 均值 |
|---|---|---:|---:|---:|---:|
| 合成（24） | `base` | 16 | 8/13 | 13 | 9.83 |
| | `i_scale=0` | 16 | 8/13 | 13 | **10.00（差）** |
| | `clamp1.0` | 16 | 8/13 | 13 | 9.83 |
| | `clamp0.5` | 16 | 8/13 | 13 | 9.83 |
| IUCr（48） | `base` | 39 | 9/19 | 24 | 7.74 |
| | `i_scale=0` | **40** | **10/19** | 24 | **6.58（好）** |
| | `clamp1.0` | 39 | 9/19 | 24 | 7.74 |
| | `clamp0.5` | 39 | 9/19 | 24 | 6.63（好） |
| 真实谱（50） | `base` | 31 | 9/13 | 17 | 9.31 |
| | `i_scale=0` | **32** | 9/13 | 17 | **10.08（差）** |
| | `clamp1.0` | 31 | 9/13 | 17 | 9.31 |
| | `clamp0.5` | 31 | 9/13 | 17 | 9.31 |

### 33.4 截断零变化 ⇒ 「无界惩罚」是个假警报

`clamp1.0` 在三把尺子上**每一格都与 `base` 相同**（召回、Top-1、Top-5、`fp_above` 全等）。
`clamp0.5` 只在 IUCr 上把 `fp_above` 从 7.74 改到 6.63、把 `CPD-1C` 的首位真值名次从 40
提到 20，召回一格未动。

也就是说：**被 `|ln s| > 1` 惩罚到 0.045 以上的那 9.9 % 的卡，本来就远在 Top-20 之外。**
砍掉它们的尾巴不影响任何排名。§33.1 那个「0.306 的扣分」在纸面上很吓人，在 Top-20 边界
上**一个位置都没动**。

这条对别处也有用：**看到「惩罚项无界」先别急着截断，先测它影响的样本是否落在决策边界上。**
本例的答案是「不在」，所以整类「clamp 一下更稳」的改动都不必做。

### 33.5 那 +2 相是重新加权，不是修 bug

既然尾巴不影响结果，`i_scale=0` 的 +2 相就只能来自这一项在**正常量程内**对大量卡施加的
轻微惩罚被整体去掉。这是「改权重」的效应，与 §31.4 换估计量同类：净 +2 相（2 %），
代价是 `fp_above` 在两把尺子上变差（合成 +0.17、真实谱 +0.77），只有 IUCr 变好（−1.16）。

所以 §32.5 的三条重开条件判定如下：

| 条件 | 判定 |
|---|---|
| ① 合成尺子 T1/T5 不退化 | **通过**（16/24、8/13、13/24 三格全等） |
| ② 有精度侧指标且证明 +2 相不是靠放错卡 | **不通过** —— 指标有了，结果是**两把尺子变差、一把变好**（+0.77 / +0.17 / −1.16） |
| ③ 与 §26「权重保持发布值」对账 | **未处理** —— 本节没有改任何默认值 |

### 33.6 裁定：默认值不动

1. **条件 ② 不通过**：`fp_above` 在合成与真实谱上都变差。一个「提召回但让真值卡平均多
   被 0.77 张错卡压住」的改动，不是无代价的改进。
2. **机制上它不是 bug 修复**：33.4 证明唯一像 bug 的东西（无界尾巴）不影响排名；剩下的是
   一项 6.2 % 权重的重新分配。
3. **排序口径已经很挤**：§31/§32/§33 三项连着测下来，所有单点改动都在 ±3 相（±3 %）
   量级，且每项都伴随相近数量的反方向变化。**Top-20 边界是软边界，按这个量级调参是在
   选噪声。** 真要提升召回，杠杆在化学信息（§20 元素约束一次给 +10 相）与候选池
   （§23 预筛截断），不在排序权重。
4. **`i_scale` 从「唯一候选」降级为「不推荐」**：它通过了 ①，但 ② 不通过。重开只在
   出现**序贯口径**的正向证据时才考虑 —— 那一口径本节没测。

### 33.7 复现

```bash

```

探针只读库、只读谱；`clamp*` 在探针内部重算 FoM，`base` 走产品 `compute_fom`，
**产品代码一行未动**。


## 34. 候选池上界：98 相里只有 1 相卡在池外（2026-11-07）

§31–§33 连着证明排序权重这一层没有便宜可捡。本节量另一层 —— **真值相到底进没进候选池**，
把「池子太小」和「排序不对」分开。

### 34.1 分层：池外只剩 1 相

98 个真值相（元素 / 上界口径），`candidate_limit = top_n = 2000`：

| 最佳真值卡的名次 | 相数 | 占比 |
|---|---:|---:|
| Top-20 | 69 | 70.4 % |
| 21–100 | 20 | 20.4 % |
| 101–500 | 7 | 7.1 % |
| 501–1000 | 1 | 1.0 % |
| 1001–2000 | **0** | **0.0 %** |
| **池里根本没有** | **1** | **1.0 %** |

唯一池外的那一相是 `real/7-2` 的 **Hornblende**，而库里**有** `mineral_name='Hornblende'`
的卡 —— 所以它是**预筛漏捞**，不是库覆盖缺口。其余 97 相全在池内，其中 28 相排在 20 名外。

**结论：候选池不是瓶颈。** 把 `candidate_limit` 从 1000 抬到 2000，名次落在 1001–2000 的
相数是 **0**。

### 34.2 放大候选池反而更差

同一批样本，`candidate_limit=1000`（§32 的 base）Top-20 命中 **70**；
抬到 **2000** 之后是 **69**。多出来的 1000 张卡没有任何一相被捞回，却挤掉了 1 个真值相。

这与 §23 的结论一致：候选池的收益在「给元素约束」那一步，不在「加名额」。加名额只是加
竞争者。

### 34.3 那 28 相有多远：中位 52 名

名次分布本身就有信息 —— 它们不是「差一点」，而是分散：

| Top-N | 命中 | 占比 |
|---:|---:|---:|
| 20 | 69 | 70.4 % |
| 30 | 75 | 76.5 % |
| 50 | **83** | **84.7 %** |
| 100 | 89 | 90.8 % |
| 200 | 93 | 94.9 % |

20 名外的 28 相名次区间 **22–796**，中位 **52**。

这张表说明一件事：**在当前引擎下，唯一量级足够大的旋钮是 Top-N，不是排序参数。**
Top-20 → Top-50 多覆盖 **14 相（+14.3 个百分点）**；而 §31/§32/§33 里所有排序改动的
最好成绩是 **+3 相**。差一个数量级。

### 34.4 预筛截断只发生在 4/32 个样本

| 样本 | 池大小 | 实际打分 |
|---|---:|---:|
| `real/5-2` | 2000 | 2000 |
| `real/5-2b` | 2000 | 2000 |
| `real/5-3` | 2000 | 2000 |
| `real/7-2` | 2000 | 2000 |

32 个样本里只有这 4 个撞到 `candidate_limit` 上界，全是峰最多的实验室谱（也就是 §23 里
那批）。其余 28 个样本池大小 34–2000 不等，**根本没有被截断**。所以「预筛名额不够」不是
普遍问题，只在峰极多的谱上出现；而 §34.1 已证明给它们加名额也捞不回相。

### 34.5 读到这里的三个结论

1. **候选池上界已到顶**：2000 池里 98 相只缺 1 相，且那一相是预筛漏捞。继续加 `candidate_limit`
   是负收益（34.2）。
2. **剩下 28 相是排序问题**：中位名次 52，20 相挤在 21–100。而排序层已被 §31/§32/§33
   连续否掉 —— 三条独立路径、五个估计量、五个权重的排列组合，最好成绩 +3 相。
3. **唯一量级足够的旋钮是 Top-N**：20 → 50 多覆盖 14 相。它是一个**产品决策**（界面显示
   多少行、用户愿意滚多少），不是算法参数。本报告不下这个结论，只把数字摆出来：
   *Top-20 的 70.4 % 与 Top-50 的 84.7 % 差的不是引擎能力，是展示预算。*

### 34.6 复现

```bash
python .scratch/_probe_pool_ceiling.py   # 名次分桶 + Top-N 扫描 + 池外逐条定性
```

探针只读库、只读谱，只把 `candidate_limit` / `top_n` 调大，**产品代码一行未动**。


## 35. Top-N 上调可行性：GUI 用户看到的其实是族级 82.7 %（2026-11-07）

§34.5 把「Top-20 → Top-50 多覆盖 14 相」摆成了产品决策的候选数字。本节做落地前的可行性
调研，**先修正 §34 的一个口径**：那个 +14 相是**卡级**数字，而 GUI 的候选表是**按族合并**
显示的 —— 用户看到的是「前 20 个族」，不是「前 20 张卡」。

### 35.1 族级口径：现状已经是 82.7 %

同一批名次（98 相、元素 / 上界、池 2000），按 §29 修复后的族口径（一行 = 一个相族，
族首名次 = 族内最佳成员）重算：

| 显示行数 | 族级覆盖 | 占比 | （对照：卡级） |
|---:|---:|---:|---:|
| 20 | **81**/98 | **82.7 %** | 69（70.4 %） |
| 30 | 85/98 | 86.7 % | 75（76.5 %） |
| 50 | **89**/98 | **90.8 %** | 83（84.7 %） |

两个结论：

1. **GUI 现状（20 行）已经覆盖 81/98 = 82.7 %**，比卡级 Top-20 高 12 个百分点 —— 族合并
   本身就是一层「免费的召回」。
2. **把显示从 20 行提到 50 行，收益是 +8 相（81 → 89）**，不是卡级口径的 +14。仍然是
   §31/§32/§33 所有排序改动（最好 +3）的两倍多，但量级要按 8 报，不能按 14 报。

### 35.2 Top-N 在产品里住在哪（全部调用点）

| 位置 | 现状 | 说明 |
|---|---|---|
| `core/search/search_match.py:231,278` | `top_n=20` | v2/v3 两分支默认 |
| `core/search/fpfm.py:209` | `top_n=20` | FPFM 分支 |
| `core/search/pfsm.py:322`、`sequential.py:785` | `top_n=20` | 序贯 / PFSM |
| `core/db/search_v3.py:172`、`__init__.py:242,291` | `top_n=20` | v3 直连与 re-export |
| `cli/main.py:864,964` | `--top-n` 默认 20 | CLI 用户已可自行调 |
| `ui/main_window.py:1410` | **不传** → 吃默认 20 | 整谱检索 |
| `ui/main_window.py:1729` | **显式 20** | 序贯剩余峰检索 |
| `ui/main_window.py:1801` 附近 | **不传** → 吃默认 20 | FPFM 分支 |
| `tools/run_acceptance.py`、`validate_peak_engine.py` | 10 | 验收工具，与产品无关 |

**计算成本为零**：`search_match_v3` 是先对整个候选池（≤ `candidate_limit`=1000）完整打分
排序，再 `ranked[:top_n]` 切片。返回 200 张卡与返回 20 张卡的打分开销完全一样，
只多传回 180 个对象。

### 35.3 一个必须先想清楚的映射：显示「族数」≠ 返回「卡数」

族合并只会**减少**行数：返回 50 张卡可能只合并出 35 个族。所以「显示 50 个族」需要
返回**多于 50 张卡**。两个可行做法：

- **A. 多取卡 + 全显**：`top_n=200`，表格按族合并后有多少显多少（表格本来就可滚动）。
  实现最简单（三处调用改一个数字），但默认视图会从 ~18 行跳到几十上百行，变化太猛。
- **B. 加第 4 个设置项（推荐）**：「候选列表族数上限」，默认 50，存 QSettings —— 与
  「设置 → 选项 → Search-Match」页现有三个 FPFM 旋钮同一模式。GUI 三处调用取
  足够多的卡（如 200），表格按族合并后**截到设置的上限**。用户可调、可关。

### 35.4 测试与联动的坑

- `tests/ui/test_fpfm_kalpha2.py`、`test_search_mode.py` 用 `kwargs.setdefault("top_n", 10)`
  把 GUI 调用**钳到 10** 以缩短耗时。如果 GUI 改成**显式传** `top_n=200`，`setdefault`
  不再生效，这两个测试会变慢 —— **必须走设置项**（测试把设置设小），不能硬编码传参。
- 其余测试全部显式传 `top_n=`，没有断言「默认 20 行」的用例；CLI 默认不动就没有兼容问题。
- `_run_report_preview`（报告/打印）渲染的是同一份候选列表 —— 行数上限应与表格同一来源，
  否则报告会比界面多出一截。

### 35.5 结论与建议

| 项 | 判定 |
|---|---|
| 收益 | 族级 81 → 89（**+8 相，+8.2 pt**）；卡级口径的 +14 是错误引用，已修正 |
| 计算成本 | **零**（纯切片，打分早已算完） |
| 实现面 | GUI 三处调用 + 一个设置项 + 表格截断；CLI 不动 |
| 风险 | 测试钳位失效（走设置项即可避开）、报告行数需同步 |
| 建议 | **值得做，走方案 B**；作为独立小项排期，默认值 50 属产品决策，可由用户改 |

§34.3 的卡级表保留不动（它是引擎口径的客观分布），但引用它的「+14 相」必须改读 §35.1 的
族级 +8 相。

