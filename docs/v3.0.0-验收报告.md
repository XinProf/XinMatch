## 6. 元素抽取缺陷与修复（2026-10-21）

### 6.1 发现方式

新写的只读验收工具 `tools/validate_xindb.py` 对已建成的 `COD-Inorg-20261020.xinDB`
报出：

```
[WARN] E2.elements  799 entries carry no element list (1.02%)
```

追查后确认这不是"数据瑕疵"而是**产品级 bug**：这些相在 `element_inv` 里没有条目，
用户只要勾选任何元素筛选，它们就被**静默排除**在候选之外 —— 无论峰的吻合度多高都不会
出现在结果里。属于典型的"库看起来完整、结果却少一批"的静默失效。

### 6.2 四种独立成因

| # | 成因 | 命中数 | 修复 |
|---|---|---|---|
| 1 | `_chemical_formula_sum` 写成 CIF **文本字段**（`;...;` 多行），gemmi 把分隔符原样返回 | 337 | 剥离首尾 `;`，并把内部换行折叠成单空格 |
| 2 | 文件只写 `_chemical_formula_structural` / `_chemical_formula_moiety`，无 `_chemical_formula_sum` | 40 | 加三级兜底链 `sum → structural → moiety` |
| 3 | 任何化学式字段都没有，但原子位点完整 | 418 | 新增 `elements_from_sites()`，从 `_atom_site_type_symbol` 取元素 |
| 4 | 纯氘/氚化物（`D`、`D2`、`T2 O`），`D`/`T` 不是 IUPAC 符号 | 4 | `_HYDROGEN_ISOTOPES = {"D": "H", "T": "H"}` |

成因 1 的实样（COD 1001818）：

```
_chemical_formula_sum
;Al1.15 Ba0.04 Cr0.01 Fe0.25 H2 K0.89 Mg1.57 Mn0.4 Na0.1 O12 Si2.92 Ti0.07
 Zn0.54
;
```

`_first_block_value()` 只处理了 `'...'` / `"..."` 两种引号形式，没有处理分号文本字段，
于是 `elements_from_formula()` 拿到 `";Al1.15 ..."`，首个 token 不是元素符号 → 返回 `[]`。
顺带影响 `entries.formula` 的显示（GUI 里会出现一串分号）。

成因 3 的取法是取符号头部（`Fe3+`→`Fe`、`O2-`→`O`、`K1+`→`K`），并用 IUPAC 白名单
过滤掉占位符（COD 里出现 `M`），因此不会凭空造出元素。

### 7.2 `--resume` 已实现并通过无损性验证（2026-10-22）

原 `--resume` 是空壳：参数只被复制进日志变量 `last_done`，从未用于跳过已处理的 CIF；
而 writer 的 `_guard_existing_database` 会拒绝打开已含 entries 的文件。本次实现并验证。

**为什么直接追加会毁库。** `entries` 与 `peak_chunks` 是**两条独立提交的流**：
`entries` 每 `_ENTRY_BATCH`=2000 相刷一次，`peak_chunks` 每 `chunk_size`=4096 相刷一次，
两次提交互不等待。进程被杀时两条流不对齐，且残状态有**两种**，不是一种：

| 残状态 | 成因 | 占比 |
|---|---|---|
| **entries 超前** | 尾部 entries 的峰值载荷还没落盘 | 常见（entries 刷盘频率是 chunk 的两倍） |
| **chunks 超前** | chunk 已提交，但它尾巴上的 entries 还在缓冲里 | 不罕见：落在 chunk 提交后的窗口内即可，约覆盖 44% 的相数落点 |

只处理第一种会漏；把 `covered > entries_n` 判为"文件不一致"直接拒绝，等于近一半的杀进程时机无法续建。

**三处改造。**

1. `element_inv` 由「内存累加」改为 **`close()` 时从 `entries.elements` 重建**。
   这是续建的前提：原来的倒排索引活在进程内存里，进程一死，已写入几十万相的元素索引就永久丢失。
   顺带把 40 万相级别「每元素一个 Python list」的常驻内存也去掉了。
2. writer 新增 `resume=True`：把两条流**一起回卷到彼此都认可的最后 chunk 边界**
   （`target = min(entries_n, covered) // chunk_size * chunk_size`），
   多余的 entries 行与不完整的 chunk 一并删除，再从 `entries` 重建 `_seen_ids`、
   `_global_peak`、`_next_index`、`_chunk_id`。
   **几何参数不再依赖 `meta`**（中断的库根本没有 meta，`meta` 是 `close()` 才写的），
   改为用 chunk 自身的字节长度校验 `chunk_size` 与 `top_k`，不一致就拒绝而不是写坏。
3. 归档步进起点改为**第一个被回卷的相**（`writer.resume_from_entry_id`），
   而不是「最后一条已存相的 id + 1」。这是最容易犯的错：被回卷的相从未写进 chunk，
   若从「最后一条已存相之后」开始走，那批相就**永久丢失且毫无报错**。

**验证方法：等价性实验**（`tools/_verify_resume_equivalence.py`）。
不靠推理，靠对表：先不中断跑出参照库，再在子进程里 `os._exit()` 模拟被杀（不 close、
不滚回、不 flush），续建到同样相数，然后把**每张表**逐字节比对：

| 用例 | 残状态 | 回卷到 | 结果 |
|---|---|---|---|
| A | entries 超前（14,000 entries / 12,288 chunks） | 12,288 | **逐表全等** |
| B | chunks 超前（12,000 entries / 12,288 chunks） | 8,192（丢 1 个 chunk） | **逐表全等** |

比对项：`entries` 的 `rowid` + 全部 24 列、`peak_chunks` 的 `top_d/top_i/all_d/all_i` 原始字节、
`element_inv`、`meta`（除 `build_time`），以及 `mask_truncated` 计数。规模 16,000 相 / 1,263,236 条反射。
命令：`$PY -m tools._verify_resume_equivalence`（默认合成数据，秒级；加 `--real` 用真 CIF，慢但结论相同）。

**在真实残库上的核对**（414,000 相的 COD-Full 中断库）：

| 项 | 结果 |
|---|---|
| 回卷到 | 413,696 = 101 × 4096，精确落在 chunk 边界 |
| 丢弃 | 304 行孤立 entries，0 个 chunk |
| 重算起点 | `96-712-8203`，正是被丢弃的第一相；`iter_cod_cifs(start=7128203)` 首个产出也是 7128203 |
| 恢复的计数器 | `rowid` 413,696 / `chunk_id` 101 / 累计反射 60,446,681 |
| `close()` 时重建 413,696 相的元素倒排 | **0.7 s**（可忽略） |

**代价与局限。** 续建最多重算**一个 chunk（4,096 相）**——残状态是「chunks 超前」时，
那条 chunk 的尾部 entries 已丢，只能整块重算。对 535,166 相的 Full 库是 0.77%，可接受。
`mask_truncated` 原本只统计本轮、续建会少报，已改为从 `entries.elements` 精确重算
（判据「含 bit ≥ 63 的元素」与 `_unmapped_elements` 完全等价）。
`--resume` 对**已 `close()` 的成品库**会明确报"没有可续的内容"，不会去动它。

### 8.1 id 空间必须按来源分开

PCOD 的 id 与 COD 处在**同一 7 位数字空间**（`1000000` 起），直接沿用 `96-XXX-XXXX`
会让 PCOD `1000000` 与 COD `1000000` 生成同一个 entry id，两个库一旦同时挂载就会互相遮蔽。
沿用 3COD 打包时代的既有约定，按来源平移进各自区间：

| 源 | 归档 id | 入库 id | entry_id |
|---|---|---|---|
| COD | `1000005` | `1000005` | `96-100-0005` |
| PCOD | `1000000` | `21000000` | `96-210-00000` |
| TCOD | `10000001`（8 位） | `110000001` | `96-110-000001` |

为此改了三处：

- `cif_scan._cod_id_text` 原本硬限 7 位，TCOD 的 8 位 id 会直接 `ValueError`；
  上限放到 `10^9-1`，`cod_cif_relpath` 仍只对 7 位布局负责并在越界时显式报错。
- `cif_scan._dir_id_range` 原本按「7 位总宽 − 前缀长度」推剩余位数，
  在 TCOD 的 8 位 id 上下溢，`--resume` 传 `start` 时会**误剪子树导致静默丢相**；
  改为纯字符串前缀比较（目录名就是 id 定宽前缀，字典序即数值序），7/8/9 位通吃。
- `build(..., id_offset=)`：写入时取 `cod_id + offset`，resume 起点反向减回去，
  保证「库内 id 空间」与「归档 id 空间」不混。`build_cod_inorg_xindb.py` 增加
  `--source {COD,PCOD,TCOD}`，默认 `COD`，旧用法不变。

### 8.2 PCOD 的 CIF 是按 P1 展开写的

PCOD 的 `_symmetry_space_group_name_H-M` 一律写 `"P1"`，真实对称性（如 `P -4 M 2`）
只出现在标题文本里，原子位点则已**全部显式展开**（如 SiO₂ 给出 5 个 Si + 10 个 O）。
所以按 P1 计算粉末图是**正确**的，与 COD 的对称性展开路径不可混谈。

但这带来一个附带缺口：`gemmi.SmallStructure.spacegroup_number` 对**无空格写法** `"P1"`
返回 0，导致 `crystal_system` 全为 NULL —— 100 万相会集体从「按晶系筛选」里消失。
已加兜底 `gemmi.find_spacegroup_by_name()`（认 `P1` → `P 1`，number=1，triclinic）。
修复后 PCOD / TCOD 的 `crystal_system` NULL 计数均为 **0**。

> **更正（2026-10-23 验收时发现）**：本报告早前写「对 COD 无影响」，这句话是错的。
> COD 源 CIF 确实多数带 `_space_group_IT_number` 与规范写法的 H-M 符号，但仍有

### 8.4 检索耗时：PCOD 4.8 s 的根因（已定位，未优化）

PCOD 比 TCOD 慢 13 倍，原因是**两段成本都正比于库规模**，不是某处退化。
`data/_prof_search_pipeline.py` 的实测拆分（40 个测量窗、候选 800、热缓存）：

| 阶段 | TCOD 46,846 相 | PCOD 1,061,953 相 | 倍数 | PCOD 占比 |
|---|---|---|---|---|
| 1 `prescreen` | 106.0 ms | **3,010.0 ms** | 28× | 66.4% |
| 2a `fetch_peaks` | 55.1 ms | **1,293.1 ms** | 23× | 28.5% |
| 2b `fetch_meta` × 800 | 25.7 ms | 30.4 ms | 1.2× | 0.7% |
| 3 `rank_candidates` | 102.2 ms | 202.4 ms | 2× | 4.5% |
| 合计（热） | 289.0 ms | **4,535.9 ms** | 15.7× | — |
| 合计（冷，含矩阵加载） | 331.7 ms | 5,144.2 ms | 15.5× | — |

- **prescreen**：每个测量窗都对整张 `top_d` 矩阵做一次 `(>= lo) & (<= hi)` 全量布尔运算
  再 `any(axis=1)`。PCOD 的矩阵是 1,061,953 × 32 float32（单张 130 MB，d+i 共 259 MB），
  单窗 **75 ms**；TCOD 单窗 2.65 ms —— 比值 28× 略高于相数比 22.7×，是缓存效应。
- **fetch_peaks**：为定位 800 个相，要**顺序解码全部 260 个 chunk**，
  即把 1.27 GB 的 float32 峰数据整个解一遍（159,274,265 反射 × 2 数组 × 4 B）。
  1,293 ms 基本就是这段解码时间。库越大越亏，且与命中多少无关。
- `rank_candidates` 只跟候选数（800）有关，与库大小无关，所以倍率只有 2×。

**评估**：4.5 s 是 106 万相规模的正常代价，没有病态路径；但交互式使用偏慢。
若要压到亚秒级，两处都需要结构性改造（不在本轮验收范围）：

1. `prescreen` 改用 **d 值倒排索引**（按 0.02 Å 分箱建 `bin → 相 id` 倒排，类似 `element_inv`），
   单窗成本从 `O(N·top_k)` 降到 `O(命中相数)`。
2. `fetch_peaks` 改用 **chunk 边界表**（schema 增 `first_peak_off` 列），
   按 `peak_off` 直接跳到目标 chunk，不再整库扫描。

两项都需要 schema v3.1，属于独立任务。

### 8.5 COD-Inorg 缺晶系：已原地修复（2026-10-23）

COD 库建于 2026-10-21，早于 `find_spacegroup_by_name` 兜底补丁，残留 681 条
`crystal_system` 为 NULL 的记录，这些相会从「按晶系筛选」里消失。
**只影响这一个筛选维度，峰数据与检索打分不受影响**（晶系是纯元数据）。

#### 8.5.1 先补两处代码缺口

只补 `find_spacegroup_by_name` 一档修不干净，全量重解析后有 347 条仍是 NULL。
于是给 `cif_meta` 加了两处：

1. **`_symmetry_cell_setting` 兜底**：磁结构 / 超空间群的对称性写成
   `_space_group_ssg_name  Imma(00\g)s00`，既无 IT 号也无规范 H-M 符号，但晶系是直接
   写明的。新增 `_CELL_SETTING_TO_SYSTEM` 映射（`rhombohedral` 归入 `trigonal`，
   因为七晶系分类把菱面体格子并进三方）。
2. **`volume` 回归修复**：`read_small_structure` 对少数 COD 文件的晶胞标签读不出来，
   `ss.cell` 退化成默认的 `(1,1,1,90,90,90)`，`is_crystal()` 为 False，本该拿到的体积被丢掉。
   改为在 `ss.cell` 不可用时用六参数重建 `gemmi.UnitCell` 再算体积
   （例：`96-156-3735` 恢复为 358.316 Å³，与旧库数值精确一致）。

#### 8.5.2 等价性判定：重建到底会改什么

`data/_meta_diff_cod.py` 用**当前代码**把 78,036 个源 CIF 全部重解析，与库内 18 个元数据列
逐列比对。结论是重建**只会改动 670 行**，且只动两列：

| 列 | 不一致行数 | 说明 |
|---|---|---|
| `crystal_system` | **670** | NULL → 具体晶系 |
| `space_group` | **11** | 符号规范化（`Fm-3m` → `F m -3 m`），同一空间群的另一种写法 |
| 其余 16 列 | **0** | formula / elements / elem_mask / 六个晶胞参数 / volume / density / 文献字段全部一致 |

> 比对过程中踩了两个「判据口径错」：① `element_mask()` 返回 `(lo, hi)` 二元组，
> 直接和库里的整数比会得出「100% 不一致」；② 建库器按**63 位截断**存储
> （`low & _MAX_STORABLE_MASK`），不套这个截断也会全错。按库内
> `meta.element_mask_bits=63` 复算后，`elem_mask` 不一致为 0。

#### 8.5.3 执行

`tools/_patch_meta_cod_inorg.py`：单事务 UPDATE 670 行的 `space_group` + `crystal_system`，
不碰 `peak_chunks`。带一道安全护栏——只允许「NULL → 值」和「同一空间群的符号规范化」
（用 `find_spacegroup_by_name` 比对编号），任何把已有值改成别的空间群的操作直接拒绝。

补丁前先备份为 `COD-Inorg-20261020.xinDB.bak-20261023-beforemeta`。

| 指标 | 补丁前 | 补丁后 |
|---|---|---|
| `crystal_system` 为 NULL | 681 | **11** |
| `validate_xindb` | 0 fail / 1 warn / 26 项 | 0 fail / **1 warn** / 26 项（同一 warn，见 §8.6） |

#### 8.5.4 三重验证

1. **结构**：`validate_xindb` 26 项 0 fail。
2. **物理量未变**：`_compare_xindb_peaks <备份> <补丁后>` → `entry order identical: True`，
   `PASS: all 20 chunks hash identically across top_d/top_i/all_d/all_i`。
3. **与重建等价**（决定性实验，`data/_verify_patch_equiv.py`）：把 670 个受影响相 +
   130 个随机对照相硬链接到临时目录，用**当前代码**重建一个 798 相的临时库，再逐相对照：
   - 18 个元数据列：不一致 **0**
   - 峰数据字节（d 与 I 的 float32 流）：不一致 **0**

   → **原地补丁的结果与整库重建逐字节相同。**

#### 8.5.5 「补丁 ≡ 重建」为什么成立

- **峰与元数据解耦**：`compute_pattern(cif_path, ...)` 只吃 CIF 路径，不读 `parse_meta`
  的输出；`peak_compute.py` 自建库以来未修改（mtime 2026-10-21 12:42 < 建库 18:23）。
  所以晶系修复不可能动到峰。
- **元数据是纯函数**：`parse_meta` 对同一 CIF 是确定性的，补丁写入的就是它当前会返回的值。
- **重建还会多改什么？** 只有 `build_time` 这一个时间戳。补丁刻意保留原始 `build_time`
  ——它应该记录「这个库是什么时候建的」，原地补不该冒充重建。

#### 8.5.6 剩下 11 条为什么不修

| entry_id | space_group | 原因 |
|---|---|---|
| `96-900-4170` `96-900-7430` `96-900-7431` `96-901-0978` `96-901-0979` `96-901-1487` | `F 1 2/d 1`、`F d d`、`F -4 d 2`、`C 1 1 21/d` | 非标准/缩写写法的 H-M 符号，gemmi 拒绝解析；全部来自 AMCSD（`900-*`），源数据本身不规范 |
| `96-152-8279` `96-154-4612` `96-154-4613` `96-433-1458` `96-210-4629` | 空 | 源 CIF 的 `_space_group_IT_number` 写的是 `?`，且无 `_symmetry_cell_setting`，**数据源没有提供** |

这 11 条只占 0.014%，靠晶胞度规只能定晶格系、分不出三方/六方，强行填等于编造，故留空。

### 8.6 顺带发现：3 个相拿到假峰（未修，留给重建）

`gemmi.read_small_structure` 对少数 CIF 读不到晶胞时，会返回默认的 `(1,1,1,90,90,90)`。
`compute_pattern` 并不知道这是默认值，照此算出 **d = 1.0 Å 的单峰**。

全库扫描 `is_crystal() == False`：COD-Inorg 源里有 **54 个** CIF，但只有 **3 个**落进库：

| entry_id | 现状 | 文本晶胞 | 可用文本晶胞恢复后 |
|---|---|---|---|
| `96-156-3735` | 1 个假峰（d=1.0） | a=4.2606, c=19.739 | **150 个真峰**，d 0.7708–19.739 |
| `96-156-3736` | 1 个假峰（d=1.0） | a=4.3581, c=10.1704 | **114 个真峰**，d 0.7711–10.1704 |
| `96-210-4629` | 1 个假峰（d=1.0） | 无 | 只能剔除 |

这 3 个峰占全库 9,394,774 个峰的 **0.00003%**。`validate_xindb` 那条 `E1.lattice`
warn 就是 `96-210-4629`（NULL 晶胞 + 1 个假峰）触发的。

**正确修法是「晶胞恢复」，不是「丢掉相」。** 前两相的元数据晶胞本来就是对的，
用 CIF 文本标签的六参数重建 `gemmi.UnitCell` 后能算出正常粉图，最强线位置与元数据的
c 值精确吻合。丢相版会净损失这 2 个相；恢复版净收益 2 个相。

规模是 **COD 独有**：抽样 20,000 个源 CIF，COD 晶胞读不到 2 个（0.01%，全库约 54 个），
**PCOD 0、TCOD 0**。

这属于「碰峰」类改动，会改变峰输出，**无法原地补**——已登记为待办（Task #15），
等建 COD-Full 的窗口顺手重建 COD-Inorg 时一起落地。
