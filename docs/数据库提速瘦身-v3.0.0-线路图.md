# XinMatch v3.0.0 数据库提速与瘦身 —— 可执行线路图

> 版本：**2.0.0 → 3.0.0**（升一个大版本）
> 范围：**仅 XinMatch 项目**，不考虑 PolyXRD 兼容、不兼容历史老库（旧 `.db` 一律重建）
> 目标：物相检索**更快** + 数据库**更小**
> 基线：`cod_inorganics.db` 745 MB / `cod_full.db` 987 MB / `cod_full_curated.db` 836 MB

---

## 0. 结论摘要（TL;DR）

| 维度 | 现状（实测） | v3.0.0 目标 | 依据 |
|---|---|---|---|
| 默认库体积 | 745 MB | **≈85 MB（~9×）** | peaks 行表 + 3 索引占 95%，改列存打包后消失 |
| cod_full 体积 | 987 MB | **≈110 MB（~9×）** | 同上，452 MB 行表 + 464 MB 索引 → 打包 BLOB |
| 首检冷启动 | 2~5 s（全表流式扫 peaks 建 top-K 缓存） | **<0.1 s**（top-K 矩阵入库即成） | 消灭 `_load_top_k_intensities` 全表扫描 |
| 单峰窗口查询 | 每测量峰一次 `GROUP BY` SQL 往返 | 纯 numpy 向量化预筛 | 复用 PolyXRD 已验证的 `(N,K)` 矩阵预筛 0.1~0.3 s 思路 |
| 体积病根 | 峰数据「行表化 + 3 个 B-tree 索引」 | 列存打包（float32 BLOB） | §2 实测归因 |

**一句话结论**：XinMatch 的库体积与速度病根和 PolyXRD 完全相同——峰数据被存成"每行一条峰"的低密度行表，再叠加 3 个索引撑起 95% 体积。v3.0.0 把峰改为**列存打包 + 构建期生成 top-K 预筛矩阵**，体积降 ~9×、检索免全表扫描。

## 1. 现状体检（实测数据，2026-10-21）

### 1.1 库体积归因（只读 dbstat 实测）

**`cod_inorganics.db`（745 MB，71,206 相，621 万峰）**

| 对象 | 体积 | 占比 |
|---|---|---|
| `peaks` 行表 | 283.8 MB | 38% |
| `idx_peaks_entry_intensity` | 176.7 MB | 24% |
| `idx_peaks_entry_id` | 125.9 MB | 17% |
| `idx_peaks_d` | 119.9 MB | 16% |
| `entries` + `elements` + 其余 | ~39 MB | 5% |

**`cod_full.db`（987 MB，112,734 相，1098 万峰）**

| 对象 | 体积 | 占比 |
|---|---|---|
| `peaks` 行表 | 452.0 MB | 46% |
| `idx_peaks_entry_id` | 254.6 MB | 26% |
| `idx_peaks_d` | 209.6 MB | 21% |
| `entries` + `elements` + 其余 | ~70 MB | 7% |

> **共同病根**：`peaks` 行表 + 它的索引占 **93~95% 体积**。每行一条 `(entry_id, d, intensity, h, k, l)`，d/intensity 用 8 字节 REAL，加 3 个 B-tree 索引（其中 `idx_peaks_entry_intensity` 还是运行时在 `query_peaks.py` 里 `CREATE INDEX IF NOT EXISTS` 临时建的）。

### 1.2 速度瓶颈定位（按收益排序）

| # | 瓶颈 | 位置 | 根因 |
|---|---|---|---|
| 1 | **top-K 缓存全表流式扫描** | `query_peaks.py::_load_top_k_intensities` | 每次进程首次检索要把整个 peaks 表 `ORDER BY entry_id, intensity DESC` 扫一遍（71k 相 2~5 s；112k 相 ~5 s），仅在内存 LRU 缓存，不落盘 |
| 2 | **每测量峰一次 SQL 往返** | `query_peaks.py::search_by_d` | N 个测量峰 = N 次 `WHERE d BETWEEN ? AND ? GROUP BY entry_id`，候选集在 Python 侧累加 |
| 3 | **临时建索引** | `query_peaks.py:224-227` | `strongest_k>0` 时运行时 `CREATE INDEX idx_peaks_entry_intensity`，首次触发要付一次 176 MB 索引构建 |
| 4 | **元素过滤非倒排化** | `query_filter.py::search_by_elements` | 虽用了 `elements` 倒排表，但 `excluded` 分支仍是 `SELECT DISTINCT entry_id ... IN (...)` 全表相关子查询 |
| 5 | **峰详情逐条 SQL** | `search_match.py`（候选打分时） | 每个候选单独 `WHERE entry_id=?` 取全峰（与 PolyXRD `_rank_candidates` 同病） |

## 2. 设计原则（新格式 v3 / 暂名 `xinmatch3`）

1. **列存打包，不存行表**：峰与位点一律定长二进制数组（float32），`np.frombuffer` 零拷贝。
2. **检索只碰强峰矩阵**：库内直接存好 `(N, K=32)` top 强峰矩阵，开库即 mmap，**运行时零建索引**（消灭 §1.2 的 #1、#3）。
3. **两级检索 + 硬上限**：强峰矩阵向量化预筛 → ≤800 候选 → 才解全峰 → 现有 FoM/Hanawalt 打分（**打分口径一行不改**）。
4. **元素位图整数运算**：`entries` 加 `elem_mask`（uint64 位图），替代 `excluded` 相关子查询。
5. **meta 自描述**：`schema_version` / `peak_convention` / `top_k` / `dtype` / 构建工具与时间戳。
6. **无历史包袱**：旧 `.db` 一律重建，不保留旧格式 reader、不做迁移兼容。

## 3. v3 schema 草案

```sql
-- 单文件 .xinmatch3（SQLite 容器）
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);   -- schema_version=3, top_k=32, dtype=f32

CREATE TABLE entries (                                    -- 每相一行
    entry_id    TEXT PRIMARY KEY,                         -- 沿用 COD ref_id（如 96-400-1849）
    formula     TEXT, space_group TEXT, mineral_name TEXT,
    crystal_system TEXT, color TEXT, quality TEXT,
    year INTEGER, author TEXT, journal TEXT,
    elements    TEXT,          -- "O,Ti" 逗号串（显示/复核用）
    elem_mask   INTEGER,       -- uint64 元素位图（过滤用，整数运算★）
    a,b,c,alpha,beta,gamma,volume,density REAL,
    n_peaks     INTEGER,
    peak_off    INTEGER, peak_n INTEGER,   -- → peak_chunks（CSR）
    tier        INTEGER        -- 优选分层（去重/质量，见 §7）
);

CREATE TABLE peak_chunks (                                -- 打包峰数据
    chunk_id    INTEGER PRIMARY KEY,                      -- chunk = 4096 相
    top_d       BLOB, top_i   BLOB,       -- (n,32) float32 预筛矩阵★
    all_d       BLOB, all_i   BLOB        -- CSR float32 全峰（仅候选解）
);
```

**体积测算**（cod_inorganics 71,206 相 × 平均 87.3 峰）：

| 组成 | 估算 |
|---|---|
| 全峰 `all_d/all_i` float32 | 71,206 × 87.3 × 4 B × 2 ≈ 50 MB |
| 预筛矩阵 `top_d/top_i` (N,32) f32 | 71,206 × 32 × 4 B × 2 ≈ 18 MB |
| `entries` 元数据 + 元素位图 | ~15 MB |
| 索引（仅 entry_id PK + elem 倒排） | ~2 MB |
| **合计** | **≈85 MB（现 745 MB）** |

## 6. 明确不做 / 风险登记

| 项 | 决定 | 理由 |
|---|---|---|
| 改 FoM/Hanawalt 打分权重 | **不做** | 改了基准就不可比，且非本任务目标 |
| 兼容 PolyXRD / 历史老库 | **不做** | 用户明确"不用考虑对方兼容、不背历史包袱" |
| 检索路径写库 | **禁止** | 一律 `mode=ro` / mmap |
| 全谱拟合进主链路 | **不做** | 无关本任务 |
| 大库排序稀释 | 内建 `tier` 分层，交互库默认 10~30 万条 | 复用 PolyXRD 已验证结论 |

---

## 7. 附：`tier` 分层说明（可选优化，建议并入 M1）

XinMatch 实测"库越大 top-1 越差"（同相复本稀释）。`cod_full_curated.db` 已按 `(formula, space_group)` 去重，方向正确。v3 建议在 `entries` 加 `tier` 列（0=实验测定优先 / 1=预测 / 2=理论），默认交互库控制在 10~30 万条，与"库小 + 快"同向。
